# Uina 架构审查（2026-09-12）

审查基准：实际源码（89 个 .ts）。文档仅作线索，所有结论均核对过调用链。
判断标准：第一性原则 / 奥卡姆剃刀 / 高内聚低耦合 / 状态唯一所有者 / Core 只给机制。

优先级：**P0 = 根因性重复或真实缺陷，P1 = 明确的职责越界，P2 = 清理与简化。**

## P0-1 生命周期事实有 4 套表示，这是全项目最大的复杂度来源

同一个 `turn_start` / `tool_done` 事实，被四套类型各表示一次：

| 层 | 定义 | 位置 |
|---|---|---|
| 1 | `LoopHooks`（9 个回调） | `agent/loop.ts:23-50` |
| 2 | `RuntimeEvent` / `OutputEvent`（21 种） | `runtime/events.ts:41-48` |
| 3 | `HostEvent`（12 种） | `host/events.ts:12-46` |
| 4 | `TrajectoryProjection` 私有 nodes | `ui/adapters/agent-events.ts:14-17` |

证据：
- `loop.ts:418-419` 同一时刻双发：`hooks.onTurnStart?.(turn, text)` 与 `runtimeHooks.events.emit({type:"turn_start"})`。
- `loop.ts:739-741 / 746-752`：`onToolStart/onToolDone` 与 `storeEvent("tool_started"/"tool_finished")` 双写。
- `host.ts:156-173`：把 `LoopHooks` 逐条再映射成 `HostEvent`。
- `agent-events.ts:19-30` UI 自建 `listeners + notify()`，`:94-95` 用 `nodes.find()` 回写 tool 状态，`:100` 自行 `Date.now()` 计时。

**RuntimeEvent 是超集**（turn_start / turn_end / tool_call / tool_result / output_start|update|end / agent_start|end / session_compact / model_select…），另三套都能由它派生。

方案（不新增机制，只删）：
1. 删 `LoopHooks`，Subject 只发 RuntimeEvent（含 `error`/`notice` 补进 RuntimeEvent）。
2. `HostEvent` 降为 `RuntimeEvent → HostEvent | undefined` 的纯函数投影；host 侧事件计时（`host.ts:161-169` 的 `toolStartedAt`）改由投影层持有。
3. `TrajectoryProjection` 移出 UI：要么下沉为 Core 只读投影，要么由 UI 直接消费 HostEvent 序列——不留第四份状态。

收益：删掉一整套回调契约、一层适配器、UI 一份状态副本；`Subject` 减少约 60 行双写。

## P0-2 ExtensionHost 手写 8 个专用 emit，与通用 emit 形成两条派发路径

`extensions/host.ts:179-380` 手写 `emitToolCall / emitToolResult / emitContext / emitBeforeAgentStart /
emitSessionBeforeCompact / emitBeforeProviderHeaders / emitBeforeProviderRequest / emitAfterProviderResponse`，
另有通用 `emit()`(:156) 与 `emitObserved()`(:170)；再由 `extensions/runtime-hooks.ts` 把前 8 个适配成 `RuntimeHooks`。
而 `runtime/events.ts` 里对应的 8 个事件类型**从不经通用 emit 广播**，只在专用方法里手工构造。

按结果语义其实只有三类：
- broadcast（无返回、错误隔离）→ `emit`
- short-circuit（返回 block 即停）→ `emitToolCall`、`emitSessionBeforeCompact`
- fold / chain（顺序变换、累积返回）→ 其余 5 个（四段代码结构完全相同，仅累积字段不同）

方案：收敛为 `dispatch(event, mode)` + 三个 reducer；或最少改动——抽一个 `foldHandlers()` 辅助，
让 5 个 fold 方法共用。8 个手写方法塌缩为 1 次通用派发。

## P0-3 `ai/providers.ts:600` 抹掉配置显式声明的 thinkingLevels（真实缺陷）

```ts
thinkingLevels: discovered.thinkingLevels?.filter(...)   // 展开在 {...base} 之后
```
目录项无 `thinkingLevels` 时整个表达式为 `undefined`，把 `base.thinkingLevels` 覆盖掉，
`configuredThinkingLevels`（`config.ts:40-42`）随即返回未知。与 `config.ts:33-39` 注释自述的
"不静默收窄或抹掉用户显式声明"直接矛盾。

方案：`base.thinkingLevels ?? discovered.thinkingLevels?.filter(...)`，补一条测试。

## P0-4 `runtime/guard.ts` 的 freeze/clone 与"本地扩展默认受信任"冲突

`readonlySnapshot = deepFreeze(clone(value))`（:8-10），`guardRuntimeHooks`(:17-41) 对每个 hook 输入输出都 clone，
`host.ts:162` 的 `emit` 再 `readonlySnapshot` 一次 —— 一条事件被 clone+freeze 两遍。
流式热路径上每个 `output_update` delta 都递归冻结整个对象。

同进程扩展能 `require` 任意模块，freeze 不构成真实边界，只有 O(n) 成本。
方案：受信任扩展直接传引用；仅对 fold 类 hook 的**返回值**做 copy-on-return（防扩展持有可变引用）。
真要沙箱应在进程边界做，不在事件派发里做。

## P1-1 内置能力与项目扩展**不同构**，扩展无法接管内置

- `host.ts:281-291`：builtin 先于 `load()` 激活；`renderer-registry.ts:33` 与 `broker.ts:94` 重名直接 `throw`
  → 扩展写同名命令/工具只会崩，`/model`、`/compact`、`exec_command` 事实上不可替换。
- `host.ts:317` 在 `extensionHost.dispose()` 之后直调 `killTrackedDetachedChildren()`
  （内置模块级全局 `exec-command/process.ts:28-41`）——Core 知道某个具体内置模块的内部全局。
- `cli/app.ts:282` 硬编码扩展私有工具名 `"exec_command"`。
- `builtin.ts:40-48` 注入 `subject`/`models`，而 `ExtensionAPI`（`runner.ts:16-30`）不暴露。

方案：把 `subject`/`models` 的窄面作为 `ExtensionAPI` 成员；注册重名改 last-wins（记被覆盖者）；
进程清理移入 builtin 的 teardown（teardown 机制已存在）；CLI 走 `host.commands.dispatch`。

## P1-2 UI 持有 Core 权威状态副本并自行判定业务规则

- `ui-host.ts:304-306 / :449` 构造期与 `setReasoningEffort` 中 `throw 当前 Provider 不支持思考等级`；
  `:887-888` 用 `thinkingLevels.includes()` 过滤档位 —— 模型可用性是 Provider 领域知识，不属于 UI。
- `ui-host.ts:130-139 / :143` 存 usage 三副本，`:436 / :536-544 / :971-983 / :1010-1018` 同帧多次同步。
- `tui.ts:243-245` 扫描 transcript 判定 `isInterrupted`；`:207` 三级兜底自行计时。
- `ui-host.ts:1010-1018`：`computeLayout()`（渲染路径）内改 `contextBar` 状态、`:1087` 写 `this.scrollOffset`，
  与 `:996-997` 自称的"pure"矛盾。

方案：UI 只渲染 `HostSnapshot`；`interrupted` / `elapsedMs` 由事件直接携带（HostEvent 已有 `ts`/`elapsedMs` 字段）；
`computeLayout` 保持纯函数。正面参照：`ui/adapters/jobs.ts`、`subagents.ts` 是纯转译无缓存，应作为对齐目标。

## P1-3 jobs 与 subagents 近乎平行，应合并为一套 Task 机制

`jobs/registry.ts:128,165-187,295-300,334` 与 `subagents/registry.ts:51,58-77,207-211,230` 结构同构
（id 前缀、list/get/read、owner 校验、settle/release、cancel/interrupt、snapshot、`errorMessage`），
UI 侧 `task-dashboard.ts:98-181` 与 `subagent-dashboard.ts:79-144` 逐行同构。

方案：抽 `TaskRegistry<T>`（id/buffer/waiters/owner 校验/settle/snapshot），两者只保留 producer 与语义字段。

## P1-4 投递模式规则自称唯一归属，实际有两处且语义不一致

`host.ts:231-239` 注释写"这是**投递模式规则**的唯一归属"（闲时一律 direct，忙时 direct→steer）；
但 `loop.ts:280` 也有 `options.mode ?? (this.isBusy() ? "steer" : "direct")`，
`:281` 再加 `mode === "direct" && !this.isBusy() && this.queues.size === 0`。
队列非空时两者行为不同。

方案：规则只留一处（建议留在 Subject，host 只做透传），另一处删除。

## P1-5 队列 owner→sink 路由硬编码两份

`host.ts:141` 与 `runtime-tools/index.ts:25` 各写一遍 `ownerId === "root" ? … : subagents.acceptInput(...)`。
方案：`ownerId → sink` 路由表（root 只是其中一个条目），两处共用。

## Pi 对照实证（核对 E:\Uina\ThirdParty\pi 源码后的修正）

### Pi 的真实分层

| 层 | 机制 | 位置 |
|---|---|---|
| agent 内核 | `AgentEvent`（10 种）单一事件流 | `packages/agent/src/types.ts:429-444` |
| agent 内核 | `AgentLoopConfig` 函数式拦截点（beforeToolCall / afterToolCall / transformContext / convertToLlm / prepareNextTurn / getSteeringMessages / getFollowUpMessages / shouldStopAfterTurn / getApiKey） | `packages/agent/src/types.ts:149-294` |
| coding-agent 宿主 | `AgentSessionEvent = Exclude<AgentEvent,"agent_end"> + 宿主扩展事件` | `packages/coding-agent/src/core/agent-session.ts:144-170` |
| coding-agent 宿主 | `ExtensionEvent`（30+ 种，`ExtensionAPI.on` 有 40 个类型化重载） | `packages/coding-agent/src/core/extensions/types.ts:1086-1301` |

关键实现 —— `agent-session.ts:402` 只有一个订阅点，`_handleAgentEvent`(:643-693) 对**同一次事件**顺序分发三方：

```
this.agent.subscribe(this._handleAgentEvent)   // :402
  → await this._emitExtensionEvent(event)      // :667  扩展总线
  → this._emit(...)                            // :670  UI 监听器
  → sessionManager.appendMessage(event.message)// :689  持久化
```

### 对照结论

**1. P0-1 成立，且被强化。** Pi 印证了"单一事实源 + 宿主订阅分发"：
内核只发一次，宿主 subscribe 一次，**扩展总线 / UI / 持久化三个消费者共用同一次事件**。
Uina 的 `loop.ts` 是同一时刻**双发**（`hooks.onTurnStart` + `emit turn_start`，:418-419），
且持久化另走 `appendMessage()`(:798-801) 与 `storeEvent()` 双写 —— 一次事实被写了四遍。
**值得抄的是 `_handleAgentEvent` 这个"一订阅、三分发"的形状。**

**2. 需要修正我上一轮的表述：不该删 RuntimeEvent。** Pi 保留**两层**事件
（内核 `AgentEvent` + 应用层 `ExtensionEvent`），且应用层比 Uina 的 21 种**更大**（30+ 种、40 个 `on` 重载）。
两者的差别不是种类数，是关系：**Pi 是层级复用**（`Exclude<AgentEvent,…> + 新增`），
**Uina 是并行重复**（4 套各自定义同一批 turn_start/tool_done）。
所以 P0-1 的正确表述是：删 `LoopHooks`、把 `HostEvent` 降为 `RuntimeEvent` 的投影、
把 `TrajectoryProjection` 移出 UI —— **保留并扩展 RuntimeEvent，而不是压缩它**。

**3. P0-2 成立，且被强化。** 复杂度不在事件种类数，在派发路径数：
Pi 30+ 种事件只有**一条**派发路径（handler Map + 类型化 `on` 重载）；
Uina 21 种事件却有**三条**（通用 `emit` + 8 个手写 `emitXxx` + `LoopHooks` 回调）。
Pi 的做法是"类型层面丰富，实现层面统一"。

**4. P2 的 thinking 建议被印证。** Pi 只有**一份** `thinkingLevel`
（`agent.ts:77`、`agent-harness.ts:312`），用时直接求值（`agent.ts:450`），
无 `preferred`/`current` 两份、无 clamp 同步。Uina 可只存 preferred + 用时 `clampThinkingLevel()`。

**5. Pi 无对应物，Uina 属自有设计，不能拿 Pi 背书：**
`jobs` / `subagents`（Pi 的 coding-agent 只有 `model-registry`，无后台任务注册表）、
`TrajectoryProjection`（Pi 无轨迹可视化）。这两处的判断仍只能靠架构原则本身成立。
