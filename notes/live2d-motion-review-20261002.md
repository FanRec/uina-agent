# Live2D 动作动画评审报告

- 评审对象：`.uina/worlds/live2d/`（17 个文件，5 个子模块）
- 评审日期：2026-10-02
- 方法：通读全部源码 + 脚本重算最终输出值（`notes/bin/live2d-audit.mjs`）+ 交叉核对 `notes/live2d-feedback.md` 的现场反馈
- 未做：未改任何代码，未连VTS 实测（模型文件不在本机，VTS 未运行）

## 一、结论先行

**架构分层是对的，动作语义设计有真功夫，但"可爱感"的落地被三处数值设计系统性吃掉了。**

分层结构（生理噪声 → 弹簧身体 → 动作节拍 → 语义映射）职责清晰，通道仲裁的抢占/降级/原子性语义完备，代码注释里保留了大量"为什么这样标定"的设计推理（这是本仓库的优良传统）。18 个 cue、9 款基准体态、10 种微表情的语义覆盖面在同类项目里属于扎实的一档。

但重算之后确认：**至少 4 个动作在数学上不可能达到设计意图**，其中 `pout`（傲娇撅嘴）的意图丢失率是 100%。另有 3 处属于"参数调了但效果不好"。这些问题不是实现 bug，是**标定与钳位策略的设计缺口**——注释里的标定理由（如"待机微笑是底色而非增量"）本身成立，但未考虑负方向表情与未设定项。

一个正面信号：现场反馈记录显示 18 个 cue 基本全部"能看见"，说明**接线层已经通了**（`vts-client.ts` 的同名 custom 参数创建 + 白名单过滤是有效工作）。问题出在数值层，不在管道层。

## 三、可爱感被吃掉的地方（核心问题）

### 3.1 `pout` 撅嘴意图 100% 丢失 —— 最严重

链路重算：

```
FACE 表请求        ParamMouthForm = -0.90        （撅嘴）
compose 待机底色   max(-0.90, 0.25) = +0.25      ← 被地板抬正
retargeter 极性保护 直传（sourceId==ParamMouthForm）= +0.25
最终 MouthSmile    +0.25                          ← 微笑，不是撅嘴
```

根因在 `motion-director.ts:456`：
```ts
merged[k] = clampLive2DParam(k, Math.max(merged[k] ?? 0, nVal));
```
待机微笑被设计成"下限而非增量"（注释理由本身正确——它修好了 `confident` 0.85 被顶成 1.0 的问题）。但这个 `max` **对负方向一视同仁**：`pout` 是表中唯一请求负 MouthForm 的表情，恰好被这条规则正面拦截。

同时 `playful_pout` cue（`face:"pout"`）在描述里是"傲娇嘟嘴偏头"，是全表里最"可爱"定位的动作之一，实际呈现为"微笑+偏头"。

### 3.2 `shocked` / `sleepy_yawn` 未设 MouthForm —— 惊讶时仍在微笑

同上机制的第二个受害者。这两个表情表里没有 `ParamMouthForm` 项，落到 `Math.max(0, 0.25) = 0.25`。

`surprised_gasp`（惊讶倒吸气）的实际观感是"睁大眼睛 + 嘴角上扬"，语义自相矛盾。`sleepy_yawn`（犯困）同理。

### 3.3 眼笑动态范围被噪声常驻值压到饱和

`physiological-noise.ts:170-171` 恒定输出 `ParamEyeLSmile/RSmile = 0.15`，与所有表情的 additive 叠加后：

| 表情 | 目标值 | +0.15 噪声 | 实际 | 状态 |
| --- | --- | --- | --- | --- |
| `laugh` | 1.00 | 1.15 | **1.00** | 饱和 |
| `tender_smile` | 0.95 | 1.10 | **1.00** | 饱和 |
| `smug_grin` | 0.95 | 1.10 | **1.00** | 饱和 |
| `smug` | 0.90 | 1.05 | **1.00** | 饱和 |
| `sparkle` | 0.80 | 0.95 | 0.95 | 接近上限 |
| `shy` | 0.70 | 0.85 | 0.85 | 正常 |

5 个表情里有 4 个顶到 1.0 满格。**表达力损失是结构性的**：眼笑最强与次强（`laugh` vs `tender_smile`）在模型上完全等值，视觉上无法区分。而现场反馈里那句"可爱！"正是这条线通了之后才出现的——说明这条线确实是可爱感的主要来源，那它就更不该被压平。

### 3.4 三个"害羞类"表情的眼开差异仅 +0.05~0.12

以 `relaxed` 基准眼开 0.70 为参照：

| 表情 | 眼开 | 相对待机 |
| --- | --- | --- |
| `shy` | 0.75 | **+0.05** |
| `smug` | 0.75 | **+0.05** |
| `pout` | 0.82 | **+0.12** |
| `sparkle` | 1.35 | +0.65 |

`shy` 是全表最应该"眼睛睁大一点显得无辜"的表情，实际与待机几乎无差。VTuber 的害羞感主要靠**眼开下压 + 上目线 + 眼笑**，本项目三条都有，但眼开这条被标定在噪声阈内。

## 四、看起来做了但效果不好的参数

### 4.1 `focused` 的"后仰感" —— 现场反馈已指出，根因确认

现场记录："`focused` 感觉像是头后仰"。描述是"正坐前倾仰头"。

重算融合值（`vts-retargeter.ts:99-101`，FaceAngleY = head + body×0.75，钳 ±20）：

| 体态 | headY | bodyY | FaceAngleY |
| --- | --- | --- | --- |
| `focused` | +12 | +8 | **+18.0** |
| `streamer_hype` | +10 | +12 | **+19.0** |
| `relaxed` | −10 | −6 | −14.5 |

`focused` 同时给了头抬 +12 和身后倾 +8，两者同号叠加。"前倾"应该低头，定义里 `ParamAngleY: 12.0`（正 = 抬头）与语义相反。`streamer_hype` 同病（这就是现场说"这个有 bug"、至今没定位的那款）。

注意 `relaxed` 是唯一头身反号的体态，所以它是唯一看起来对的。这也是"前倾"应该怎么写的参照。

### 4.2 头身融合对"可爱"是减分项

`vts-retargeter.ts:88-107` 把躯干角按 0.75 权重叠加进 `FaceAngle*`，理由是"VTS 原生模型普遍将 FaceAngle 作为驱动上半身与面部的统一输入"。

但代价是：**`ParamBodyAngleX/Y/Z` 同时还在被独立注入**（custom 参数，注释说"供用户在 VTS 绑定界面一一对应地接到模型参数上"）。两条路径同时生效 = 躯干运动被算两遍，且叠加量取决于用户在 VTS 里的绑定配置——**行为不可预测**。现场"shrug 肩可能没接上但他说可以的"也可能与此有关（身体通道行为与预期不符）。

这个 `0.75` 是个magic number，注释没解释为什么是 0.75 而不是 0.5 或 1.0。

### 4.3 语流律动的"有机"其实同频

注释称头躯干"有机耦合，消除固定时钟发条感"，重算周期：

| 信号 | 频率 | 周期 |
| --- | --- | --- |
| 躯干 X 主谐波 | p×3.8 | 1.65s |
| 躯干 X 副谐波 | p×1.9 | 3.31s |
| 头部 Z 语流 | p×3.8 | **1.65s** |
| 头部 Y 点头 | p×3.8 + p×7.6 | 1.65s / **0.83s** |
| 生理呼吸 | phase×1.74 | 3.61s |

头 Z 与躯干 X **完全同频同相**（都是 p×3.8）。两段注释分别说"错相"和"有机耦合"，但实际是完全同步的。头部点头的 7.6 = 3.8×2 是整数倍，每个左右摆动周期点头两次——这本身可能是有意的韵律设计，但与"有机"的描述不符。

真正打破周期性的是双谐波叠加（0.72/0.28 权重），不是头躯关系。

### 4.4 生理噪声的呼吸联动项从未被消费

`physiological-noise.ts:80` 产出 `ParamAngleY: (breath - 0.5) * 3.0`，注释说"呼吸联动胸腹与头部微仰低"。但 `compose` 里 `ParamAngleY` 走的是通用noise 叠加分支，而 `ParamBreath` 另有一条"说话时呼吸变浅"的独立链路。

呼吸与头动的耦合关系存在两套并行机制，彼此不知道对方存在。这不一定是错，但注释把它写成"联动"而实际是"独立叠加"，是文档与实现的偏差。

### 4.5 `HEAD_TABLE` 缺 roll 轴，`shake` 借用了 yaw

`shake`（摇头）映射到 `ParamAngleX` ±18。但"摇头"在中文语境是**左右摆动**（yaw 语义正确），而 `tilt_left/right` 已经是 `ParamAngleZ` ±18 的侧倾。命名上 `shake` 与 `tilt` 的区分是清楚的，但 `shake` 只有一个静态偏转值（+18），**没有"左右来回"的时间结构**——它是一次性倾倒，不是摇头。`double_nod` 同理，两个 `nod` 目标值相同（都是 −20），只是时长不同（220/380ms），实际是"低头—停顿—保持"，不是"点头两次"。

这类"名字承诺了动作、参数只给了姿态"的落差，在 18 个 cue 里至少有 `shake_head`（描述"拨浪鼓式连连摇头"）、`double_nod`（"用力连续点头两次"）两处。

### 5.2 实现偏复杂

| 项 | 问题 |
| --- | --- |
| `MotionLeaseManager` 的 6 个抢占选项 | `preemptSameReason` / `preemptSamePriority` / `allowDegrade` / `atomic` / `signal` / `priority` 六种组合。实际上调用方只用了几种固定组合：`cue` 用 degrade+preemptSamePriority，`express` 用 preemptSameReason+degrade，`pose`/`flip`/`costume` 用 atomic。选项空间远大于实际使用空间，是"为假想的并发场景预留"。可考虑收敛为 2~3 个具名策略 |
| `resolveCueToBeat` 的表达式解析 | 支持逗号/分号/和号/加号四分隔符 + `=`/`:` 双修饰符 + 冒号多段 + 键控修饰 + 数量级猜语义的历史包袱（第 434-452 行两套分支处理冒号）。这是"给LLM 用的宽容解析器"，复杂度有理由，但 `parseCueSegment` 里两处冒号处理逻辑重叠 |
| `abortableDelay` 的监听器泄漏 | `setTimeout` 回调里 `removeEventListener`，但 `abortHandler` 分支（clearTimeout）不解绑自身。功能上无害（`{ once: true }`），但不对称 |
| 通道与参数的双重门控 | `compose` 里逐处 `isChannelLocked(ch, LEVEL)` 判断散落 9 处。逻辑正确但密度高，改动时容易漏看某一路 |

### 5.3 通道划分的一个隐含代价

`PARAM_CHANNEL_MAP` 把 `ParamCheek`（脸红）划到 `eyes` 通道。这让**脸红与眼笑/眉毛/眼开抢同一个租约**：任何含脸的 cue 都会独占整个 eyes 通道，而 `shy` 同时想改脸红 + 眉毛 + 眼开 + 眼笑 4 组参数——它们不得不再细分成独立 cue，浪费了组合自由度。

设计上说得通（都在眼部），但代价是 `shy` 这个表情无法与 `sparkle` 组合（两者都要眼笑 + 眼开，会互相覆盖）。

## 六、建议的优先级

如果只做三件事：

1. **修 `pout` 的负方向丢失**（3.1）——这是唯一 100% 失效的动作，且它是"可爱"定位的核心动作。最小改法：待机微笑地板只对 `merged >= 0` 生效，负值直通。
2. **给 `shocked` / `sleepy_yawn` 显式 MouthForm**（3.2）——惊讶/哈欠必须有嘴角下沉，否则语义自相矛盾。
3. **给眼笑留出动态范围**（3.3）——把噪声常驻 0.15 降下来，或把 `laugh` 之外的表情值下调，让 5 个表情在模型上可区分。

如果做五件，追加：

4. **修 `focused` / `streamer_hype` 的头身同号**（4.1）——现场已反馈两次，是明确的语义错误。改成 `relaxed` 那种头身反号即可。
5. **删临时探针与 legacy 清理死分支**（5.1）——一次性代码已过留存期。

## 七、本报告的证据边界

- 全部数值为**脚本重算**（`notes/bin/live2d-audit.mjs`，可复跑），不是读注释推断。
- 未连VTS 实测：`ParamAngle*` / `ParamBodyAngle*` 等的**实际模型量程**未验证——报告中的"撞墙"判断基于代码里的 `clampLive2DParam`（ParamAngle ±30 / ParamBodyAngle ±15），若模型实际量程更小，撞墙会更早发生。
- `pout` / `shocked` 的结论假定 VTS 的 `MouthSmile` 输入参数确实接收负值。VTS 的 `MouthSmile` 范围未验证；若为 0~1，则撅嘴在管道层也不可行（但那属于另一个问题，且不会改变"当前意图 100% 丢失"的结论）。
- 现场反馈（`notes/live2d-feedback.md`）来自用户原话印象，非受控观察；`streamer_hype` 的"有 bug"至今无具体描述，本报告给出的同号推断与"后仰感"同源，但未经用户确认。
