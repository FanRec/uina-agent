## 使用原则与证据边界

- Core 拥有稳定事实、生命周期和最小能力接口；扩展拥有可组合的能力，UI 拥有展示、输入和焦点。按事实所有权划边界，不按文件行数、类型数量或目录方向机械拆分。
- 本地扩展默认受信任，不新增未经需求支持的权限、工具轮次或并发限制。调用者主动选择的能力集合与默认强制限制分别判断。
- 单一事实来源允许快照、事件和 UI 投影共存。修复相互矛盾的写入和推导，不要求只有一个读取通道，也不把所有状态集中到 Host。
- 模型能力与 usage 来自 Provider、可信目录或显式配置；区分未知、估算、上次请求实测和当前上下文估算。配置不能扩张已知真实能力。
- 优先修复具体失败行为。没有仓内调用者、存在常量、Pi 有某项功能，都不能单独证明应该删除或新增。
- 失败必须可见且可恢复，但恢复不意味着自动跳过坏记录、无条件继续请求或把取消请求记为完成。

证据分为三种：

| 标记 | 含义 |
| --- | --- |
| 代码复核 | 本轮审查核对了相关实现；不等于已经在真实环境复现 |
| 原审查线索 | 继承原审查的代码定位或历史探针记录；实施前需核对相关路径 |
| 待验证 | 尚无足够证据确认用户影响或修复方案 |

本轮只重构文档，没有修改实现，也没有重跑测试、真实 Provider、TTY 或故障注入。历史检查结果见文末。路径均相对仓库根目录；函数名优先于会随修改漂移的行号。

修复项按 P0 → P1 → P2 处理，同级按触发频率、影响和依赖选择，不要求先清空整个类别。P0 表示数据一致性和现有契约优先，并非声称全部缺陷已在生产复现。设计决策与待验证事项不能直接当作已批准的实现方案。

## 二、设计决策与行为验证

这些条目的缺口或实现形状可以确认，但目标行为、支持范围或方案仍需明确。结论确定后再拆最小实现项，避免批量扩建框架。

### B01 压缩后的连续性（原 M1、M2）

【代码复核 + 历史记录】默认提示词要求“不超过 200 字”，程序只判空；这是提示词约束，不是硬截断。旧摘要与新历史一起再生成。jsonl-store 追加压缩记录，原始历史仍在磁盘，因此撤回“不可逆删除历史”和“唯一永久吃掉记忆的模块”。

需要回答：哪些信息应保留在当前上下文，哪些退出后需要可检索？存档存在不等于模型能找回；换成“合并摘要”提示词也不能保证保真。

最小验证：固定少量包含偏好、关系、承诺、事实纠正、未完成事项以及必要技术细节的对话，比较当前提示词与候选方案在多次压缩后的保留、纠错、遗忘和实际使用情况，同时记录上下文规模。不得把过时事实永久保留视作成功，也不把回答自称“记得”当成证据。

根据结果再决定提示词、保留预算或历史读取接缝。摘要预算可以存在，应与真实上下文及场景匹配；不要求无限长度，不直接移植 Pi 的工程任务模板作为 Uina 的全部记忆结构。

最小试验：选当前实际使用的一条 Provider 路径，对比 SDK 候选与现实现的工具往返、usage、thinking 回放、取消和中断行为。只有迁移确实减少协议维护且保留所需行为才扩大范围；不要在 SDK 上再复制一套厂商解析与校验。

### B03 内置与项目扩展共享可用能力（原 S1、S3、S4、S5、S9、D4、D6 部分、T1 部分、T5）

【代码复核】项目 ExtensionAPI 无 Job/Subagent 入口；子代理创建没有传 runtimeHooks。runtime-tools 的 teardown 关闭共享服务，但当前 reload 只卸载项目扩展，不能据此声称 reload 已关闭内置服务。

先用一个普通项目扩展验证“启动后台任务或子代理 → 快速返回 → 接收结果 → 卸载清理”。公开现有最小服务能力，避免另造通用 service locator。共享服务关闭由其实际创建与持有者负责；扩展仍应能清理自己创建的资源，不能写成“扩展只能撤注册”。

对子代理明确 hook 的适用范围、执行身份和上下文归属：工具/Provider 规则需要一致生效时走同一接缝，不能无条件复制根代理提示词、UI 闭包或所有生命周期 hook。验收既覆盖应该传播的行为，也覆盖不应串入的上下文。

scope、include/exclude、显式 maxActivePerOwner 分别判断用途和契约，不能因仓内暂未启用就称为死代码，也不为了证明价值强行接入默认限制。快捷键在首个真实需求出现时再扩展 API。

### B04 状态观察与用户命令边界（原 F6、S8、R2、R4）

【代码复核 + 原审查线索】TUI 已用 snapshot.queue 初始化恢复队列，启动时早于订阅的 queue 事件不证明 UI 漏项。快照加事件可以共存；只有确有初始化竞争时，才修复订阅/快照衔接，不新建一套状态广播机制。

UI 皮肤设置可以注册为命令。需要修的是不可用环境的静默 no-op 或错误能力声明，而不是禁止 UI 命令。展示忙状态与 Agent 执行状态可不同，但不能用展示动画决定输入执行规则。

用户 !cmd 与模型 exec_command 可以共享进程执行、取消和输出处理，不必共享模型工具拦截语义。Pi 的 agent-session 也有独立 executeBash；是否对用户命令开放专门 hook 由实际扩展需求决定。

### B05 profile、会话身份与历史保留（原 E12、O7）

【代码复核】会话路径按 cwd，配置路径在用户目录；SessionHeader 已有 id/cwd/createdAt。没有 UI 读者不意味着会话没有身份，不能据此删历史元数据或建设多会话产品。

需要明确配置/profile 与默认会话路径是否匹配、如何显式选用已有历史。验证两个配置是否互相串历史后再安排迁移，保留原记录。691KB 单文件和 24KB 单记录本身不足以证明需要轮转或容量上限；容量策略按启动耗时、内存和长期使用证据决定。

### B06 长任务结束与记录保留（原 O3、O9、V5）

【代码复核 + 待验证】Job/Subagent 注册表持有历史记录，Job close 等待 producer 结束。记录增长的实际代价、永不结算 producer 的关闭行为尚未量测。

用可控制 producer 验证取消、失败和不结算时的可见状态与宿主退出。任务活跃资源和终态诊断分别处理；不能超时就宣称工作已取消，也不默认增加任务并发上限。确有长时增长后再选择释放、归档或显式移除，不删除仍需续接的子代理状态。
