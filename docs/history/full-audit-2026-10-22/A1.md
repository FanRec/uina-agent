### A1-01 [M] 十个 hook 注册点里 6 个生产零注册者，其中 provider 三点在每次请求仍付两次深拷贝的空转成本

- 位置: src/runtime/hooks.ts:29-39（HookName 全表）；空转成本点 src/ai/gateway.ts:192-197 + src/runtime/guard.ts:60-67；机械接线 src/extensions/host.ts:478（runShouldStop）、src/extensions/runtime-hooks.ts:18-22
- 事实: `turn.shouldStop`、`tools.beforeCall`、`tools.transformResult`、`provider.transformHeaders/Payload/observeResponse` 六个名字有完整聚合链与测试钉点，但全仓生产检索（src/extensions 内置、.uina/extensions 全部、.uina/worlds 全部、examples/）的 `onHook(` 注册者只有 4 个名字：turn.prepare（mcp、skills 示例）、turn.transformContext（voice、compaction）、turn.preflight（voice、compaction）、turn.afterEnd（compaction）。gateway 侧 `providerHooks` 恒在场（core/types.ts:228 注释自认"always present"），guard 对每次请求的 headers+payload 做 readonlySnapshot 深拷 + copyValue 再拷——零注册者时链返回原值，成本照付。
- 证据: 检索式 `onHook\("([a-z]+\.[A-Za-z]+)"` 全仓命中清单——生产侧无 shouldStop/beforeCall/transformResult/provider.* 注册（仅 tests/extensions-hooks.test.ts、tests/session-facts.test.ts 等钉点）。`turn.shouldStop`/`tools.beforeCall`/`tools.transformResult` 由 subject-runtime-plan L6 明文授权为 Interceptor 接缝（撤销对这三者的"越权"指认，保留"零注册者+成本"事实）；provider 三点在 docs/proposals 中仅 ui/context-inspector-design.md:107 顺带一句"不展示 wire 内容（传输层观测另立主题）"，无施工授权。

- 处置建议: provider 三点二选一——按 MCP/审计需求补书面授权，否则删除；shouldStop/tools 两点保留（L6 授权+Pi 对齐），但给 guard 加"链空则直通"快路径消空转。

### A1-03 [M] pipeline 两处空 catch 吞掉聚合层自身故障，失败不可见
- 类别: D（兼 G 外层冗余）
- 位置: src/tools/pipeline.ts:89-91、src/tools/pipeline.ts:141-143
- 事实: 扩展 handler 抛错已在 ExtensionHost 逐 handler catch 并经 emitError 上报（extensions/host.ts:302-304、334-336）；外层空 catch 只可能命中聚合层自身异常（guard.ts 的 readonlySnapshot/Object.freeze 对畸形入参抛出等内核 bug），命中后既不上报也不失败，静默当作"没有 hook"。
- 证据: runtimeHooks.tools.* 唯一生产来源是 guardRuntimeHooks（agent/loop.ts:185、extensions/runner.ts:364）包装的 host 链；host 链每个 handler 调用自带 try/catch+上报。故外层 catch 的触发集 = 内核 bug，恰是最不该沉默的一类。
- 移除后果: 删 catch → 内核 bug 从"静默跳链"变"回合显式失败"（符合 AGENTS.md"无效机制明确失败"）；扩展 handler 错误行为不变（内层已兜）。
- 处置建议: 保留兜底但改为经 `reportError`/error 事件上报一行，或删空 catch 让聚合故障显式失败。
- 自检: 已核 pipeline.ts:133 的 `validImages(transformed?.images)` 抛错同被 141 的 catch 吞成"改写被丢弃"——该处 hook 返回无效图片属外部（扩展）输入，失败被吞还丢 details/results 改写且无痕迹，佐证同条。

### A1-04 [M] guard.clone 的 structuredClone 失败静默降级为浅拷贝，破坏自身隔离契约
- 类别: B
- 位置: src/runtime/guard.ts:117-125（clone 的 catch 分支）
- 事实: 文件头注释声明本模块职责是"hook 实现不得持有可变引用"（guard.ts:6-7）；clone 失败时 catch 改为 `{...value}` 浅拷贝/逐元素递归，不可克隆成员（函数、类实例引用）原样穿透——隔离契约在失败路径上被自己违反，且零上报。
- 证据: 触发条件=数据含 structuredClone 不可容纳的值。内核边界上流通的全是 plain 数据（ChatMsg/RequestProjection/InjectionProvision 均为 JSON 形状；带函数的 QueuedMessage.render 在 loop 侧单独存 map，不过界：agent/loop.ts:626）。无任何已证失效路径；若真有扩展塞函数进 details，静默共享引用比明确失败更危险。
- 移除后果: 改 throw 后，携带不可克隆值的 hook 贡献当场报错并被 A1-03 建议的上报路径显示——现行为下同一场景产出跨边界可变共享。
- 处置建议: catch 改明确失败（throw 原错误），不做浅拷贝降级。
- 自检: 已核 withSignal 已把 AbortSignal 移出克隆路径（guard.ts:24-27），catch 分支不覆盖 signal 这一已知不可克隆值；已核 pipeline.ts:136-137 对 details/images 用裸 structuredClone（失败即被 A1-03 的 catch 吞），两处口径不一致本身佐证降级无契约依据。
