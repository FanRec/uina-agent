# Uina Minecraft World — Driver / 受控玩家详细设计

**状态：控制内核（资格/身体/反馈/窗口/当前事实）已实现并通过 fake bot 集成验收；尚未接真实 Mineflayer、Pathfinder/PVP 插件，未经过真实游戏验证。**

日期：2026-10-15（Asia/Shanghai），2026-10-17 修订。修订经过与理由见 [changelog](../changelog.md)，本文只写当前合同。

**设计依据：**[概要](../design.md)、[跨模块行为](../contracts.md)、[唯一公开接口](../public-api.md)及[固定源码证据](../research.md)。

本文只定义 Driver 的内部职责、操作算法、状态、第三方适配、版本兼容和验证要求。跨模块方法及数据类型以 `public-api.md` 为唯一设计来源，不在本文维护第二套公开接口。玩法算法、Callable 机制、Program 执行域和 World 历史的职责归属见[概要 §2.2](../design.md)；本文只说明与它们接触的边界，不设计其内部实现。

## 1. 设计结论

采用：

**一个私有 Mineflayer 客户端 + 一个有效身体主人 + 统一写入资格检查 + 可组合/独占两种控制方式 + 一个客户端事实出口。**

### 1.1 核心原则

1. Driver 负责 Minecraft 客户端的**连接、真实操作、控制隔离与当前事实采集**。
2. Runtime 决定身体调度和控制权归属；Driver 保证实际写入符合授权。
3. 连续控制与离散操作共享资格，但保留不同执行语义。
4. 成熟插件可以独占受控执行，也可以经适配参与组合；不强制全部转换为逐 Tick 输入。
5. 控制依赖由能力提供的当前协调者安排；Driver 检查合法来源、冲突与交接，不建立每个按键、视角、手部各自的锁和队列。
6. 新协议操作及原生插件可以局部扩展，不修改身体所有权机制。
7. Driver 提供派发事实、预测与协议观察，不越权认定高级游戏目标成功。
8. 优先复用 PrismarineJS，实现必要的真实写入隔离，不重新实现 Minecraft 客户端。

### 1.2 不变量

- 同一客户端同一时刻最多一个有效身体资格。
- 已撤销的资格永远不能恢复。
- 旧异步操作不能通过当前主人身份继续写入。
- 旧操作及其清理不能改变新主人的资源。
- 已派发的外部游戏效果不能假装被取消或回滚。
- 身体释放前，必须证明旧来源不再具有实际写入能力。
- 连接、死亡、重生、维度与活对象代次变化必须使相应旧引用失效。
- 当前事实必须区分服务端观察、本地预测、派生值和未知。
- Driver 不保存第二份游戏任务、长期地图或工程进度。

## 2. 职责与依赖

| 内容 | Driver 的责任 |
|---|---|
| Minecraft 连接 | 建立、维护、终止及重建客户端 |
| 协议环境 | 识别实际版本、游戏数据及底层操作支持情况 |
| 玩家操作 | 移动、视角、挖掘、攻击、使用、装备、窗口交互 |
| 身体资格 | 核验、撤销、交接以及操作来源隔离 |
| 原生插件 | 适配实际写入、停止、资源归属及异常 |
| 反馈控制 | 本地采样、帧顺序、有效期、输入提交与背压 |
| 当前事实 | 获取客户端实际状态、标注来源/覆盖并发布变化 |
| 操作回执 | 报告派发、低层完成范围及有关证据 |
| 底层扩展 | 提供新原生操作及受控插件适配接入方式 |

Driver 不负责 Run 调度、玩法算法、JS 执行、历史数据、资产存储或主脑认知。

上层通过 `PlayerPort / BodyOps / WindowSession` 使用受控玩家。

Runtime 是 `PlayerPort.acquire()` 的正常调用方；普通 Callable 与 Program 通过 Runtime 的 `withBody()` 取得操作代理，不直接持有原始 Bot。

Driver 与 World 之间只有事实采样、状态变化和失效通知，不形成双向业务调用。

## 3. 内部结构

```text
      能力 / Program 的控制算法（外部）
                       │
                Runtime / withBody
                       │
                       ▼
                   PlayerPort
                       │
              Body Session / Gate
                       │
          ┌────────────┴─────────────┐
          │                          │
   Continuous Control        Discrete / Stateful Operations
          │                          │
   ┌──────┴──────┐          ┌────────┴────────┐
   │             │          │                 │
Composite     Exclusive   Dig / Attack     Inventory /
Binding       Adapter     / Interact       Window
   │             │          │                 │
   └─────────────┴──────────┴─────────────────┘
                       │
                 Private Bot
                       │
          Mineflayer / PrismarineJS
                       │
                Client Facts
                 │         │
                 ▼         ▼
                World    Feedback
```

逻辑上划分五组内部职责，不强制一组对应一个类或服务。

| 内部职责 | 状态所有权 | 主要实现 |
|---|---|---|
| Client Host | Bot、连接状态、环境版本、连接与身体代次 | 客户端生命周期与健康 |
| Body Session / Write Gate | 当前资格、控制来源、撤销状态与资源归属 | 权限检查与交接 |
| Operation Adapters | 操作代次、控制状态、插件目标与临时资源 | 实际操作和停止 |
| Client Facts | 事实来源、覆盖、水位和失效范围 | 当前状态采样与通知 |
| Feedback | 反馈帧、输入有效期和控制流状态 | 高频控制及背压 |

### 3.1 私有 Bot 边界

原始 `bot` 只允许 Driver 边界内经过审查的原生适配实现持有。具体适配由组合根装配，Driver 基础部分不导入建筑、采集或战斗算法。

普通 Callable、Program、World 查询及游戏算法不能直接获取 Bot。

内部适配不是默认安全的：它仍须在全部实际业务写入点执行资格检查。

直接修改共享 Bot 状态的第三方插件必须经过源码审查和适配。

### 3.2 装配

组合根创建并连接：

- Client Host。
- 控制资格和操作适配。
- Client Facts。
- Feedback。
- Runtime 提供的控制归属及停止门。
- 由外部提供的、符合快速采样约束的传感实现。

依赖采用构造注入或明确装配，不引入供任意模块穿透的全局容器。

## 4. 连接、身份与生命周期

### 4.1 连接状态

内部连接状态：

| 状态 | 含义 |
|---|---|
| `connecting` | 建立协议连接 |
| `syncing` | 连接存在，但必要的玩家/世界状态未就绪 |
| `ready` | 客户端具备执行底层动作的条件 |
| `disconnected` | 连接已断开 |
| `faulted` | 客户端控制正确性无法保证 |

`ready` 不代表动作一定允许执行。

实际准入还需满足：

```text
Client Ready
AND 有效 Owner Attachment
AND 无停用、急停或 Owner Lost 禁止门
AND 当前宿主调用仍存活且 access=act
AND 有效 Body Permit（需要身体的操作）
AND 有效 Operation / Resource
AND 具体操作在当前环境可用
```

普通游戏聊天不需要身体资格，但必须具有合法当前 act 调用、连接与 Owner 准入，不能绕过停用和急停限制。对外只读查询不因父调用持有身体而升级。

### 4.2 身份代次

| 身份 | 创建/更新时机 | 用途 |
|---|---|---|
| Connection | 每次创建新客户端连接 | 隔离旧客户端 |
| Incarnation | 重生、跨维度、身体上下文重建 | 隔离旧身体环境 |
| Body | 每次取得新身体资格 | 隔离不同主人 |
| Operation | 每次启动新的受控操作或长期会话 | 隔离同一 Body 内的旧操作与子操作 |
| Window | 每次窗口打开 | 隔离旧窗口与槽位 |
| Entity Appearance | 实体出现及网络身份重用 | 防止指向错误实体 |

Controller 是持续控制类 Operation 的角色，复用其身份与 generation；不再维护一层总是同时变化的 Controller 代次。窗口也是有独立寿命的会话资源，其短操作可以有子 Operation。

这些身份是宿主生成的资格或只读引用。可序列化的追踪 ID 本身不授权，脚本不能拼接同名字符串取得写权。

### 4.3 身份关系

```text
Connection
  └── Incarnation
       └── Body
            ├── Operation A（持续控制角色）
            ├── Window Session Operation
            │    ├── Open 子操作
            │    ├── Click 子操作 1
            │    └── Click 子操作 2
            └── Operation C（短操作）
```

Body 可连续执行多个 Operation。

Operation A 结束后，即使 Body 仍然有效，A 的异步后续也不得继续写入。

窗口会话归打开者的仍存活调用作用域及 Body 所有，跨越 `openContainer()` 返回和多次点击；不能在打开 Promise 或某次 click 完成时退役整个窗口。调用作用域结束、Body 退出、显式关闭或服务端关闭才使会话失效。反馈流同样跨越多次 next/apply，逐帧请求结束不退役流。

连接或 Incarnation 失效会使所属活控制、窗口、反馈和实体引用失效。

历史世界坐标和实体 UUID 可以供重新定位，但不能充当活控制资格。

### 4.4 客户端重建

重建客户端必须：

1. 撤销旧连接全部业务资格。
2. 隔离旧 Bot 的异步回调、定时器、监听器和协议写入。
3. 创建新的 Connection 身份。
4. 重新建立玩家与世界状态。
5. 发布旧事实覆盖失效及新连接就绪信息。
6. 等待 Runtime 明确授予新的身体资格。

新连接不继承旧 Body、Window 或 Controller。

Driver 不自动重启旧游戏任务。

## 5. 身体资格与写入隔离

### 5.1 资格归属

Runtime 负责决定何时取得身体。

Driver 只维护当前有效 Body Permit，并核验申请是否符合外部所有权门。

**身体调度的唯一权威在 Runtime**：Runtime 决定"该谁跑、跑什么"（任务/运行队列、优先级、抢占、公平）。Driver 只强制两件事——同一时刻最多一个有效资格（资源隔离），以及按到达顺序发放唯一身体租约（互斥与交接期等待）。

Driver 不建立第二套任务队列。`acquire` 的排队只是 grant 级顺序（并发申请谁下一个取得身体），不是业务任务仲裁，不做优先级、不做抢占；Runtime 的身体调度位于 `acquire` 之上。合同项已闭合：每次身体使用只有一个在途 `acquire`，Driver 只实现互斥与交接期 FIFO（上一项 `close` 完成后才发放下一项），不对并发申请做业务裁决，也不返回“并发冲突”这种需要调用方重试的错误。

停用/拆除期必须结算排队者：连接/化身代次更替与驱动关闭都会以 `DISCONNECTED`/`INTERRUPTED` 明确拒绝整队并摘除各自的 abort 监听；结算后的 grant 还要复查连接状态，绝不把无法履行的租约发给排队者（否则会得到指向空化身的会话）。

同一调用树中的嵌套操作通过 Runtime 的作用域机制继承当前身体资格。

### 5.2 Body Session 状态

```text
acquired
   │
   ▼
 active
   │
   ├── 正常释放
   ├── stop / preempt
   ├── disconnect
   ├── incarnation change
   └── emergency
           │
           ▼
        revoking
           │
           ▼
        quiesced
           │
           ▼
         closed
```

- `active`：允许合法来源产生动作。
- `revoking`：立即拒绝旧来源的新写入并开始清理。
- `quiesced`：证明旧来源已不能影响后续主人。
- `closed`：资源与回执结算完成。

`revoking` 不可逆。

结束后再次取得身体必须创建新资格。

### 5.3 实际写入检查

每个可能产生游戏副作用的操作必须绑定其创建时身份，同时核验宿主绑定的当前调用身份与 access。实际有效权限是创建来源的授权、当前调用权限、父作用域约束和资源有效性的交集；已有 Body Permit 不是跨只读子调用的通行证。

脚本桥接和受信任原生异步后续都保留调用归属。捕获旧 act player 后从 read 子调用写入，报 READ_ONLY_VIOLATION；作用域/资格失效报 CONTROL_INVALID 或 REFERENCE_STALE。宿主管理的强制清理由窄清理句柄执行，不接受业务代码自报“维护权限”。

至少在以下位置核验：

1. 启动操作之前。
2. 异步恢复后，即将产生副作用之前。
3. 修改 Bot 控制状态、位置、速度、装备或窗口预测之前。
4. 修改插件目标和共享配置之前。
5. 向协议客户端派发业务包之前。
6. 执行可能改变共享状态的清理之前。

对于持续控制，检查位于每次有效输出的实际应用边界。

对于同步操作，检查与状态修改之间不能存在可让其他操作插入的异步等待。

对于异步操作，不能依赖进入函数时的一次检查。

Runtime 是调用身份、父约束、实际 access、存活状态和委托关系的唯一权威。组合根把其宿主内核验接缝注入 Driver；Body/Operation 只保存关联引用，不自行认定权限。正常写入按以下顺序判断：

1. 从可信执行入口取得这次真实调用，不能先把代理恢复到创建者的 act 上下文。
2. 结合代理创建来源、当前调用及祖先约束求交，再核验调用存活与 Operation/Body/资源代次。
3. 判断这次操作是当前协调者的合法子操作还是竞争来源；只在允许范围内执行同步修改。

同进程可使用 Runtime 所有的 AsyncLocalStorage/显式绑定传递当前调用，但不能使用全局“最后一次请求”。Promise 后续通常延续创建上下文；EventEmitter 监听不自动保留登记时上下文，Adapter 须在登记原生回调时捕获该 Operation 的宿主绑定，执行前重查其存活。返回给业务代码的 player 代理不能简单 bind 到创建 act，否则 read 子调用能经捕获代理恢复旧权限。

Program IPC 只接收可信桥接入口附带的执行域/调用帧关联。Runtime 根据宿主登记的来源解析当前调用，并与句柄创建者及父约束求交；请求体中的 callId/access/owner 均不授予权限。旧消息、别的执行域借用句柄、伪造 parent 或只读帧携带旧 act 句柄，在进入 Adapter 前拒绝。具体执行域实现归 Program，但这些失败场景是接缝的硬要求。

### 5.4 操作资源

每个 Operation 内部只需保存：父操作/所属调用、绑定的 Body 与连接代次、active/revoking/closed 状态、已派发效果引用。长期控制复用这个记录；窗口、反馈增加其确有的协议状态。它不是另一份 Run/Callable 状态机。

**Operation 拥有资源的生命周期归属，不等于保存一份通用资源集合**（`Operation.resources` 已删除，不得重建）：具体资源由实际执行器或会话保存——按键归 KeyHold、原生使用状态归 Body 使用会话、窗口归 WindowSession——退役时通过确定的所有权关系与该机制的清理入口处理。某个资源缺少可信退役路径时，补那个具体资源的清理，而不是恢复一套通用资源列表。

一个 Operation 拥有自己创建或取得的资源：

- 定时器。
- 事件订阅。
- 插件目标。
- 挖掘与物品使用状态。
- 持续控制输出。
- 窗口。
- 反馈流。
- 异步子操作。

清理只能处理仍属于该 Operation 的资源。具体承载（当前实现）：按键持有 = KeyHold（每连续根一份，撤销只清本根按键）；原生使用状态归属 = Body 会话唯一权威（requireAvailable/claim/release，drive/useItem/feedback 同一路径）；窗口状态 = WindowSession；事件订阅/定时器 = 各自组件的 disposer 表。没有第二份隐形记账。

旧操作不能执行没有资源身份约束的全局清理。

原生插件如必须调用全局方法，应证明此时不存在新主人，并在交接屏障内同步完成必要处理。

### 5.5 宿主维护操作

协议确认、必要客户端物理模拟、连接维护不属于普通业务动作。

这些操作可以在没有 Body Permit 时继续，但必须有明确、受控的内部入口。

不能借维护权限发起采集、移动、攻击等业务行为。

## 6. 控制操作模型

### 6.1 两类执行语义

**连续控制：**

- 移动方向与按键。
- 视角控制。
- 持续使用物品。
- 长期路线跟随。
- 反馈式跑酷或走位。

**离散或有状态操作：**

- 攻击一次。
- 挖掘指定方块。
- 装备物品。
- 与方块/实体交互。
- 点击窗口。
- 进入、保持、结束某种物品使用状态。

两者使用同一写入资格和资源归属，但不强制走同一个 Tick 输入接口。

有状态操作可以持续多个物理步，其内部由明确的操作状态机执行，不等于反复发送相同的一次性命令。

### 6.2 两种原生复用模式

这是适配行为的两种约定，不是插件分类注册系统，也不强制共享控制算法基类。控制算法与复合决策属于提供它的能力；Driver 只装配其受控写入口和资源寿命。

#### A. 组合控制器

用于需要协同多种控制算法的情况。

例如：

```text
Composite Controller
   ├── 路线跟随 → 移动建议
   ├── 目标瞄准 → 视角建议
   ├── 攻击逻辑 → 攻击时机
   └── 交互逻辑 → 临时交互请求
                ↓
          最终受控操作
```

子算法不分别取得身体，不直接写共享 Bot。

由能力模块提供的复合控制器负责：

- 选择实际移动和视角输入。
- 识别控制冲突。
- 处理临时独占要求。
- 安排必要的操作顺序。
- 输出合法的操作请求。

#### B. 受控独占控制器

用于适合整体运行的成熟插件，例如某些 Pathfinder 路径执行流程。

独占控制器可以保留其内部算法和状态机，但必须满足：

- 绑定当前 Body / Operation。
- 写入由适配边界核验。
- 无法与不兼容控制器并行写入。
- 停止与资源清理可被验证。
- 结束后不留下有写入能力的旧回调。

独占不等于拥有整个 Runtime。默认在自己的 Operation 寿命内独占该身体的业务写入口；只读采样与必要客户端维护仍可进行。不为了容纳少数插件再引入每通道资源锁。

### 6.3 控制冲突

默认规则：

- 只读操作可并行。
- 顺序身体操作可共享一个 Body。
- 同一协调作用域内已声明兼容的操作可以重叠执行，不因都接触身体而全局串行。
- 两个无协调关系的持续控制器不能并行。
- 嵌套操作只有经当前协调者明确委托、且符合该适配声明的组合条件才可写入；仅共享 Body 或同一调用树不证明可并行。
- 互相冲突的操作必须确定性拒绝或由协调者安排顺序。

不能让不同控制器通过最后写入者获胜的方式互相覆盖 Bot 状态。

协调者使用 `withBody` 给出的同一 scope/player，及通过该 scope.call 进入的受许可子调用，构成可核查的委托来源；不是看到同一个 Body ID 就放行。连续操作接收这些来源经现有 BodyOps 发出的兼容短操作或状态机子操作，子操作保留自己的身份与资源。这个关系由 Runtime 绑定、Driver 检查，不增加公开 delegate token 或控制器注册系统。

Adapter 用局部代码检查实际写入与已有活动 Operation 的兼容性，不按一组资源名字自动生成锁或调度器。这是本地控制组合的准入判断，不等于服务器一定同时接受所有游戏效果。接口最低应能表达以下关系，实际成功条件仍须按版本、物品和动作状态验证：

| 可表达的组合（尚待游戏验证） | 执行关系 |
| --- | --- |
| 移动 + 视角 + 单次 attack | 连续移动/视角继续；attack 不暗中瞄准或清键，作为同一协调者的子操作派发 |
| 移动 + 已有视角控制 + dig(preserve) | 挖掘只维护自己的目标/计时/协议，保留视角；目标超出可达或命中条件则报告事实，由协调者调整，不强停整个移动流 |
| 移动/视角 + 持续使用 | 可在同一连续输入中表达；独立 useItem 留下的使用资源也不能被另一个操作的省略 use 顺手释放 |
| 自动瞄准 dig + 另一个视角控制，或换装备 + 依赖旧手持物的挖掘 | 真实冲突；协调者暂停有关输出或先结束旧子操作，再执行交互，不自动关闭全部兼容输入 |
| 原生插件的完整独占执行 + 无委托的另一个控制器 | 拒绝重叠；需要组合时选择该插件适合复用的算法和受控执行路径 |

这不是宣称原版允许任意主手挖掘、攻击、蓄力同时成立。受物品、协议和动作状态约束的组合仍须真实验证；支持条件不足时说明具体冲突，不用“一个输出者”取消全部并行能力。

### 6.4 临时独占与依赖

复合控制并非简单合并按键字段。适配应说明操作是否会调整视角、改变装备、占用使用状态或窗口，以及何时结束这些修改。协调者据此先撤销不兼容持续输出，等待该输出的撤销边界，执行受控子操作，再基于新事实恢复仍有效的控制意图。

兼容子操作直接在连续流存活期间执行，不能默认采用“关流 → 离散操作 → 重建流”。确有冲突时，协调者只停止冲突输出并等待其撤销边界，保留无冲突的移动/使用等意图；原生复合操作可在自己的 Operation 内委托子操作。若所选完整插件只能独占，关闭旧流再执行它是明确的能力选择，不是 Driver 对所有组合的统一限制。

Driver 不根据一组资源名字自动推断这些前置条件，更不决定先放置、射击还是绕行。依赖和顺序属于算法所有者的普通代码；本节只规定准入与交接。没有明确组合合同的重叠写入报 CONTROL_CONFLICT。

### 6.5 独占插件与复合操作的切换

切换必须先退役旧 Controller/Operation，并满足控制隔离要求。

新控制器不能在旧插件仍可写入共享状态时启动。

如果成熟插件无法安全停止，则不能通过简单改写 owner 字段实现切换。

## 7. 底层操作语义

### 7.1 输入分类

执行语义需区分，公开方法/参数仍只定义在 [public-api §4](../public-api.md)：

| 类型 | 示例 | 规则 |
|---|---|---|
| 持续状态 | 前进、潜行、保持使用 | 每次提交替换所属连续状态；省略项按公开合同释放，到期/失效也撤销 |
| 一次性动作 | 攻击一次、使用一次 | 同一次有效提交最多执行一次 |
| 状态机动作 | 挖掘、蓄力、特殊交互 | 明确开始、保持、结束和异常清理 |

持续状态重复提交不应重新启动同一个原生动作。

同一手的 held-use 只在未使用→使用时启动；持续提交同一状态不逐 Tick 再发 use。使用→释放可能触发游戏效果。单次使用经独立操作调用，不以“保持一帧再释放”代替；与持续使用冲突时先拒绝或由协调者显式结束旧使用。

一次性动作不得因 Tick 推进、重复帧或通信重试而重放。

已派发但结果未知的离散操作，不自动再次派发。

### 7.2 `drive`

`drive(input, ticks)` 的 Tick 解释为实际执行的客户端物理模拟步。

要求：

- 开始输入的物理步有明确边界。
- 返回实际应用步数及结束观察；失败时按公开错误合同保留已有步数和效果引用。
- 取消可以提前结束。
- 物理循环暂停不能导致无限等待。
- 离散动作不会在每个 Tick 重复执行。
- 持续控制与其长期 Operation 身份绑定。

墙钟超时用于检测停滞，不能代替物理步数。

在首个实际消费该输入的模拟步开始计数；第 ticks 个消费步结束后、下一次模拟之前撤销本次 drive 的持续键/use，视角不回滚。正常返回必须达到请求步数；取消、停滞或连接失效以对应错误结束，不能把较少步数当完整成功。attack 只在本次输入安装时派发一次，不随 ticks 重复。既定的本地 drive 不需要脚本逐 Tick 续命。

### 7.3 `dig`

`dig` 是独立的有状态操作。

其适配至少包含：

1. 目标有效性与版本支持检查。
2. 身体及操作资格检查。
3. 受控瞄准或必要视角调整。
4. 实际挖掘开始派发。
5. 挖掘过程监视。
6. 完成、取消或异常结算。
7. 本地预测与服务端事实分别记录。

Mineflayer 的挖掘流程存在异步 `lookAt()` 和本地完成预测。恢复后必须重新核验资格。

不能把本地目标块变成空气当作服务端确认。

默认 dig 可瞄准目标；与现有视角协同的 dig 使用公开合同的 preserve 选项，复用上游 ignore-look 路径且不得暗中覆盖视角。进入和恢复时检查有关目标、手持前置条件与当前观测；不能把“不自动瞄准”解释为保证持续可挖。是否移动、维持瞄准或换目标由协调者决定，Driver 不增加挖掘路线策略。

原始 `dig` 不承诺掉落已进入背包。

### 7.4 攻击与交互

`attack` 的基础完成范围是一次攻击尝试被有效派发。

不自动承诺命中、伤害或击杀。

`interact` 的基础完成范围是指定交互被派发；放置成功、容器打开、交易完成等由相应观察或领域能力核验。

lookAt/ControlInput.lookAt 接受连续 PointTarget 或 EntityRef，由 Driver 换算角度，与 look 互斥；仍核验真实 Call/Body 来源。

如某低层操作承诺更强效果，必须有明确完成条件及证据来源。

### 7.5 装备与使用

区分：

- 快捷栏切换。
- 背包槽位搬移。
- 主手/副手装备。
- 持续使用物品。
- 一次性使用。
- 使用状态正常结束与异常取消。

装备操作如果涉及窗口和槽位修改，使用同一受控库存路径。equip/endUse/lookAt 均返回 EffectReceipt，不吞掉清理或释放蓄力的后果。

结束物品使用可能产生真实效果，例如释放已蓄力的弓。

不能统一把释放解释为无副作用清理。

一次 useItem/once 是一次协议激活；若留下原生使用状态，资源归仍存活调用作用域与 Body 下的使用会话，不能在激活短操作返回时擅自 release。endUse 提供独立离散结束入口，无需为释放物品强行凑一个 drive Tick；无 use 输入只结束本次流拥有或明确接管的使用资源，不能破坏兼容子操作的独立使用。调用/Body 退役时强制清理并保存后果。具体签名只见 public-api。

### 7.6 扩展操作

新原版或模组操作可以增加受控原生适配，但必须复用：

- Body / Operation 身份。
- 实际写入检查。
- 资源归属。
- 停止机制。
- 派发与证据记录。

不要求所有新操作都塞进现有 `ControlInput`。

Driver 不因新增某类玩法而增加专门的业务调度器。

## 8. 高频反馈

### 8.1 执行位置

客户端物理、写入核验和必要停止处理留在 Driver 的关键执行路径。

生成程序和复杂控制计算在独立、可终止的执行域。

脚本函数、闭包和普通 JS 局部状态留在脚本执行域。

Driver 对执行域只要求数据桥接和可撤销的宿主请求；具体 JS 引擎、闭包执行和宿主调用实现归 Program 设计。跨边界只传：

- 采样参数。
- 反馈数据。
- 仅用于路由、由宿主核验归属的操作句柄标识；不跨进程传活对象或凭 ID 自授资格。
- 输入结果与回执。

不传原始 Bot，也不把函数序列化进 IPC。

### 8.2 反馈帧

反馈必须绑定：

- Connection。
- Incarnation。
- Body。
- 所属流与 Operation（持续控制角色共用该代次）。
- 帧序号。
- 单调采样时间。
- 输入有效期。
- 事实来源与覆盖信息。

反馈序号只在所属控制流及其代次内具有比较意义。

不能与 World 查询游标或 Run revision 混用。

### 8.3 反馈循环

```text
Driver 采样
   ↓
生成反馈帧 N
   ↓
控制算法计算
   ↓
提交 N 对应输入
   ↓
Driver 核验资格/序号/有效期
   ↓
应用到后续合法控制边界
   ↓
Driver 再次采样
```

规则：

1. 每个流只有一个顺序的在算帧，另有一个 latest-only 待交付槽；新采样只替换待交付槽，不立即废掉仍在有效期的在算帧。
2. next 交付新帧后，前一帧不再可提交；同一帧最多消费一次，重复/乱序提交在任何副作用前失败。
3. apply 在准入时和实际安装输入的物理边界都校验资格、已交付 sequence 和 validUntil；不能用入队时间掩盖排队后过期。
4. 正常 resolve 表示输入已安装到实际后续物理步，并返回该应用步的回执；仅桥接接收不算应用。拒绝、取消或未应用的超时不补播。
5. 控制流退出时撤销其持续输入。
6. 超过有效期未产生更新时撤销持续输入，并记录故障。withBody 中等待不延长本流有效期；资格仍存活不代表输入仍有效。
7. 终止脚本前先撤销资格；不依赖脚本 `finally` 清理真实 Bot。

### 8.4 物理时序

固定 Mineflayer 实现中：

```text
simulatePlayer
   ↓
physicsTick
   ↓
updatePosition / movement packet
```

`physicsTick` 是本次物理模拟后的事件。

在该事件中提交的新控制通常作用于后续物理模拟，而不是已经完成的模拟。

采用确定语义：第 N 步模拟完成 → 采样 N 的结果 → 执行域计算 → 输出进入待应用槽 → 在仍有效的第 M 步模拟前安装，其中 M>N。异步延迟可能使 M>N+1；不能许诺每帧一定赶上下一步，也不把输出补记到 N。

**窄接缝是条件条款（2026-10-17 依据 research.md#driver-audit 降级）。** 上游并未提供任何接缝；同进程部署中，在两次模拟之间同步安装输入并监听 `physicsTick` 计数，与下述"模拟前安装、模拟后计数"语义精确等价（`physicsTick` 仅在真实模拟分支发出，已按固定源码核实），Driver 当前实现即采用该路径，不需要为 drive/feedback 补丁物理循环。以下窄接缝仅在两个场景出现时才以最小补丁实现（优先 wrap `physics.simulatePlayer` 单点，不 fork 循环）：(a) 输入安装异步化（M5 执行域桥接，apply 到达时需在模拟前核验来源与有效期）；(b) 需要归属插件模拟后修改或取证 wire 值。接入时顺序固定：

```text
原有 play/实体/区块等模拟条件检查
  → 模拟前：核验来源与有效期，安装将由 M 步消费的输入
  → simulatePlayer(...).apply(bot)：唯一一次实际物理模拟
  → 模拟后窄接缝：计数 M，采样本次模拟结果
  → 原有 physicsTick/physicTick 监听：原生插件可能产生额外本地修改
  → 发包前：记录这些修改的 Operation/来源，采样本地候选状态
  → 原有 updatePosition / movement packet，及该版本的 tick_end
```

每个实际消费步只计一次。play 外、实体未就绪、区块不可模拟、physicsEnabled/shouldUsePhysics 阻止模拟、补偿上限丢弃的时间片均不计数；定时器回调次数、movement/tick_end 包数也不计数。最后一个消费步结束后在下次模拟前撤销本次 drive 的持续输入；短操作的独立派发不增加物理步数。模拟前步骤抛错或只入队没有模拟，也不能返回已应用步。

必要的一次性输入可在提交边界派发，但其回执仍区分派发与随后真实消费步。完整原生插件在 physicsTick 写的按键通常供未来步消费；若其在此时改位置、速度或视角，则另列为模拟后修改，可能进入本次移动包。发包前快照仅是本地候选状态；updatePosition 仍会限速、转换/舍入视角等，实际字段须在原 sendPacket/协议派发入口取证，不能用 bot.entity 快照冒充 wire 值。采样不得把监听顺序碰巧取得的混合状态冒充纯 M 步结果；事实入口可发布这些额外变化，但保留不同来源/本地水位。沿用原有物理循环、追赶与发包规则，不另起模拟器或第二个定时器。

`physicsTick` 本身仍是模拟后事件，不将监听器排序当模拟前接缝。若插件在模拟后、移动包前改变位置或视角，该变化另外归属于该 Operation，并标本地修改，不能算作已经被第 N 步物理消费的输入。相关源码与验证边界见[研究复核](../research.md)。

### 8.5 背压与健康

- 高频反馈使用有界缓冲。
- 旧帧优先丢弃或合并，不补播过期动作。
- 额外传感必须能在当前采样预算内完成。
- 大范围寻路和重计算切片或移出关键执行路径。
- 用单调时钟判断输入有效期。
- 物理步停滞由独立的墙钟健康检查发现。
- Driver 关键线程整体阻塞时，必须依靠其执行域外的监督方检测；本线程定时器不构成可靠急停证明。

监督方的具体归属和终止确认见 §10.7，不以驱动自报 heartbeat 或独立线程替堵塞线程续心跳来制造健康。

具体控制频率、预算和超时由实测决定。

## 9. 第三方插件适配

### 9.1 基本策略

每个实际采用的实现通过独立 Adapter 接入，例如 PathfinderAdapter、PvpAdapter、InventoryAdapter；它们是普通模块/函数，不要求共同基类。上层只能使用受控 Player/窗口/事实合同，不能 import 插件类、调用 bot.pathfinder/bot.pvp、持有其 Movements/目标/锁/原生窗口对象，或根据内部事件安排交接。

按以下顺序选择，保留实际游戏效果作为判断依据：

1. 优先组合公开 API；能证明异步写源与停止封闭就不改上游。
2. 公开 API 不足时评估复用搜索、数据或其他成熟算法，并自实现受控执行。算法入口也要核查共享状态，不能只因名为 getPath 就当纯函数。
3. 完整成熟执行的效果值得保留、且局部控制补丁比替换执行更可靠时，才对固定版本作集中补丁。不得把修改导航/战斗算法夹带成“控制修复”。

PVP 内部依赖 Pathfinder 的事实不必为了形式解耦而重写。由两个 Adapter 在边界内部显式装配为同一受控操作及其子操作，固定兼容的依赖组合；不向 Combat/Navigation 暴露这种插件内部耦合。独立导航不得同时占用该 PVP 正在使用的 Pathfinder 实例。

不得认为以下措施单独足够：

- 在顶层方法增加 AbortSignal。
- 等待插件 `stop()` 返回。
- 只拦截网络发包。
- 只在执行开始时检查 Body Permit。

因为插件可能在异步恢复后修改：

- Bot 控制状态。
- 位置与速度。
- 本地库存预测。
- 共享路径目标。
- 监听器与定时器。
- 原生物品使用状态。

### 9.2 适配基本要求

每个原生适配应明确：

| 项目 | 说明 |
|---|---|
| 支持条件 | 依赖、协议功能与客户端状态 |
| 操作身份 | Body / Operation 绑定；Controller 为长期操作角色 |
| 实际写入范围 | Bot、插件、窗口、协议与本地预测 |
| 异步来源 | Promise、计时器、监听器、Tick 回调 |
| 停止方法 | 如何撤销新写入和停止持续输入 |
| 清理范围 | 哪些资源可安全清理 |

### 9.3 Pathfinder

允许两种复用方式：

**完整受控独占：**保留路径规划、移动、挖放和已有站位处理，对所有实际写入与异步来源进行适配。

**算法复用：**复用路径搜索、路径节点及相关计算，由自定义复合控制器实施实际移动。

不得假设完整 Pathfinder 天然可以输出纯移动建议。

也不得在未经测试的情况下删除其位置/速度修正。

这些修正可能参与边缘站位、惯性和挖放转换；必须分别评估效果和控制隔离。

其 `stop()` 或 `setGoal(null)` 不能直接成为停止屏障的唯一证据。

固定源码的公开 `stop()` 只设置标志，内部停止路径先发 `path_stop`，再执行 `fullStop`；后者清控制状态并修改本地速度/位置。正常导航的这些修正保留明确 Operation 归属，不能标成服务端纠偏；取消适配先退役写源与持续输入，不通过旧 fullStop 的无条件修正证明“角色已静止”。是否改变导航站位算法归 Navigation，须与原插件对照验证。

## 10. 停止与控制交接

### 10.1 停止分成两件事

**立即撤销资格：**阻止旧来源继续产生有效写入。

**完成交接屏障：**证明旧来源和清理行为不会影响下一主人。

两者不能混为一个简单的 `stop()` Promise。

### 10.2 停止流程

```text
Stop Requested
      │
      ▼
立即拒绝旧来源写入
      │
      ▼
撤销 Body / Operation 资格
      │
      ▼
退役控制器与所属异步来源
      │
      ▼
撤销持续输入，停止所属操作
      │
      ▼
处理窗口、插件与临时资源
      │
      ▼
记录已派发或未知效果
      │
      ▼
证明旧来源不能影响新主人
      │
      ▼
Quiesced / Release
```

实际撤销不能等待持久化完成后才发生。

持久停止意图及 Run 结算由 Runtime/Executor 负责；Driver 返回控制实际状态与失败信息。

### 10.3 屏障成立条件

必须证明：

- 旧资格永久失效。
- 旧异步后续无法产生有效业务写入。
- 旧待派发本地命令已处理或被拒绝。
- 所属持续输入已撤销。
- 插件目标、窗口和反馈流已停止或失效。
- 旧清理不会触碰新主人的资源。
- 已派发的外部效果已经确认或登记 unknown。

无需等待已经失去全部写入能力的 Promise 自然结束。

反之，Promise 已结束也不等于屏障成立。

### 10.4 清理副作用

清理操作本身可能产生游戏后果。

例如：

- 释放已蓄力的弓。
- 结束持续使用。
- 关闭携带光标物品的窗口。
- 执行特定插件的停止修正。

清理必须使用受控的内部资源句柄，并记录相关派发及未知结果。

不能为了“恢复干净状态”主动发起额外的丢弃/搬槽。清理必需的 release/close 可能有协议固有后果，须保存派发与未知结果；无法安全完成则报告具体故障，不声称零效果或永久占着身体等待“无副作用关闭”。

### 10.5 交接失败

无法证明旧插件写入已失效时，不允许新主人取得同一个客户端实例的控制资格。

必要时：

- 隔离旧控制来源。
- 终止当前客户端。
- 重建连接。
- 重新发布连接状态。
- 报告未知效果。

重新连接是故障隔离手段，不是正常每次释放身体的流程。

### 10.6 自保控制

Driver 支持 `run` 与 `safety` 两类控制来源，但不自行决定何时需要介入。

独立安全控制必须经过与普通控制相同的资格和停止边界。

已有有效复合控制器内部的短时自保动作，可由该控制器协调执行。

急停、Owner Lost、World 停用门禁止产生新的自保业务动作。

共享 worker 故障先由 Program/Runtime 封闭全部受影响调用并撤销控制，再终止并确认退出。Driver 不因替代 worker 启动而复活旧来源，交接仍以本节屏障为准。

### 10.7 整体阻塞的域外监督

整个游戏主线程失响应时，Driver 自己的 timer/stop/finally 无法建立退役。Uina 侧 Executor 唯一监管伴生进程树；Windows 命名 Job、精确实例、启动准入、父崩溃、独占和退出确认由 [Executor §3–§5、§7](executor.md) 定义，Driver 不再维护一套监督者。

Driver 只消费必要保证：旧本地写源已隔离才允许新客户端/资格；kill 返回、IPC 断线或超时不是退出证明；证明不了保持 faulted/control unknown。进程退役不撤销已派发的服务端效果，Runtime 继续保留 unknown 和缺失尾部。单个 guest/共享 worker 的退役仍由 Program 与 Runtime 在本进程处理，不能每次停止都重启整个客户端。

## 11. 当前客户端事实

Runtime 集成须注入真实 HostCallVerifier 和非阻塞 DriverExecutionSink，唯一形状见 [public-api §7.1](../public-api.md#71-可信组合根注入)。默认宽松 verifier 不得用于完整写集成。Operation 创建时绑定 Call 来源，实际派发/回执/清理入 Runtime 队列；对应 close 完成前，已产生清理事实先入队。Driver 不等数据库、不成为第二份 Effect 权威，Runtime 终结另等记录 H 屏障；未来服务端证据仍可晚到。


### 11.1 唯一客户端事实基础

当前协议视图优先复用 Mineflayer/Prismarine 的状态。

Driver 额外维护必要的：

- 来源。
- 时间。
- 连接及资源代次。
- 已知覆盖范围。
- 本地预测关联。
- 事实水位及失效信息。

不再复制完整世界模型。

### 11.2 Client Facts 输出

提供当前读取、变化提示与选定证据捕获：

**读取当前事实：**从当前客户端状态取得一致的只读采样，附上来源、覆盖和水位。

**发布变化：**在有关事实状态更新后发布变化或失效范围。

**捕获选定证据：**在窗口/实体/区块等原始事实被覆盖或移除前取得不可变载荷与稳定源身份；变化提示可合并，选定证据不可被静默合并掉。

它们是 Driver 与 World 的内部接缝，不承担 World 的历史查询、空间搜索或领域记录写入。

读取不隐式移动、打开窗口、主动发起同步或执行其他游戏动作。

### 11.3 事实来源

至少区分：

| 来源 | 含义 |
|---|---|
| Server observed | 收到有关协议事实 |
| Predicted | 客户端预测或本地物理模拟 |
| Derived | 基于现有事实计算所得 |

混合结果不能使用一个来源标记覆盖全部字段。

Unknown 是覆盖/知识缺口，通过 unknown 与可空领域值表达，不是另一个协议事实来源枚举。公开混合观察采用 public-api 的分组来源；采样时间与各组真正收到/形成事实的时间分别保留。

例如 SelfState 中：

- 位置/速度可能来自本地物理模拟。
- 生命和饥饿状态来自协议更新。
- 地面接触状态可能来自本地计算。

对混合结果按必要字段组携带来源与更新时间，不对每个标量强制单独建模。

### 11.4 一致性

一次采样应在同一个本地状态观察边界读取所需字段。

这保证本地视图一致，不意味着这些字段在服务器上曾经同一时刻原子更新。

不同来源的时间和证据必须保留。

### 11.5 方块覆盖

必须区分：

1. Chunk 对象存在。
2. 有关方块数据实际加载。
3. 目标格具有可信当前值。
4. 目标格仅有本地预测。
5. 目标格当前未知或已卸载。

不能只凭 `blockAt() != null` 或 `chunkColumnLoad` 推断所有方块已知。

覆盖应根据固定协议版本实际收到的数据建立。

卸载导致当前覆盖失效，但不要求删除 World 已保存的历史。

### 11.6 事实变化

在协议入包和本地预测的实际修改入口标注来源，不能只监听共用的 blockUpdate/updateSlot 事件反推。当前格/槽位沿用上游视图；对存在预测的部分保存稀疏关联及最后服务端观察，不全量复制世界。服务端同值更新也重新登记来源；区块卸载或连接重建使相应当前覆盖失效，旧观察只能由 World 作为历史使用。

在更新事实来源、覆盖或当前值之后发布变化提示。

数值没有改变，但证据性质发生变化时，也应更新相关事实版本。

例如本地预测目标方块为空，随后协议确认该位置为空。

Driver 不把这种升级吞掉。

### 11.7 与 World 和 Feedback 协作

World 将客户端事实投影为统一查询/订阅接口，并负责历史持久化。

事实接缝唯一类型见 [ClientFactsPort](../public-api.md)。同步 sample 固定纯值、scope、Driver 水位及 evidenceThrough，不允许活读 view 跨 await。World 先订阅后采样；状态提交后排变化提示，合并提示不是逐事件日志。选定证据在提交边界捕获，同域轻量移交入队，跨域明确区分 captured/sent/received/durable。源证据序号独立于事实 stamp；按原 ref/序号重传，默认保留唯一材料至 durable ACK；当前同域合同没有 received ACK。不可恢复缺口显式交付，reset 不删除旧证据，未封口源不宣称历史完整。

默认 World 轻量接收与 Driver 同域，共用一份不可变捕获/待落盘材料，按持久提交回收，不额外复制 outbox 或模拟跨域 ACK/重发。SQLite/重计算在线程外。拆域不传 sample 回调；纯当前 capture 用轻量有序当前状态检查点，不等 evidenceThrough 载荷或数据库。纯历史不请求 Driver；联合查询只有承诺截至样本的历史前缀才采用证据 fence，并由 World 核验实际依赖。协议需求见 [World §6](world.md)，不增加普通/严格模式。前缀等待/大载荷不得占住日常当前读，RPC 返回不自证原子。Driver 不拥有 World 水位。

大范围当前地形按需通过 sections 固定请求范围的不可变基底/必要补丁与覆盖，复用选定地形历史材料。小范围 block/self/inventory 不先创建 Section 版本；没有活动区域切面/历史核验需要时，不将每次预测变成长期版本链。Driver 保证读材料真实不可变，工作线程展开搜索；不扫描复制全加载区，不 transfer 仍使用的 buffer，不让 Driver/World 各建全量缓存。不能低成本固定某区域时明确该查询可用性，不影响其他当前读。见 [World §7](world.md)，实际内存/延迟仍须测量。

Feedback 使用相同的底层纯采样实现，但不每 Tick 调用 World 的异步业务查询或数据库。

Driver 即时返回的是 Fact；World 查询才为事实加上同点查询游标形成 Observation。反馈流、drive 终点和窗口 snapshot 不生成伪 World 游标。

组合根注入实际需要的快速传感采样函数。

新增传感不要求建立第二套能力目录。

Driver 事实水位、World 查询游标和反馈帧序号属于不同作用域，不得直接互换。

stamp 只能证明源已前进，不证明 World 已收到对应空间范围。World 按 [World §9](world.md) 在范围未知时保守覆盖当前源；Driver 不为此等历史载荷或数据库，也不要求新增 notice 区间日志。SQLite 打开失败不阻止已有 Driver 的当前 sample；scope 只用可信运行期绑定，否则是显式 unbound，不能从连接地址推断存档身份。样本已有的 evidenceThrough 可供联合结果填写 history 进度，它不是持久 ACK；纯当前不计算历史进度。

## 12. Window Session

### 12.1 窗口身份

Window Session 绑定：

- Connection。
- Incarnation。
- Body 与窗口会话 Operation；每次修改另绑定当前调用和短子操作。
- Window generation。
- 原生协议窗口 ID。
- 类型、布局及属性。

同一协议 ID 被复用，也不能使旧窗口重新有效。

### 12.2 当前快照

窗口快照应包含：

- 窗口身份与版本。
- 窗口类型。
- 槽位布局。
- 当前槽位物品及数量。
- 当前光标物品。
- 必要的工作站属性。

版本属于 Driver 的本地窗口观察版本，不直接等同服务端协议 `stateId`。

对于会原地修改的 Prismarine Item，需要比较或保存不可变快照，不能只比较旧对象引用。

有些堆叠数量及光标修改不经过 updateSlot，故每个受控预测步骤和协议更新步骤提交时比较完整窗口快照；值或来源/属性改变推进本地 revision。快照的公开字段仅在 public-api 维护。

打开窗口前登记监听与本次打开意图；同一客户端只允许一个在途打开。open_window 没有目标坐标回指，需核对预期目标上下文、窗口类型与代次，不能把任意 windowOpen 归因给本次目标。意外窗口或归因不足返回明确失败/未知，不偷偷绑定。

### 12.3 修改操作

同一窗口的实际修改操作串行执行。

点击流程：

1. 校验 Window / Body / Operation。
2. 读取当前不可变快照。
3. 校验预期 revision。
4. 校验预期槽位、物品、数量与光标。
5. 校验当前协议对操作方式的支持。
6. 在本地预测修改之前再次核验资格。
7. 执行受控原生操作并派发。
8. 接收可用协议事实或显式执行必要重同步。
9. 返回完成范围和证据。

窗口读取不得隐式触发主动协议操作。

需要重同步时，以受控操作执行。

固定版本的 `_syncWindow` 是主动点击请求全量槽位，并非被动 read；它本身没有完整停止/超时合同。适配必须预登记响应、串行执行，在关闭/断线时取消，并校验其 no-op 所需的未开始拖拽等前提。Prismarine windows 2.9.0 的 drag/doubleClick 尚未实现，协议 mode 合法也不能放行未实现路径；具体依赖依据见[研究复核](../research.md)。

### 12.4 结果确认

不同 MC 版本不一定提供相同的逐点击确认。

区分：

- 确定未派发。
- 已派发。
- 本地预测变化。
- 收到相关协议状态。
- 本次效果仍然未知。

click 返回共享 WindowClickReceipt，confirmed 仅列本次操作可确认的槽位与光标后态。Program 只用这些变化推进参照视图，未受影响槽位保留原预期；不能将任意实时 snapshot 归因为自身操作。

相关后态无法完整确认时 needsSnapshot=true，下次点击要求显式 snapshot。严格前态、潜在目标槽、光标与版本验证仍执行，不允许 expect:null 关闭检查；多次点击不构成服务端事务。此回执与 Program 参照推进属于待实现接线，不能由既有 fake bot 验收推定已经完成。

当前槽位符合预期，不必然证明某次历史交易完成。

未知交易不得盲目重试。

### 12.5 关闭窗口

`close()` 只能关闭自己仍然有效的窗口代次。

旧窗口不得清理新窗口。

普通 close 在光标非空或手势未结束时返回明确前置条件错误，调用方先通过显式操作处置；不能自动丢弃或搬移物品以换取“干净关闭”。作用域退出/停机仍须强制退役：Driver 关闭所属窗口并报告可能的光标后果、故障或未知，不以普通 close 的前置条件错误阻止撤销。旧版上游 closeWindow 还会附加窗口外点击，适配不能无条件继承该行为。

### 12.6 特殊交互

底层窗口输入可以通过同一受控资源模型扩展，例如：

- 村民交易。
- 附魔选择。
- 铁砧改名。
- 特殊工作站。
- 版本专属 GUI。
- 模组窗口协议。

不要求全部通过原始 `click(button, mode)` 完成。

新增特殊交互适配仍遵守相同的身份、串行和停止约束。

这里只规定客户端输入及事实边界；交易选择/附魔/改名的玩法规则归相应能力。现有 WindowSession 不因本文列举而自动拥有这些方法，确切新增输入应由所属适配在 public-api 维护，不向玩法模块泄漏 Bot。

## 13. 低层完成合同与回执

Driver 只承诺自己能够实际核验的范围。

| 操作 | 可声明的低层完成范围 |
|---|---|
| Drive | 输入在有效资格下应用了指定实际步数 |
| Feedback | 指定帧输出被后续实际物理步消费，不只是接收入队 |
| Attack | 一次攻击尝试实际派发 |
| Interact | 指定交互尝试实际派发 |
| Dig | 挖掘过程、预测和相关协议事实分别成立到什么程度 |
| Equip | 对应装备或槽位状态得到何种确认 |
| Window Click | 点击派发及相关槽位事实能够确认到什么程度 |

回执包含实际派发程度、声明的低层完成条件、已取得的证据和未知部分。

`sent` 只表示进入本地协议派发，不代表服务器完成。

不能因为一个本地 Promise 正常返回，就将外部效果标记为 `met`。

Driver 不判定：

- 是否成功击杀目标。
- 是否采够木材。
- 是否完成建筑。
- 是否完成用户的交易意图。

这些目标属于上层领域能力。

Runtime 关联并持久保存执行记录与效果证据；Driver 不建立第二套持久游戏任务日志。

高频操作允许按控制段聚合必要证据，不要求每个 Tick 同步写盘。

## 14. Minecraft 多版本兼容

### 14.1 兼容目标

Driver 应尽可能覆盖**所采用的 Mineflayer 版本及依赖组合实际支持的 Minecraft Java 协议版本**。

但明确区分：

1. 协议连接可用。
2. 客户端状态采集可用。
3. 某种底层操作可用。
4. 插件适配通过验证。
5. 具体玩法能够完整运行。

前一项成立不能自动证明后一项成立。

### 14.2 版本识别

Client Host 建立连接后取得实际协商版本及对应 Minecraft 数据。

版本识别使用 Mineflayer 和 PrismarineJS 已提供的机制。

不维护一份独立的硬编码版本百科。

### 14.3 底层能力判断

通过组合以下事实判断操作是否可用：

- 当前协议版本。
- `bot.supportFeature()` 等上游功能检查。
- minecraft-data / 运行环境数据。
- 实际适配实现的支持条件。
- 已知的限制或尚未验证状态。

底层能力可区分：

- `available`：当前环境满足该操作的实现与前置条件。
- `unavailable`：明确不支持，并说明原因。
- `unknown`：缺少足够证据，不能承诺支持。

不把某次测试成功推广成所有版本都已验证。

### 14.4 差异处理

Driver 负责协议和客户端操作层差异，例如：

- 方块与物品的数据表示。
- 物品组件及原生装备操作。
- 库存窗口和点击协议。
- 交互包与动作确认。
- 物理引擎及客户端基础能力。
- 实体、窗口和连接状态的版本相关处理。

实际支持需要依据版本条件选择相应原生实现或受控适配。

不要求为每个 MC 版本建立独立 Driver 子类。

### 14.5 新版本与模组

上游增加新版本时：

1. 核对当前依赖组合。
2. 核对协议与数据变化。
3. 复查实际写入适配点。
4. 验证客户端事实来源。
5. 验证关键操作与停止。
6. 更新底层可用性结论。

模组新增协议操作时，新增对应受控适配。

无法理解或实现的新机制应报告不支持，而不是假定普通原版操作一定可以处理。

### 14.6 依赖固定

固定影响控制与游戏行为的实际依赖集合，不仅是 Mineflayer 顶层版本。

包括相关 Pathfinder、PVP、Prismarine 组件及其实际运行依赖。

升级时重点检查：

- API 和协议变化。
- 异步恢复路径。
- 原生写入位置。
- 停止与清理。
- 预测及证据来源。
- 物理与反馈时序。

不要求所有 MC 版本拥有相同的高层玩法能力。

## 15. 底层扩展机制

Driver 的扩展单位是**受控原生操作/控制器/事实采样适配**，而不是新增一套 Skill 系统。

新增适配只需明确：

- 当前环境支持条件。
- 输入与输出。
- 实际资源和写入范围。
- 操作来源身份。
- 停止与清理方式。
- 低层完成范围。
- 事实采样与证据。

能力所有者通过已有 Callable 合同对外提供新玩法。

Driver 不负责这些 Callable 的发现、注册或策略选择。

若新操作能直接使用已有 BodyOps，则无需扩展 Driver。

只有真正缺少底层客户端能力时，才扩展相应受控适配。

## 16. 故障处理

| 故障 | Driver 处理 |
|---|---|
| Body 失效 | 立即拒绝旧来源新写入 |
| Operation 失效 | 撤销操作资源，不影响同一 Body 后续合法操作 |
| 旧回调迟到 | 使用创建时资格检查，拒绝其写入 |
| 插件停止不封闭 | 不允许交接，必要时重建 Bot |
| 连接断开 | 撤销活资格、失效当前覆盖与引用 |
| 死亡/重生 | 死亡立即撤销旧控制；重生建立新 Incarnation |
| 切换维度 | 重建有关身体与世界上下文 |
| 反馈过期 | 拒绝输出、撤销所属持续输入 |
| 物理步停滞 | 返回具体故障，不无限等待 Tick |
| 驱动关键线程阻塞 | 依靠执行域外监督检测及隔离 |
| 方块预测被否定 | 更正当前事实，保留原派发与未知证据 |
| 窗口竞争修改 | 拒绝失效预期，必要时明确重同步 |
| 窗口点击回执未知 | 不自动再次执行消费或转移 |
| 急停/Owner Lost/停用 | 立即关闭准入、撤销控制，不自动恢复旧运行 |
| 版本缺少功能 | 返回明确不可用或未知，不模拟成功 |

所有停止、故障和恢复行为必须保留已确定的游戏进度与未知效果。

## 17. 模块边界走查

### 17.1 采集

```text
Gathering Callable
  → Runtime.withBody
  → Navigation
  → 受控 Pathfinder
  → 导航 Operation 结束
  → 装备工具
  → Dig
  → Driver 发布预测与协议事实
  → Gathering 核验实际入包
  → Body Session 释放
  → Runtime 结算
```

导航、装备和挖掘共享一个 Body，但可以具有不同 Operation 身份。

旧导航结束后不能继续修改挖掘操作的移动状态。

### 17.2 兼容并行与必要交接

```text
上层协调者
  → 持有一个 Body
  → 启动移动/视角连续控制
  → 同一 scope 下启动 dig(preserve) 子操作
  → 移动物理步继续，挖掘等待/协议同时推进
  → 每次真实写入仍检查各自 Operation 与 Runtime 权限
  → 目标不可达或确需换装备时报告实际条件
  → 协调者只暂停冲突输出、结束必要操作，再恢复有效意图
```

整个过程只持一个身体资格；这里规定可表达的关系，尚未在真实服务器验证移动挖掘。移动/视角加单次攻击、移动/视角加使用也应有各自真实并行验收，而不是用先后完成冒充组合。

若当前选择完整受控独占插件，或有关适配尚无兼容组合合同，协调者才关闭旧流并完成屏障后执行它；选择何时切换和如何恢复算法状态属于调用方。

无协调关系的另一长期控制器不得并行竞争。

### 17.3 异步挖掘停止

```text
Dig D1
  → await lookAt
  → Runtime Stop
  → Driver 撤销 D1
  → 完成交接
  → 新操作 D2 开始
  → D1 的旧 await 返回
  → D1 试图发起挖掘
  → Write Gate 拒绝
```

D1 不能读取当前主人，并借用 D2 的资格。

D1 的迟到清理也不能影响 D2。

### 17.4 窗口回执未知

```text
Window W1
  → 预期槽位核验
  → 本地预测改变（来源为 prediction）
  → 点击已派发
  → 协议确认缺失
  → 连接断开
  → W1 失效
  → 新连接建立
  → 重新读取库存
  → 上层处理当前事实与历史未知效果
```

不能因为重新读取后物品数量符合预期，就直接认定之前的交易已完成。

## 18. 验证标准

### 18.1 控制所有权

必须证明：

- 同一时刻只有一个合法身体主人。
- 旧 Body/Operation/Controller 无法写入新主人状态。
- 旧窗口、监听器、插件目标和清理无法污染新资源。
- 并行冲突能够确定性拒绝。
- 复合控制与受控独占控制均能正常运行。
- 同一协调者的兼容移动/视角/攻击、移动/保留视角挖掘、移动/使用实际重叠推进，不靠全部关流或全局串行通过测试。
- read 子调用经捕获 act 代理、迟到 IPC 和无当前归属的事件回调不能取得写权。

### 18.2 插件停止与隔离

对固定版本的 Pathfinder、PVP、Digging、Inventory，在关键异步边界注入停止。

检查：

- 是否仍有旧业务发包。
- 是否仍有旧 Bot 状态修改。
- 是否留下持续输入。
- 是否误清新主人状态。
- 控制屏障是否诚实报告无法确认的情况。
- 精确解绑是否保留其他观察者；所有 removeAllListeners/全局 clear/旧 Promise/超时清理都纳入核查。

### 18.3 反馈与物理

验证：

- 实际物理步与输入时序一致。
- 旧帧不补播。
- 同帧单次动作不重复。
- 无新反馈时持续输入能够撤销。
- 区块不可模拟或物理暂停不会无限等待。
- 驱动关键事件循环没有被控制计算阻塞。
- 模拟后插件修改与模拟结果分别取证；未模拟但发 tick_end、补偿时间片丢弃均不增加 drive 步数。
- 同域 stop/定时器在整体阻塞时失效，由受管启动者终止并观察退出，退出前不放行替代连接。
- 监督方崩溃、所属进程树清理和生命周期绑定另做 OS 边界验证，不能用仅终止一个直接子进程代替。

### 18.4 游戏协议效果

使用真实服务器验证：

- 服务器拒绝挖掘后的本地预测修正。
- 物品使用中断及释放效果。
- 攻击派发与命中结果分离。
- 多人容器竞争与库存重同步。
- 窗口 ID 复用及非空光标处理。
- 重生和跨维度后的旧引用失效。

兼容并行须在真实服务器确认下列结果，不能以调用可同时派发、Promise 返回或本地预测代替：

| 场景 | 要核验的游戏效果 |
| --- | --- |
| 移动中 dig(preserve) | 在所声明的可达/瞄准条件内，移动是否造成挖掘重置或被拒；服务端方块结果与所需掉落证据是否成立。越界失败须有原因，不算整个组合成功 |
| 移动与拉弓/持续使用 | 使用是否被移动或下一帧意外中止、重复激活或提前释放；根据实际可得的服务端实体/物品结果及测试服观测核验，不能只读本地 usingHeldItem |
| 连续控制中的临时交互 | 交互是否发生；移动/视角是否仅按声明的冲突范围改变，兼容输出是否继续，恢复是否基于新事实；不得把未声明的全局清键/转头当正常协调 |
| 同场景成熟插件对照 | 在相同游戏版本、权限、初始条件与网络条件下比较目标成功率、耗时、资源损耗、卡住/恢复和控制延迟，检查组合适配是否明显退化 |

接口保持这些组合的表达能力，不提前承诺每种动作都同时成功，也不因某一组合未验证就全局禁止并行。具体不支持或尚未知的条件应准确说明；已允许尝试的执行仍按实际证据返回达成、失败或未知。

### 18.5 实际控制效果

对照成熟原生插件验证：

- 路线执行成功率与耗时。
- 窄桥、冰面、跑跳和碰撞。
- 导航中的挖掘与放置。
- 战斗追击与复合走位。
- 高频反馈延迟。
- 异常恢复能力。

适配造成明显行为退化时，应复查控制隔离方式、组合方法及所选复用路径，而不是默认接受退化或继续叠补丁。必要时保留成熟插件的受控独占执行，另为真正需要组合的场景提供适配；不能仅凭接口允许并发宣称组合方案更优。

### 18.6 多版本

对声明支持的协议版本分别验证：

- 连接和客户端同步。
- 基础移动与观察。
- 挖掘、交互、装备。
- 库存与窗口。
- 关键原生插件。
- 停止与恢复。
- 底层功能可用性判断。

只有真实验证覆盖的操作和版本组合才能标记为已验证。

### 18.7 验证层次

- **静态与单元验证**：接口、身份、操作规则。
- **故障注入**：异步写入、停止与资源隔离。
- **真实服务器验证**：协议和游戏事实。
- **真实 Uina 游玩验证**：实际效果、自由度、响应与成本。

前两层通过不能代替后两层。

## 19. 最终取舍

| 问题 | 采用 | 不采用 |
|---|---|---|
| 客户端 | 私有长寿命 Mineflayer | 自研完整客户端 |
| 身体所有权 | 单一有效资格 | 多独立身体队列 |
| 控制器 | 组合与受控独占并存 | 全部强制逐 Tick 混合 |
| 操作 | 连续与离散分别表达 | 一种输入模型包办所有行为 |
| 插件适配 | 固定依赖、实际写入点适配 | 裸用插件 + AbortSignal |
| 停止 | 资格撤销、来源隔离、交接屏障 | 只等待插件 stop |
| 当前状态 | Mineflayer + 来源/覆盖元数据 | 完整复制第二套世界 |
| 反馈 | 本地高频控制、外部脚本计算 | 每 Tick 调用 LLM |
| 版本兼容 | 上游支持 + 实际能力检测 | 每个版本建立 Driver 子类 |
| 底层扩展 | 受控操作与协议适配 | 新建通用插件运行框架 |
| 游戏策略 | 不在 Driver 中实现 | Driver 内置建筑、战斗等决策 |

## 20. 本文的证据边界

本轮阅读当前 Uina 与固定上游源码，复核跨模块合同，并执行 §18.8 的原始故障/执行域探针。控制内核已实现（fake bot 阶段，118 例集成/单元验收）；真实 Mineflayer 适配补丁、真实服务端、反馈桥接测量与游玩对照尚无。其余验证标准仍待执行，不能据本文状态、反例断言或类型检查宣称已满足。

**最终定位：Driver 是 Uina 在 Minecraft 中唯一受控的客户端操作边界。它负责可靠地控制玩家并提供真实客户端事实，而不负责决定玩家应该做什么。**
