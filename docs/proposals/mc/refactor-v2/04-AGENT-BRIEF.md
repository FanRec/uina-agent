# 交给编码 AI 的工作指令

此文作为开发与评审提示词模板。**它不是命令 AI 机械照搬具体算法**；开发 Agent 应据实际源码、测试和当前依赖自主选择最简有效方案。

## 1. 编码 Agent 主指令（复制后填工作包）

```text
任务：重构 Uina Minecraft World 的 [M编号/模块名]。

必须先阅读：
- 01-DESIGN.md 中对应设计及跨模块原则；
- 02-IMPLEMENTATION.md 的该工作包、依赖和代码所有权；
- 03-VALIDATION.md 的相关验收场景；
- 仓库现行 docs/proposals/mc 的权威文档；
- 本次任务标注的 Uina 与 Cortico 源码及对应测试。

工作目标：提高真实 Minecraft 游戏场景的正确性、成功率和效率，保持原有 Uina Runtime / Program / World / Driver 边界。

执行：
1. 先核对当前代码版本与真实缺口。列出已实现、确实欠缺和当前不适用的 Cortico 技巧；不要把旧审查意见当定论。
2. 先找可复现的失败；提出最小有效的算法/接口改法。必要时对比两种方案，自主选择质量更高者，并说明为什么。
3. 直接实现，不留一套新旧平行策略。仅改本工作包拥有的文件；跨模块变更先写短接口提案，交所有者集成。
4. 复用当前调用、授权、World 观察、Body Feedback、Effect 与 Library。不要新增同功能 Manager/队列/状态库，也不允许未经授权直接控制 Bot。
5. 写/改对应单测与集成场景，并尽量真服验证。结果分开标注 T0/T1/T2/T3；未跑不算 PASS。
6. 移除无消费者旧代码和多余配置；更新当前权威文档与必要的变更记录。

允许你优化甚至推翻本设计提出的可选算法，但不能凭主观宣称优越：必须说明对用户任务的收益、成本、接口影响和验证证据。若一个简单修复能解决问题，不引入复杂预测/策略框架。

交付：diff 概要、修改前证据、设计决策、实施结果、测试命令与结果、未验证范围、删除清单和跨模块接缝。
```

## 2. 独立评审 Agent 指令

```text
你负责审查另一名 Agent 已完成的 Uina MC 工作包，不负责替它辩护。

按实际源码和运行证据检查：
- 产品任务是否真正改善，而非仅多了接口、日志或错误包装？
- 是否保留唯一身体写入源、Effect/事实归属、真实完成条件？
- 规划与执行是否共享物理/权限规则？
- 是否增加新旧双轨、重复状态、无消费者抽象、过度重试？
- 与 Cortico 的参考算法相比有无核心遗漏、版本不适配或错误移植？
- 性能和成功率是否有固定场景对照，未测试部分是否如实表述？
- 所有修改是否在约定代码所有权内？是否更新了权威文档？

输出仅分四类：阻断问题（附源码/复现证据）、非阻断问题、经过验证的改进、应删除/简化项。
不要因为代码更短或更复杂而自动判好坏，不要提出没有真实消费者的新通用框架。
```

## 3. 共享接口提案（跨工作包时使用）

```markdown
## 接口变更提案
- 使用场景/当前不能完成什么：
- 现有接口为何不足：
- 数据所有者、唯一写入者、消费者：
- 最小接口形状（必要时示意 TypeScript）：
- 对计划/执行/取消/失效的影响：
- 可不加接口的替代方案及其不足：
- 测试和迁移：
```

**提案简短即可**。如果可以只改内部函数，不需要填写此模板；不应让开会/文档开销妨碍真实功能修复。

## 4. 提交评审顺序

- 先审查“是否真的解决用户问题”，再看边界是否清晰。
- 通过边界与结果检查后，再审查性能、命名、抽象和注释。
- 如果算法更强但实现不够干净，优先局部重构收敛，不以推倒整个项目为默认答案。
- 如果算法很漂亮但没有可复现收益，回退到简单方案。
- 不要求所有任务一次提交一套完整系统；每个工作包应可单独验收和回滚。
