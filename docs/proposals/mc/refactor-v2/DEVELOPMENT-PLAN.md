## 0. 立即执行的指令

你现在是本轮 Uina Minecraft World 重构的**技术负责人兼开发执行者**。已有一版设计与实施方案。你的任务不是再次泛泛比较 Uina 和 Cortico，而是：

1. **快速核验方案**：读取当前代码、既有文档和关键测试；检查方案中的事实、模块责任、依赖和算法选择。明确沿用、调整、否决的内容，并把发现的重大遗漏补入计划。
2. **自行裁定本轮开发范围**：从下述工作包选取一个能够完整实现、集成、测试和清理的纵向切片。默认从导航实际失败与底层正确性开始，除非现状证据支持调整优先级。
3. **直接开发**：定位根因，必要时重构或重写局部代码；修复后删除被替代的旧实现；同步更新权威文档。
4. **直接验证**：有可用 MC 测试服务器就执行真实场景；无服务器时完成可执行的 T0/T1 测试并将 T2 标为 `NOT_RUN`，不要虚报完成。
5. **持续推进**：每完成一个已验收切片，依据收益、依赖和剩余问题选择下一切片。不要每完成一个小步骤就请求我批准；遇到确实需要外部凭证、破坏性操作或不可获取资源的阻断再说明。

**不得将“完成设计”“代码编译通过”“单次接口返回成功”作为领域能力完成的证明。** 不确定的事情如实写明；能用测试验证的优先测试，而不是讨论。

## 1. 产品目标与边界

本次重构要改善真实生存世界的玩家体验：

| 用户任务 | 应达到的结果 | 不合格的假象 |
|---|---|---|
| 走到目的地、绕过障碍 | 实际可站立地抵达；无法到达时能解释物理/规则阻碍 | `route.plan` 可达，`goto` 原地空转或只等超时 |
| 清除威胁或安全脱险 | 合理走位/攻击；真正远离危险；死亡与击杀有证据 | 仅发送攻击包视为命中；撤退未成功却报 `retreated` |
| 根据蓝图建造 | 目标方块/属性真实成立，施工期间保留行动通道 | 循环遍历完就当完工；错误站位反复导航 |
| 探索洞穴/寻找目标 | 覆盖实际可达的未知区域，减少重复路径 | 四个方向尝试完就宣告探索结束 |
| 自主准备资源/装备 | 能处理局部失败，必要时才将高层决定交给 Program/LLM | 每个物理动作都要模型推理；反复调用而无进展 |

**优先顺序**：服务端事实与控制正确性 → 真实任务成功率 → 失败后有效纠错 → 时间/资源/模型成本 → 代码体量。不得为了少代码删除必需的不变量，也不得为了“万无一失”堆积无消费者的机制。

**保留边界**：Runtime 管 Run/Call/Effect、授权、停止与恢复；Driver 管 Mineflayer、物理、协议与身体写入；World 管观察/历史；Capability 管 MC 领域行为；Program 管目标组合；Library 管资产。不要创建新的 MC Agent Loop、第二个 Body 仲裁器、全局任务队列或状态真源。

## 2. 开工前：一次性核验，不重复做大调研

### 2.1 读取顺序

1. 执行 `git status`、`git rev-parse HEAD`，确认本地未提交改动；有改动先识别归属，禁止覆盖。
2. 读 `docs/proposals/mc/{README.md,development-plan.md,development-guide.md,known-gaps.md,design.md,contracts.md,public-api.md}`，以及涉及模块的 `modules/*.md`。确认已有文档可能滞后，以代码和可复现行为为准。
3. 阅读本包 `01-DESIGN.md`、`02-IMPLEMENTATION.md`、`03-VALIDATION.md`；按待修改目录查看代码、调用方及测试。不要为做 G25 而先通读整个宿主框架。
4. 阅读实际依赖版本、patch 文件、`package.json` 的 MC 测试命令和测试服务器启动方式。
5. **仅针对拟修改算法**阅读 Cortico 相应实现及测试，不复制其框架，也不在尚未确认适配性前移植整份补丁。

### 2.2 方案裁决（精简，完成后立即开工）

对于准备实施的工作包，形成不超过一页的表：

| 项目 | 必填结论 |
|---|---|
| 现有行为 | 当前源码位置、现象、已做过的修复及其证据 |
| 设计裁决 | `沿用 / 调整 / 否决`，理由是什么 |
| 最小有效方案 | 优先尝试的实现，为什么足以解决问题 |
| 是否重写 | 局部改、局部重写或完整替换及理由 |
| 跨模块影响 | 实际调用方、控制/状态所有权、公开契约是否变化 |
| 验收办法 | 能复现错误并验证游戏效果的具体测试 |

**发现既有设计有误时直接修订；发现某工作包已解决就标记完成并略过，不为执行计划而再次重写。** 只有依赖关系或架构边界发生实质变化时，才重新审查总体设计。

## 3. 任务选择与推进机制

### 3.1 优先级判断

以`影响×发生频率×失败代价×可验证性`综合判断，同时考虑前置依赖与变更风险。数值不是必需；必须写清为什么当前任务优先于下一任务。

默认优先级：

1. **P0：基础真实行为不正确**——已知导航 G25、计划/执行不一致、真实放置/挖掘确认、Body 停止与执行隔离。
2. **P1：领域动作不达预期**——战斗假撤退、卡顿走位、建造站位失败/依赖问题、探索覆盖不足。
3. **P1：长任务体验**——自保、生产与物品纠错、Agent 可理解的失败和可重用 Program。
4. **P2：有证据的性能优化**——路径搜索热点、运动开销、无谓 IPC/持久化、工具上下文成本。

已有正确的能力不要因为 Cortico 代码更多就重新实现。理论上更优但暂无可复现场景的算法，不能优先于确定性缺陷。

### 3.2 每轮只选择一个可闭环的开发切片

**切片必须包含**：明确的坏行为/缺口、根因、方案、代码范围、真实或可运行验收、旧实现清理和文档更新。切片通常覆盖一个主要模块及必需的邻接修复，不要求同时完成全部 M0–M10。

默认首个切片：**G25 路径规划可达但实际侧隙绕柱无法移动**，范围 M0 + M2/M3，必要时包含 M1 的窄修复。若当前工作树已解决 G25，则按已知可复现导航缺陷或战斗撤退语义错误选下一项。

**不得**只完成“写了新类/接通了接口/加了测试骨架”就关闭切片。若真实场景未验证，维持 `待真服验收`，可以同时推进不依赖服务器的下一个切片。

### 3.3 开发循环

```text
核实当前事实与设计
    ↓
选择最值得修的完整切片
    ↓
复现 → 定位根因 → 确定最小方案
    ↓
实现/重写 → 测试 → 修正 → 删除旧实现
    ↓
检查依赖、权限、实战结果与回归
    ↓
更新项目原有权威文档、记录证据
    ↓
选择下一切片（有条件则继续）
```

完成切片后不要重新启动“全面研究阶段”。只有发现设计基础被推翻时才调整模块结构。

## 5. 推荐的开发顺序与解锁条件

### 批次 A：导航端到端闭环（默认先启动）

**目标**：实际修复导航问题，而不是只加更快的失败退出。

1. M0 固定 `G25` 山地单格侧隙，连同平地 30 格、1 格台阶、三级台阶和上行走廊对照；记录环境初始化和 Mineflayer 事件。
2. 对照 `route.plan` 的 Movements 与 `goto` 实际配置及执行轨迹，判明是搜索候选、物理可行性还是路径跟随错误。
3. 选择最小修复。必要时吸收 Cortico 的搜索级缓存、方块特征、门/水/放置约束、失败放置避让；**但性能优化不可代替 G25 修复**。
4. 真服重复验证修复，并保留现有 G21/G24 的成功场景。
5. 删除为旧缺陷而存在且不再必要的特殊兜底，清理多份配置/判断。

**解锁下一批**：受影响的导航场景有真实可达或准确不可达结论，停止/超时/取消无回归；如果测试服务器不可用，明确标 `待真服验收`，但可推进领域纯算法。

### 批次 B：战斗 + 施工 + 探索（适合并行）

**战斗优先子切片**：先修正 `withdraw` 终态与假 `retreated`，再把持续移动/攻击的控制循环从串行等待证据中解耦；以 Cortico `combat-context.ts` 为简洁基线，比较效果决定是否引入预测控制。

**施工优先子切片**：保留现有 Target/Diff/Library；修复只尝试首站位、固定次数反复施工；加入必需的支撑依赖与可工作站位选择。只在真实施工问题要求时增加临时脚手架和显式渐进模式，不预建通用施工框架。

**探索优先子切片**：替换四向游标为轻量前沿探索；先做会话内稀疏覆盖、可达性和未观察边界。跨 Run 持久化不是第一阶段必选项。

这三个模块可以先做纯算法与测试，导航接缝稳定后分别完成真服集成；不可直接改写 M2/M3 的实现文件。

### 批次 C：真实持续任务与长期稳定性

结合 M7/M8/M9，按最影响长任务成功的具体失败推进：自保抢占、复杂物品操作、恢复后重复动作、工具使用理解。保留 Program/Runtime 的高层任务管理与恢复语义，不从 Cortico 引入第二个任务框架。

**发布收口**：执行受影响场景回归和至少一次真实 LLM/Program 长任务；检查实际进度、死亡、无效调用、恢复效果、Token 消耗；没有 LLM 或服务器能力时如实标记而不是补造模拟报告。

## 6. 三条必须固定的架构接缝

**S1 Driver → 领域**：底层只产出事实和受控操作结果，不能直接决定建筑任务是否完成、战斗是否胜利。服务端接受/拒绝与未知状态不得被吞掉。接口优先复用 `BodyCallScope` / `WindowSession` / 现有结果；确有消费者时才补窄接口。

**S2 搜索 ↔ 执行**：一套 Movements/动作合法性定义，供只读计划与真实导航使用；但两者可以有不同的运行预算、缓存和结算。不要让 `route.plan` 对活动 Bot 产生副作用。

**S3 领域 ↔ 控制**：战斗、施工、探索通过 Runtime 与现有 Goto/Body 获取资格；本地连续控制与 Pathfinder 跟随互斥。安全抢占、停止与重连/维度变化后，旧操作不可重新写入。

接口不足时先核查消费者和最小调用场景，再修改唯一拥有者。禁止先造万能策略框架再让各模块适配它。

## 7. 实现取舍：给开发 Agent 保留判断空间

| 议题 | 默认方向 | 何时允许变更 |
|---|---|---|
| Cortico `pathfinder-perf.ts` | 抽取有价值的算法与测试，不整个覆盖 `Movements.prototype` | 发现必须修改上游且最小补丁不可维护时，评估受控 fork |
| 上游依赖补丁 | 先检查已有 `patches/`、包版本和真实根因 | 若重写局部依赖更简单可靠，可以直接重构；保留 MIT 授权归属 |
| 局部预测控制 | 非必选项；先修现有 Pathfinder/步态 | 实测固定场景收益稳定、CPU/延迟可接受 |
| 战斗 Context Steering | 以 Cortico 纯策略为基线，适配 Uina 控制 | 若另一简单策略在同场景更好，可替换 |
| 施工依赖 | Ready 集 + 真正需要的支撑约束 | 复杂建筑证明必须用完整 DAG 时再实现 |
| 地图结构 | 当前任务的轻量稀疏覆盖 | 真实跨任务复用需要，再走既有 World Record |
| 物理安全与身份代次 | 保留现有单写源、取消及隔离 | 只接受等价且可证明更简单的改写，不删正确性 |

**不为“以后可能有用”维护两个执行器、两套状态或一堆可选适配层。** 优化必须对真实行为或明确维护成本产生收益。对有争议的新算法，可以短期在测试分支 A/B；决定后只保留胜出的主线实现。

## 8. 测试、完成判据和真实性

### 8.1 验收层次

- **T0：** 类型、纯函数、单元和回归测试。
- **T1：** 控制/协议集成与异常时序；不等价于服务器实际接受。
- **T2：** 实际 Java 服务端固定场景；要求目标方块、玩家位置、伤害/死亡等游戏事实可核验。
- **T3：** 真实 Program/LLM 连续任务；用于验证自治、工具使用和进度恢复；不把 T3 用在确定性单测上。

基线可复用命令（执行前查看脚本副作用、服务器设置和权限）：

```bash
pnpm test
pnpm typecheck
pnpm build
pnpm dev:mc:climb
pnpm dev:mc:terrain-nav
pnpm dev:mc:combat
pnpm dev:mc:build
pnpm dev:mc:repair
pnpm dev:mc:production-repair
pnpm dev:mc:i2
```

所有这些命令**存在于参考基线 `package.json`**，不保证当前工作区或测试环境已就绪。只执行与当前改动相关的测试，集成阶段再做覆盖全部相关范围的回归。

### 8.2 完成一个切片必须同时满足

1. 原问题被复现，或给出可信的既有服务器日志证明；修改后的成功判断依赖真实状态，不只依赖返回码。
2. 必要 T0/T1 通过；涉及物理、战斗和施工的功能具有对应 T2 验证，未执行则明确“待验收”。
3. 已有成功案例不能退化；对确定性地形至少进行多次独立重复，并记录次数、失败条件和时延；随机战斗注明样本数量，不靠单场胜负下结论。
4. 同时检查中断、停止、重连、旧异步回调和未知结果；不新增双 Body 写入者和重复副作用。
5. 被替换的逻辑、配置、测试假设、死代码已经清理；公开契约如变化，所有消费者和权威文档同步更新。
6. 给出简短证据：改动前后实际表现、代码 diff、测试命令、测试环境和未解决问题。

**验收反例**：超时从 40 秒降低到 10 秒很有价值，但如果可以物理通过的侧隙仍无法通过，不能把“导航增强完成”写入结论。攻击已发送但未命中、尝试撤退却未脱险、计划含缺失块却输出完成，同理。

### 8.3 没有服务器或 LLM 时如何继续

不必为了启动确定性开发而等待资源。能做 T0/T1 的先做；明确记下缺失的 T2/T3，不把它们归类为 PASS。选择另一项不依赖该资源的完整切片推进；等环境具备后优先补验。不要求为绕过服务器缺失而构建大型模拟器。

有服务器时尽量直接测试，但只在本地/授权测试世界执行可能修改地形、生成怪物或清空物品的场景；使用独立测试地块和可恢复初始化，不破坏正式存档或其他玩家资产。

## 9. 并行编码与代码所有权

| 所有权 | 唯一负责的文件/区域 | 可以并行的其他工作 |
|---|---|---|
| M1 | `driver/mineflayer/protocol.ts`、`driver/window/`、相关底层身体操作 | M2 的搜索独立文件；M4/M5/M6 纯算法 |
| M2 | `driver/mineflayer/pathfinder.ts`、Pathfinder 依赖补丁 | M1 协议；M4/M5/M6 纯算法 |
| M3 | `driver/goto.ts`、`driver/input/walking.ts` | M4 战斗、M5 施工、M6 探索内部文件 |
| M4/M7 | 战斗/生存模块；各自负责逻辑，不重复控制权管理 | M5、M6、M8 |
| M5 | `construction/`、`actions/build.ts` 等施工文件 | M4、M6、M8 |
| M6 | `actions/explore.ts`、`shared/explore.ts` | M4、M5、M8 |
| M8 | 物品/工作站领域文件，**不碰 M1 的 WindowSession 实现** | M4、M5、M6 |

多 Agent 并行时使用独立 Git worktree/分支；只在唯一 owner 处集成跨模块改动。单 Agent 工作时按切片串行推进更简单，不必为了模仿团队流程创建额外 worktree 或审批层。

**跨域变更格式**（仅当确有需要）：`问题与消费者 → 现有端口为何不足 → 最小新合同 → 谁实现 → 回归测试 → 旧代码处理`。不写冗长 RFC。

## 10. 进度管理、文档与交付

以仓库既有 `docs/proposals/mc/development-plan.md` 维护本轮当前进度（如果其结构已经足够，按原格式添加简短一节即可），`known-gaps.md` 跟踪仍开放的问题和关闭证据，模块设计写到对应 `modules/*.md`，变更原因写 `changelog.md`。**不要把本执行计划长期复制成第二套权威设计。**

每个切片保留一条紧凑记录：

```markdown
| ID | 范围/目标 | 状态 | 代码变更 | 验证 | 余项 |
|---|---|---|---|---|---|
| N-G25 | 山地侧隙导航 | doing | pathfinder/goto | T0 PASS, T2 NOT_RUN | 待真服 |
```

状态使用 `todo / doing / verify / done / blocked`；`done` 必须满足切片验收，`verify` 用于代码已完成但真实验证缺失的情况。不要无证据地将整个 M4/M5 标记完成。旧文档中先前的 PASS 记录只用于回归基线，不代表本次新实现 PASS。

每完成一个切片给出不超过必要篇幅的报告：

```markdown
### 完成：<切片 ID / 目标>
- 根因与旧行为：
- 关键设计取舍（含是否采用 Cortico 方案）：
- 修改/删除的源码：
- 实际结果：场景、次数、指标及日志路径：
- T0/T1/T2/T3：PASS / FAIL / NOT_RUN：
- 仍存在的问题：
- 下一切片及选择理由：
```

若测试失败，继续修复或回退并说明；不能因已经投入较多代码就保留没有收益的复杂方案。只有访问权限/凭证/不可逆外部操作必须由用户决定时才停止该分支并询问，不把正常技术取舍交回用户。

## 11. 本轮启动顺序（直接执行）

1. 查工作区 HEAD/未提交修改、现有 MC 文档、`known-gaps` 和现有 MC 测试入口。
2. 对本包设计做**针对当前首选任务的快速裁决**：保留/调整/否决；只列影响开发的结论。
3. 优先尝试复现 G25。如果 G25 已不适用，找到当前最影响实际导航成功的可复现问题；同时检查战斗 `withdraw` 的成功判定。
4. 自行选定第一切片的边界和代码 owner，直接进行根因修复、测试与清理。
5. 更新仓库内权威文档，报告本次完成结果和下一切片；若仍有充足能力与环境，继续下一切片，不重新做整仓研究。

**最后强调**：本计划规定的是问题选择方法、架构约束和交付标准。具体算法、数据结构、文件组织与重写程度可由你根据代码与真实测试作出更好的决定。目标是 Uina 在 Minecraft 里真正玩得更好，而不是机械完成 M0–M10 清单。
