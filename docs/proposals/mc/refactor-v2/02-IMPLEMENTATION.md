# Uina MC 重构实施方案与开发工作包

> 本文按开发责任而不是运行时模块划分任务。M0–M10 **不是** 11 个新的 Manager。  
> 所有路径相对仓库根目录；MC 源码根为 `.uina/worlds/minecraft/`。

## 1. 落地方法

每个工作包遵循五步：

1. **核对事实**：查看当前实现、已有测试与 Cortico 对应文件，写清确实缺什么，不能依据旧审查报告直接删代码。
2. **确定局部设计**：列出将复用的现有端口、拟修改的行为、可选算法；仅必要时提交跨模块接口提议。
3. **实现和替换**：先写失败复现，再修改唯一所有者；旧代码被替代后删除，不长期并存。
4. **验证收益**：单测、集成/真服对比；记录未验证项，不以类型检查代替真实游戏效果。
5. **收敛交付**：清理冗余、修改权威文档，提交 diff、验证命令和数据，交给独立审查。

不要求 Agent 机械照搬此文列出的函数结构：若找到更少改动、更可测试且效果更好的实现，应提供原因和证据直接采用。禁止偏离的仅是本文件的**所有权、对外语义、实战验收**。

### 2.1 首先冻结三条内部接缝

**S1：M1 → M2/M3**。服务端放置/挖掘反馈、碰撞与物理条件由底层唯一产生。M2 不自行解析窗口协议；M1 不直接调整 A* 代价。需要共享的失败事实优先使用现有回执。确实不足时由 M1/M2 提议极窄的内部类型，至少有一项已实现的消费测试。

**S2：M2 ↔ M3**。M2 负责 Movement 搜索规则、动作合法性、route.plan；M3 负责真实移动、控制授权、物理进展和停止。计划/执行选项一致；不必强制两者拥有相同超时、缓存或完成判据，因其用途不同。

**S3：M3 ↔ M4/M5/M6**。领域能力只能通过现有 `gotoDirector`、`runtime().navigate`、`ctx.withBody`、`World.read` 等接口。M4 的连续身体控制与 Goto 要明确移交；M5 工地约束经规划器窄入口；M6 只读路由估价不改变活动导航。

## 3. 任务内容和完成条件

### M0 · 场景与基线

**工作**：复用已有 `dev:mc:climb`、`dev:mc:terrain-nav`、`dev:mc:combat`、`dev:mc:build`、`dev:mc:repair`、`dev:mc:production-repair`、`dev:mc:i2`；整理其输入、世界重置、输出证据。优先重现 G25；建立协议乱序、攻击撤退错误、建筑首候选站位等回归。统一少量 trace 字段即可，不要新建一套通用 E2E 平台。

**完成**：冻结旧版本 SHA、环境、场景、原始结果和跑法；测试数据能区分 `PASS / FAIL / NOT_RUN`；T2 真服结果和纯单测不混写。无法自动创建怪物/地形时保留可重复的人工布置说明。

### M1 · Mineflayer 正确性与协议修复

**研究先行**：对照 Cortico `mineflayer-fixes.ts` 逐项制作差异表：Uina 已有/缺失/不适用（版本不符）。按消费价值选择修改：窗口 `stateId`/迟到包、放置是否服务端接受、dig 闩锁、右键交互块潜行、特殊方块放置确认、同格并发与客户端碰撞状态。

**实现边界**：只修 Driver 底层事实与操作语义；不为生产或施工创建新 API。若上游补丁必要，提供对应包版本、原因、最小差异和失败复现。避免将 Cortico 的全局 `Module._compile` 猴子补丁整块移来。

**完成**：旧窗口事件不会污染新窗口；服务端拒放不记作已放；旧代次操作不会影响新 Owner；Uina 1.21.11 真服协议测试通过。M2 只接收能够解释“当前放置位置为何不可用”的证据，不依赖字符串正则。

### M2 · Pathfinder 搜索与代价

**研究先行**：重现 G25，采集规划时 Movements、实时导航时 Movements、搜索节点、路径原始动作、玩家位置、实际物理输入。先确认规划/执行差异源头，再修正。对照 Cortico 的搜索缓存、门、深水、脚手架、工地禁放/禁挖规则。

**实现顺序**：

- 使 `planPath` / 实际 `goto` 的共享参数得到统一解释，清理重复配置；保持只读计划不影响活动 Bot。
- 逐项补齐动作合法性，拒绝凭空生成无法贴面的放置、危险门路径或未知数据的虚假前提。
- 接入 M1 的明确失败反馈；相同条件下被拒的具体动作本次不再无限重选。
- 在搜索结果语义稳定后优化 stateId、方块对象和 dig 成本热点；保留每次搜索的缓存生命周期，避免世界状态过期。

**完成**：N01–N07 完成重要场景的重复真服对照；G25 的症状解决或根因已被确定并使规划与执行不再矛盾；搜索结果不因缓存误判为旧世界。修改 Pathfinder 的实际 owner 仅此一组。

### M3 · 跟随、步态与短时纠错

**工作**：阅读现有 G21/G24 跳跃修复及三路看门狗。把现有结果分成“物理可修正/路径无解/目标变化/控制已撤销”，避免所有局部失败都靠整段超时。检查 GoalNear 在近距返回成功却没走到可工作站位的情况；统一 `stepTo`、局部转向、跳跃、停止。

**可选实验**：在固定台阶/窄缝/上坡上测试有限动作候选预测；只有实际成功率和延迟收益明显才将预测函数保留。不得因它而重写 `FeedbackStream` 或物理 Tick 管线。

**完成**：N01–N07 无已知回归；运动能够及时停止，Body/Goto 两种资格无并发写；异常终态可解释且能指导重新规划。

### M4 · Combat 控制器

**工作**：先将 Context Steering/目标选择/退避判定做成无 I/O 的纯决策函数和测试；再替换 `actions/combat.ts` 里的离散行为循环。传感来自现有事实/反馈；会话持有 Body 连续走位，必要长距追击时释放再调用 `navigate/goto`；异步观察命中/死亡，不阻塞移动决策。优先覆盖：近战攻击冷却、盾牌、群战、远程怪、苦力怕、悬崖撤退。

**重点修复**：`withdraw()` 只返回终点而调用方直接结算 `retreated`；改为“确实安全/受阻”判据。`fight@1` 的返回/错误与历史 Program 消费者兼容，否则走能力版本升级。

**完成**：B01–B06 对旧版和移植基线比较；死亡/命中/撤退依据服务端事实；安全抢占不留下旧输入；无需 LLM 高频参与战斗。

### M5 · Construction 约束和调度

**工作**：保留 Target/Diff。对照 Cortico 的主从格、附着规则和功能方块；改写调度为“已满足依赖的 ready 操作 + 站位可行性 + 同站位批量施工”。针对已知的第一站位失败和固定 4 pass 问题，要求因地形/依赖变化决定是否再试。添加必要脚手架及清理确认，保护已完成的建筑和其他玩家方块。

**设计自由**：不要求全量 DAG 或精确最优解；简单场景的稳定启发式若更好就用。对 `MAX_PLAN_TARGETS=2048` 优先区分单次计算/传输限额与整个项目体量；不为了大建筑先建立新蓝图库。渐进施工需要用户显式选择且处理旧外部 schema 兼容。

**完成**：C01–C05 真服核验完成格/材料/临时块；施工失败能报告真实剩余；断线后按现场续做，不重复已成功放置。

### M6 · Explorer 覆盖与前沿

**工作**：将 `ExploreCursor` 四向策略替换为轻量空间前沿选择；只记录真实观察和当前任务必要的空间信息。按世界/维度分区，可在活动内临时保留，跨 Run 复用视实际需求走 World 记录。每轮选前沿、估价、导航、观察、更新；局部失败不能屏蔽整个朝向。

**设计自由**：稀疏 3D 图、区域图或局部拓扑图由测试地图决定；不预建 Octree/SLAM/全世界持久体素库存。信息收益可用未观察邻域计数等简单估计。

**完成**：E01–E03 的覆盖和重复路程相对旧四向方案改善；结果明确搜索预算和事实覆盖，不把未观察当没发现。

### M7 · 生存与任务维持

**工作**：复测现有岩浆、溺水、受击与低血量行为；对照 Cortico 反射处理判断是否值得补充火焰、坠落、敌人主动防卫。保留 Runtime Safety 抢占；战斗撤退的局部算法可以共享，但控制权限不能分叉。补光/进食/垫脚优先落在明确的隧道/采集/施工调用内部，不做新常驻万能 Upkeep。

**完成**：S01、B05/B06；危机解除有实际证据，任务能依已有进度恢复，反射与任务无双写。

### M8 · 生产/物品和工作站

**工作**：测试合成、窗口、容器、熔炼、交易与异常物品状态；复用 M1 的唯一 WindowSession 与服务端回执。物品使用组件和耐久信息、工具选择、空间不足报告；减少无意义反复开窗/装备。现有 `smelt@1` 的 `wait` 不需要重新发明。

**完成**：P01–P03，缺料/满包/断线的已发送不确定操作不会盲重放；不建立新的窗口状态真源。

### M9 · Agent 使用与 Program 组合

**工作**：使用真实 LLM 调用数据优化 descriptor、错误 `hint` 和少量必要的使用示例。对 `describe` 与工具发现流程做上下文压缩，不增加同义工具；常见长任务由可复用 Program 组合。Cortico 的 `precheck/goal-plan` 可参考“先看是否满足前提/用事实确认目标”的思路，**不复制它们的 MCP 工具和队列机制**。

**完成**：U01（洞穴铁矿）/U02（小屋）/U03（装备准备）中，模型无效调用、重复动作、对错误原因的误解下降，并能使用已有 Program 继续任务。

### M10 · 精简与综合集成

**工作**：每批集成后清理被取代的四向探索、固定重试、旧战斗追击、重复站位逻辑；检查未使用配置、未消费者内部 API。测量是否存在高频操作的 IPC/DB/Body 切换开销，**仅优化有数据的热点**。同步源码真实状态、项目文档、公开合同和 changelog；30 分钟以上真实模型长跑及故障注入。

**完成**：没有持续存在的新旧双实现；停止/连接代次/存档数据安全通过；各模块的 T2、T3 有真实执行记录，未跑标为 NOT_RUN。

## 4. 并行施工计划

| 阶段 | 可并行任务 | 合并条件 |
|---|---|---|
| A | M0 基线；M1 协议；M2 Pathfinder 差异审查；M4/M5/M6 的纯算法与测试；M8 调研 | M0 固定 N03/G25 与关键领域场景；S1/S2/S3 的最小接口约定 |
| B | M1 实施、M2 实施（不同文件 owner）；M4 战术纯函数、M5 施工约束、M6 覆盖算法、M8 生产修复 | M1/M2 真服通过；M2 不依赖 M4/M5/M6 的内部状态 |
| C | M3 移动执行；M4/M5/M6 领域接入；M8 | M3 停止/授权/运动场景通过后接入；领域 PR 可各自合并 |
| D | M7 生存、M9 Agent 接口、M10 清理 | 相关领域语义稳定，所有长跑验收有复现实验记录 |

**并行规则**：每个 Agent 使用独立 Git Worktree；PR 只更改归属文件；跨域文件由 owner 统一集成。避免两个 AI 分别创造相近抽象后试图“合并”；先写一个简短提案说明消费者、接口与时序。领域工作不必等待 M2 所有优化完成才能开展纯算法和测试。

## 5. 迁移规则

- **原 API 原地改算法优先**：`goto@1`、`route.plan@1`、`fight@1`、`build@1`、`explore@1` 的行为能力增强，不改变合理的结果语义。
- **兼容破坏另行评审**：如果输入输出 shape、error 约定或完成语义影响已运行 Program，要检查真实消费者、更新 `modules/capabilities.md` 和相应主版本。不能仅为纠正 bug 引入 3 套平行的 API。
- **无需用户迁移的实现删除**：内部旧循环和固定算法，在替代实现经测试通过后一次性删除；测试不依赖已失效私有细节。
- **持久数据慎改**：不修改 Library/World/Runtime 数据模式，除非有跨 Run 真实需求；修改时必须提供旧数据读取/明确迁移方案及回退边界。
- **完成分两层**：单工作包完成不等于自主游玩完成；T2 真服及 T3 真实模型成果都要记录。算法收益不足时回退到更简单的方案。
