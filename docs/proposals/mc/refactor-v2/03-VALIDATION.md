# 验收设计：真实游戏结果优先

> 本文是场景/证据规范，不是“全部已测试”的报告。改造前冻结实际服务器版本、代码 SHA、地图和初始物品。现有 Uina 目标版本为 Java 1.21.11；Cortico 默认示例版本不同，跨仓直接测量需显式对齐版本和游戏规则。

## 1. 验证层级

| 层级 | 测什么 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| T0 | 类型、单测、纯策略、属性规则 | 算法分支和数据结构正确 | 真实游戏能走/能打/能建 |
| T1 | FakeBot、协议乱序、物理模拟、取消集成 | 控制时序和协议边界 | 服务端会接受所有行动 |
| T2 | 本地真实原版服务器，固定场景 | 特定版本、地图、装备下真实完成 | 所有地图和随机战斗都稳定 |
| T3 | 真实 LLM/Program，自主完成目标 | 实际端到端自主能力、Token 和恢复表现 | 单次成功即具有统计保证 |

禁止将 T0/T1 的通过写成 T2 已验证，也不要把历史文档中“某轮 PASS”归因于本次新算法。

## 2. 优先建立的固定场景

| ID | 场景 | 主要验收事实 |
|---|---|---|
| N01 | 平地 30 格 | 达到目标/可站，平地不退化 |
| N02 | 单台阶、三级台阶、上行走廊 | 重新确认 G21/G24 旧成果；不会贴墙原地跳 |
| N03 | G25 山地一格侧隙绕柱 | 解决或确定根因；路径只读结果与实际动作条件一致 |
| N04 | 木门、栅栏门、门框斜穿 | 合法路线、正确开门、不误挖 |
| N05 | 深水上岸、悬空搭桥、无支撑垫塔 | 不生成物理无法执行的放置；有条件时真正通过 |
| N06 | 同一放置目标被服务端拒绝 | 不无限重发；条件变化后可重新尝试 |
| N07 | 未加载 Chunk、缺材料、保护区 | 已知/未知与允许/不允许区分；不会误改世界 |
| B01 | 近战单僵尸、带盾 | 击杀事实、攻击冷却、伤害变化可观察 |
| B02 | 多个近战怪围攻 | 存活率、受伤、目标切换和空间选择 |
| B03 | 近战 + 骷髅 | 处理远程威胁；不会只盯最近近战怪 |
| B04 | 苦力怕 + 地形危险 | 识别爆炸距离和退避可行性，不退入悬崖 |
| B05 | 逃跑失败/敌人短暂失踪 | **不允许假 `retreated`**；结束原因匹配真实事实 |
| B06 | 战斗时 stop/安全抢占 | 不遗留旧输入，也不干扰新身体主人 |
| C01 | 5×5×4 小屋 | 完成格和方块状态回读；不能把自己封在无法继续的位置 |
| C02 | 多层建筑/火把/门/床/农田 | 多格主从、朝向、支撑、可达站位正确 |
| C03 | 材料不足与现场冲突 | strict 不动工；显式 progressive 如实现则只做合法部分并报 remaining |
| C04 | 施工 stop、断线、重开、临时脚手架 | 不误拆他人方块；恢复按现场核对；临时结构残留如实报告 |
| E01 | 回环、四岔路、死路 | 相同预算比四向算法有更好有效覆盖，不能单路失败宣告无路 |
| E02 | 垂直洞穴与未加载区域 | 不漏 3D 通路，不把 unknown 说成不存在 |
| P01 | 合成/窗口迟到/满包 | 物品真实净增、窗口状态不串扰 |
| P02 | 熔炼 wait true/false | 世界侧进程正确、等待不无意义长期占 Body |
| S01 | 岩浆/溺水/连续受伤 | 合理抢占、确认安全、恢复正常控制 |
| S02 | companion 进程异常/OwnerLost | 不重复不确定副作用，能够显式恢复 |
| U01 | “探索洞穴并采集铁” | 程序组合、覆盖、物品净增、Token/重试次数 |
| U02 | “盖一栋小屋” | 蓝图、材料、施工、现场完整性、进度恢复 |
| U03 | “在生存环境准备装备并持续活动” | 30 分钟以上持续记录真实进展、死亡与恢复 |

**注意测试非独立**：在同一场景重新规划 5 次不能当作 5 次成功样本。所有回归均记录世界初始化和测试独立性；怪物随机行为按多个独立 Episode 统计。对照 Cortico 时除协议/方块版本外，还需对齐装备、难度、服务端配置、任务目标，无法对齐则仅作为技术参考。

## 3. 指标与报告

- 导航：实际到达率、p50/p95 耗时、停滞时长、重新规划次数、客户端/服务端位置差、无效放置次数。
- 战斗：生存率、每场承伤、击杀耗时、有效攻击比例、撤退的真实成功率及误报次数。
- 施工：目标方块完成比例、路径/站位次数、材料损失、临时块残留、恢复后重复副作用。
- 探索：新增已确认覆盖、已走路径重复距离、未访问 Frontier 数、错误“无可达/未找到”次数。
- 自主性：真实目标完成数、模型调用/Token、人工干预、卡死或无进展时间、断线后恢复结果。

最低 Episode 字段：`scenario/git_sha/minecraft_version/world_fixture/initial_state/variant/start/end/terminal_game_fact/result/error/replans/unnecessary_changes/metrics/log_ref`。缺失值写 `null/NOT_MEASURED`，**不能用 0 代替没采集**。

对每个值得改进的算法，比较：

1. Uina 基线；
2. 从 Cortico 抽取的可复现算法基线（如果适用）；
3. 自己的改良算法。

新算法只有在正确性无回归且真实指标改善时才进入主线；否则选更简单实现。随机场景记录样本量和分布，勿使用单次表现外推普遍最优。

## 4. 运行命令（已在基线 package.json 验证存在）

```bash
pnpm test
pnpm typecheck
pnpm build
pnpm dev:mc:climb
pnpm dev:mc:terrain-nav
pnpm dev:mc:combat
pnpm dev:mc:build
pnpm dev:mc:repair
pnpm dev:mc:production-repair
pnpm dev:mc:i2
```

上述真服命令依赖测试服务端和环境准备，不表示可以在任意机器直接运行。实现 Agent 应查看每个脚本的参数/副作用，选择相关场景，不要求每次 PR 都全量跑完所有真服脚本；发布候选版本与 M10 必须覆盖所有受影响场景。

## 5. 合并门禁

**必须成立**：

- 新改动 T0/T1 通过；涉及真实物理/生存/施工效果必须有对应 T2 证据或明确标记未完成，不许宣告模块最终验收。
- 停止/重连/代次切换后无旧动作写入；同一时刻没有两个身体控制源。
- 实际未完成不得返回领域成功；未知/失联/未加载不会被转换成确定成功。
- 关键旧场景无功能性回归；新 API 如改变行为/值，真实消费者已迁移并有测试。
- 删除被替代旧逻辑和重复配置，或者明确说明尚不能删除的依赖，不能永久保留暗中启用的双轨版本。
- 文档只维护当前权威版本，不另起一套与项目 `docs/proposals/mc/` 对立的“永久真理”。

**可量化的产品阈值**：第一轮 M0 基线跑完之后，由开发负责人按样本/地图/环境冻结数字。对于确定性场景可要求稳定复现并全部通过；对于随机战斗只给出数据和置信区间，不预设无依据的“成功率 99%”。

## 6. 独立审查要问的八个问题

1. 修改前的坏行为能否重现？不修改代码仅改变环境是否也可修复？
2. 新方案比最小修复多出来的复杂度是否有实测收益？
3. 是否引入了第二份状态真源、Body 仲裁或隐藏后台任务？
4. 规划规则和实际执行规则是否一致？未知是否如实？
5. 是否有 catch 后吞错、无进展循环、伪成功或无条件重复发包？
6. 取消、断线、维度/连接代次变化后是否仍安全？
7. Cortico 的代码/常量与 Uina 版本是否兼容，许可证是否满足？
8. 移植后旧实现删干净了吗？没有实测的能力是否被误称“完成”？
