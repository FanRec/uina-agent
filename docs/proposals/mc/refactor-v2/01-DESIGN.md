> 状态：批次 A（导航）与批次 B（战斗/施工/探索）已于批26–33 实施并真服验证（进度唯一真源 development-plan.md §10.3）；批次 C（M7/M8/M9/M10）未开工。日期：2026-11-06（批34 状态更新）。  
> 审查基线：Uina `a0c9a5963cb8`；Cortico `c376b91c1ebb`。实施前应重新核对目标分支；若源码已有变化，以最新事实为准。  
> 范围仅限 MC World。本文给出**目标、职责和约束**；算法内部的最佳实现允许开发 Agent 在测试支持下调整。

## 1. 目标和取舍

产品目标：用户给出 Minecraft 目标后，Uina 能够在普通 Java 生存世界中持续做出有效行动；碰到复杂地形、战斗、建造和资源约束时，优先自己在能力内部解决局部问题，需要更高层取舍时才交给 Program/LLM。

| 体验 | 成功应如何体现 | 不接受的“伪成功” |
|---|---|---|
| 走到指定地点 | 实际到达、位置和安全站立条件满足 | `route.plan` 可达却一直原地空转；只结束超时就算修好 |
| 与怪物战斗 | 合理选武器/走位、击杀或确实脱险 | 挥刀已发送就算命中；试图逃跑就报告 `retreated` |
| 完成建筑 | 目标方块及必要状态经现场核对；临时材料有归宿 | 循环走完就算完工；未加载区域当作空地 |
| 探索洞穴 | 合理覆盖可达的未知区域；减少重复搜索 | 四个方向用尽就宣称所有空间已探索 |
| 长时间自主游戏 | 可以组合任务、处理局部变化、保留真实进度 | 每一个动作都等待 LLM；断线后重复不确定副作用 |

优先级：**正确性和控制安全 > 真实任务成功率 > 延迟/材料/Token 效率 > 代码规模**。同时反对为了“安全”牺牲所有可用性：拒绝动作要有真实依据，失败后应能改变策略，严格模式与渐进模式应可区分。

明确不做：重建通用 Runtime、MC 独立 Agent Loop、第二套队列/租约/库/记忆、重写整个 Mineflayer、一次性兼容所有 MC 版本与模组、提前引入 HTN/全局 MPC/强化学习、为所有边界情况创建永久抽象。

## 2. 现有架构必须保持的边界

```text
LLM / Agent                  目标、价值判断、授权、策略转向
      |
Program / Library            长任务的组合、资产复用、决策检查点
      |
Runtime                      Run/Segment/Call/Effect、受理、控制归属、取消、持久记录
      |
Capability (MC)              导航目标/战斗/施工/探索/采集/生产的领域执行策略
      |                        ↑                 ↑
      |                     World.read       Driver feedback（受授权）
      |
Driver                       Mineflayer、协议、物理、身体控制、窗口、当前事实
      |
Minecraft server             实际游戏状态与服务端确认
```

**职责与依赖规则**：

| 所有者 | 负责 | 不负责 |
|---|---|---|
| Driver | Bot 生命周期、协议和物理适配、当前事实采样、动作派发、底层执行证据、唯一写入资格 | 长期目标、技能策略、施工进度或地图历史 |
| World | 可观察游戏事实、覆盖/来源、领域记录和历史；已有查询/Watch | 直接控制 Bot；复制一份“玩家真实位置” |
| MC Capability | 本地领域决策、行动序列、完成条件和失败解释 | 自建 Run 调度/Body 租约/数据库 |
| Runtime | 调度和授权、取消/停止、Effect、恢复边界 | 判定怪物该怎么打、哪块砖该先放 |
| Program | 任务流程、条件分支、资源与目标取舍 | 每 Tick 运动控制；复制底层领域算法 |
| Library | 程序、蓝图、经验资产 | 执行游戏操作 |

保持现有 `contracts/body.ts` 的 `ControlInput`、`FeedbackStream`，`driver/control-arbiter.ts` 的 Body/Goto 单写源语义，`runtime/engine.ts` 的 Call/Effect；新算法首先作为**私有函数/模块**加入相应 Capability 或 Driver，不从开发工作包反推出一套新公共 SDK。

三种节奏：LLM/Program 事件驱动；领域决策在必要的数 Tick/数秒上更新；连续运动随物理 Tick 更新。控制频率不等于 IPC/持久化频率。**普通运动 Tick 不创建持久 Call。**

### 2.1 四个必须成立的生命周期约束

1. 当前客户端最多一个有效身体写入者；领域能力只能通过当前授权通道操作。
2. 取消/停止/安全抢占后，旧操作及迟到回调不得写入或清理新操作的控制状态。
3. `plan` 完全只读；`execute` 在派发前基于最新事实检查，计划不是执行承诺。
4. 观察、预测、未知、历史各自保持来源；外部世界是否成功必须靠相应游戏事实验证。

已有约束按现有 Runtime/Driver 实施，不为其新建并行控制层。

## 3. 导航设计：一套物理规则，计划和执行共用

### 3.1 目标行为

- 平地、台阶、门、坡地、窄通道、浅/深水、挖路、搭桥、垫塔尽量成功；物理上不可能或不允许的路线不要宣称可达。
- 若路径失败，识别 `规划无路/目标已变/物理动作失败/服务端拒绝/控制中断/超时`，在条件未改变时不重复同一个无效动作。
- 保留 `goto@1`、`route.plan@1`，除非确实需要兼容性变更；当前默认 `placeToReach=true` 不可在重构中悄悄修改，应先评估是否符合游戏策略需求。

### 3.2 子职责和代码归属

| 层 | 主要位置 | 设计职责 |
|---|---|---|
| 协议与状态正确性 | `driver/mineflayer/protocol.ts`、`driver/window/`、`driver/body/` | 服务端状态确认、窗口同步、放置/挖掘物理事实；不修改路径权重 |
| 路径搜索 | `driver/mineflayer/pathfinder.ts` 及受控补丁 | 构造相同 Movements 规则、搜索、代价、合法性与只读试算 |
| 路径执行 | `driver/goto.ts`、`driver/input/walking.ts` | 跟随路线、局部位置控制、进展检测、纠偏、结算 |
| 调用层 | `capabilities/actions/navigation.ts`、`queries/route-plan.ts` | 对外参数、失败映射和目标语义；不实现第二份 Pathfinder |

允许共享一份内部“导航选项→Movements 配置”的函数，但**不要求创建公开 `Navigator` 接口或新的 manager**。现有 `planPath` 和 `configureMovements/gotoNear` 必须先清点行为差异，再决定最小改法。GoalNear 容差、是否挖路、放路、冲刺、跑酷和版本支持一致；规划使用独立、只读的状态，不能改活动目标。

### 3.3 动作合法性与失败反馈

**规划阶段**：动作产生前先核验方块碰撞和支撑、门状态、液体条件、Chunk 是否有足够信息、材料是否可用、任务允许不允许修改环境。硬约束不可用“高惩罚”代替；合法候选再以移动时间、挖掘、放置、风险作近似成本比较。只添加有真实消费者的策略项。

**执行阶段**：每个重要行动都采集：目标位置/动作、实际状态、成功证据或受阻原因。执行失败首先观察环境是否变了；如果同一动作在同一世界条件下被服务端明确拒绝，短期避开该动作；方块变化、重新连接/维度变化或环境差异后允许重试。

失败缓存只作用于有限区域/当前会话，存储**失败边或具体放置目标与环境条件**，不永久屏蔽“向东走”或某个方块类型。与 M1 的放置确认数据对接。未知 Chunk 不等于空气，也不默认等于永久不可达。

**诊断优先级**：先定位 G25（`route.plan` 5 步、`goto` 在山地窄缝零推进），确定原因后修复。不能用更大的 `timeout` 作为解决方案。现有 G21/G24 成功路径属于必须保留的回归项。

### 3.4 局部运动控制

默认继续复用 Pathfinder 执行器；对实际失败场景依次使用：原执行器修复 → 小型步态/跳跃控制 → 必要时有限候选短时物理模拟。预测控制不是预设答案。

候选短时预测可比较“继续前进/调整朝向/提前跳/后退助跑”等数种输入，选择可跨过障碍且碰撞/坠落风险小的动作；每 Tick 根据真实位置重新评估。先测 Physics 预测误差和 CPU 开销，再决定是否进入主线。不要引入独立的路径搜索引擎来解决一个控制阶段问题。

**验收**：计划可达且物理允许的动作，在重复真服测试中实际完成；无法完成时准确说明原因；路径/动作失败不会长时间静默；不引入停止/取消回归。

### 3.5 Cortico 参考

- [`pathfinder-perf.ts`](https://github.com/Pal-AI-Lab/Cortico/blob/main/src/worlds/minecraft/pathfinder-perf.ts)：搜索内方块缓存、stateId 表、门/水/搭桥/禁放区/失败放置过滤。吸收算法和测试案例，不照搬整体 `prototype` 覆写。
- [`mineflayer-fixes.ts`](https://github.com/Pal-AI-Lab/Cortico/blob/main/src/worlds/minecraft/mineflayer-fixes.ts)：挖掘/放置服务端确认和控制修复。
- [`bridge.ts`](https://github.com/Pal-AI-Lab/Cortico/blob/main/src/worlds/minecraft/bridge.ts)、[`travel.ts`](https://github.com/Pal-AI-Lab/Cortico/blob/main/src/worlds/minecraft/travel.ts)：不同寻路配置的只读探测及执行方式。

## 4. 战斗设计：连续控制 + 可核验的结算

### 4.1 目标与内部结构

保留 `attack@1` 的一次攻击语义与 `fight@1` 的战斗会话语义。将当前 `fight@1` 的“扫描→追击→等待攻击→再扫描”重构成三个协作部分：

| 部分 | 职责 | 执行位置 |
|---|---|---|
| 战况观测 | 当前位置速度、敌人实体及代次、受伤来源、武器/盾、地形、伤害事件 | Driver/World 现有事实接口 |
| 纯战术决策 | 目标选择、走位方向、攻击窗口、撤退/接近/结束判断 | `capabilities` 内私有纯函数 |
| 战斗会话驱动 | Body 独占、控制输入、移动交接、Effect/击杀观察、终态 | `actions/combat.ts` 或私有协调函数 |

先用 Cortico 的 16 槽 Context Steering 建立可测试基线：interest/danger、危险硬遮罩、方向平滑、迟滞与插值。添加站立可行性、悬崖/液体判断、威胁位置及近战距离；根据当前目标做少量目标粘性，避免每拍换怪。

战斗动作需要协同攻击冷却、视线/距离、盾牌、近远程武器、苦力怕引信和远程投射物。**不在第一轮穷举所有怪物专属规则**；先覆盖固定测试中的高频威胁。基于实体真实 AABB 判断距离，不把实体中心当作攻击范围。

### 4.2 关键时序

```text
进入 fight → 获取局部战况 → 本地 Body/Feedback 连续控制
                        ↓
                需要绕远路/重新接敌？
                        ↓ yes
                释放本地 Body → Runtime.navigate / Goto → 重新取得 Body
                        ↓
             命中/死亡证据异步观察；必要时即时校验血量
                        ↓
             目标清除 / 确认安全撤离 / 目标丢失 / 到期 / 中断
```

同一时刻禁止本地 Body 控制与 Pathfinder Goto 双写；安全反射抢占按现有机制退役控制。攻击证据观察与控制循环分离：不能因一次 `awaitEvidence(600ms)` 或射击确认而冻结躲避。如何在现有 `FeedbackStream` 中处理攻击输入与证据归属由实现 Agent 选择，但每次攻击的 Effect/服务端事实归属不能丢失。

**撤退成功**：需要实际远离活跃威胁，并经过短暂的稳定观察；只是调用 `withdraw` 或朝远处走了几格不是成功。撤退失败应明确失败；保留原有合法 `retreated` 输出的同时，不让它表示未完成的撤离。若确实需要新增结果枚举，先审查已有调用方并按契约版本规则迁移。

**卡住**：近战连续无法接近/击中时，先检测目标是否移动、是否被墙阻挡；本地走位无解交给全局 Pathfinder。不能只靠固定“8 秒没接近就退出”，也不要无限追逐不可到达的目标。

### 4.3 进一步研究（可选）

Context Steering 是初始基线。仅在有收益的情况下引入短时位置/攻击预测：尝试少量方向+冲刺/跳跃组合，计算预测碰撞、预期承伤和攻击机会。避免为了实现“智能战斗”预先建立训练系统、大型效用树或通用模型预测框架。

### 4.4 Cortico 参考

- [`combat-context.ts`](https://github.com/Pal-AI-Lab/Cortico/blob/main/src/worlds/minecraft/combat-context.ts)：16 槽方向评分，适合抽取为纯算法。
- [`combat.ts`](https://github.com/Pal-AI-Lab/Cortico/blob/main/src/worlds/minecraft/combat.ts)、[`melee.ts`](https://github.com/Pal-AI-Lab/Cortico/blob/main/src/worlds/minecraft/melee.ts)、[`ranged.ts`](https://github.com/Pal-AI-Lab/Cortico/blob/main/src/worlds/minecraft/ranged.ts)：目标粘性、冷却、距离控制、撤退、武器切换；吸收经过场景测试的策略，阈值需在 Uina 目标版本重新校准。
- [`policy.ts`](https://github.com/Pal-AI-Lab/Cortico/blob/main/src/worlds/minecraft/policy.ts)：可参考自主交战条件，但不移植另一套全局持久 Policy。

## 5. 施工设计：目标差异 + 可行操作 + 站位调度

### 5.1 保留哪些东西

保留 Uina 的 `ConstructionTargetCell`/`build.plan@1`/`build@1`、`construction` 目标转换、Library 的蓝图与 digest、世界核验和部分完成报告。不要导入 Cortico 的蓝图保存/目标工具或另一套 DSL。结构形状仍由 Program/蓝图数据定义，Capability 负责执行。

### 5.2 算法流程

1. **规范化目标**：读取 blueprint/cells 与明确 `airPolicy`，保留 `set/clear/preserve/unknown`；身份与版本固定。
2. **现场 Diff**：用当前已加载事实判定需拆/需放/已完成/未知；支撑与材料不足分别说明。
3. **生成必要的施工操作**：考虑主从方块、属性/朝向、物理支撑、重力块、门/火把/床/种植/液源等实际消费者；只构建真实依赖，不全格套通用 DAG 框架。
4. **选可执行的 Ready 集**：满足支撑、材料和允许修改条件的操作进入候选；不可满足的明确受阻原因。
5. **选择站位并批处理**：合法站位先过可站立、射程、视线/附着面、路径试算；优先在同一位置完成可触达的多个方块；第一候选失败不能直接放弃其他所有候选。
6. **必要时临时施工**：可选搭脚手架、保留通道和临时入口；登记“由本次施工新放置”的临时材料，清理前核验，不能误拆原有玩家作品。
7. **反馈调度**：每轮执行后更新目标格差异及依赖；新的可执行操作进入 Ready 集；当没有新进展/预算耗尽/材料不足时停止，不凭固定 N 遍认为任务完成。
8. **结算**：实际 `placed/cleared/skipped/remaining`，逐格回读目标，临时材料残留单独报告。

可先仅为方块类别建立少量“放置方法 + 支撑条件”规则，用实际覆盖的复杂建筑逐步增加。不要复制 Cortico 的全部状态注册表而不验证版本差异。

### 5.3 执行语义与约束

- 当前 `build` 缺材料或冲突时全部拒绝，是合理的严格模式。要支持“先做能做的部分”，必须让调用者**显式**选择渐进模式；若改变对外 schema/结果，按版本约定处理。不把部分施工冒充成功。
- `MAX_PLAN_TARGETS=2048` 属于单次计划/返回规模上限，不应无缘无故变成不可建大型项目的产品上限；先用有限批次/切片组合，只有真实消费者需要时调整接口。
- 施工默认不能自动拿非授权的珍贵材料，也不能借 Pathfinder 破坏其他建筑。保护条件应由当前施工上下文传给共享导航规则，而不是施工内部 monkey-patch。
- 恢复依据现场实际结果，而不是一个自说自话的持久游标。上次发包但没确认的动作可能已完成，先读再决定是否重做。

### 5.4 Cortico 参考

- [`blueprint-plan.ts`](https://github.com/Pal-AI-Lab/Cortico/blob/main/src/worlds/minecraft/blueprint-plan.ts)：主从部件、层内合并、施工 IR、依赖/现场核验。
- [`blueprint-registry.ts`](https://github.com/Pal-AI-Lab/Cortico/blob/main/src/worlds/minecraft/blueprint-registry.ts)：状态及放置规则，按当前版本筛选移植。

## 6. 探索设计：Frontier，但不创建另一套全世界数据库

当前 Uina 的 `ExploreCursor` 用四向选择及 `visited/dead`，方向上的一次 `UNREACHABLE` 会影响该次探索后续候选。这不是可信的空间覆盖算法。

### 6.1 最小可行实现

- **观察地图**：从 `region/terrain/entities` 等既有查询构造稀疏的“已看到通路/未知边缘/阻挡/危险”，以 `world/worldRevision/dimension` 分区；未加载与未观察保留 `unknown`。先将覆盖记忆限制在当前探索活动；若需要跨 Run 复用，复用 World 领域记录，不建第二个持久库。
- **前沿提取**：选择已知可达区域与未知区域的交界；区分 3D 洞穴高低连接，不强制为所有区块保存完整体素。
- **目标评分**：近似的信息增益 − 行走代价 − 危险 − 重复；有限候选调用现有只读 `route.plan` 估价，不通过规划器执行动作。
- **走到前沿并观察**：根据新观察更新区域图；障碍或路径失败只标记具体目标/边在当前条件下不可用，不封死整个方向。
- **停止条件**：目标确实被观察到；在给定预算/当前已知覆盖下无继续可达前沿；中断/危险。不得声称未加载世界“没有矿”或“探索完毕”。

目标导向可增加矿物高度、洞穴、地表生物群系等简单先验，但它们只是搜索优先级，不是被确认存在的资源坐标。真实完成条件仍依目标 `until` 的事实匹配。

### 6.2 进一步改善（不是第一轮必做）

探索前沿间的短路、区域分层、保存已探索洞穴图、针对指定目标的经验先验。是否引入 SLAM/Octree/概率地图，由真实探索规模和资源需求决定，默认不做。

## 7. 生存、生产和持续任务

**生存**：优先保留现有 `capabilities/survival.ts` 的岩浆/溺水/低血量抢占。结合战斗控制器补充有根据的威胁判断，区分“自动防卫/被攻击的反射”与“主动搜怪打怪”；后者必须尊重任务意图。自保完成以危险解除或稳定安全状态验证；不能因此再建全局状态机或租约系统。

**任务维持**：补光、临时垫脚、必要进食应优先作为采集/隧道/施工等能力局部执行选项，仅在有真实调用需求时形成可复用的共享函数。不要让世界范围内的全局 Upkeep 无限抢占任务。

**生产**：现有 `smelt@1` 支持 `wait`，保留；对照 Cortico 审查窗口同步、容器操作、合成回读、工具选择、材料和背包限制。底层窗口状态由 Driver 唯一持有，生产能力不得复制 Window Session 状态机。

**长期自主**：任务顺序、目标再选择、跨场景策略由 Program/Agent 管。领域能力提供足够进度和失败信息，让 Program 自主决定接着做、换方案、请示或放弃；不复制 Cortico `mc_do/mc_goal` 框架。

## 8. 跨模块接缝：先复用，必要时才加接口

| 接缝 | 输入/输出语义 | 负责人 | 备注 |
|---|---|---|---|
| M1 → M2/M3 | 服务端放置/挖掘拒绝、碰撞/物理状态证据 | M1 | 首先复用现有 Driver 结果；仅有具体消费者时增加私有失败事实 |
| M2 ↔ M3 | 同一 Movements 配置、路径候选和失败分类 | M2 搜索 / M3 执行 | `route.plan` 只读；`goto` 保持授权与完成判据 |
| M3 → M4/M5/M6 | 受控导航/运动原语、失败原因 | M3 | 领域模块不 import Mineflayer Bot |
| M4 ↔ M7 | 危险判断、撤退/自保控制权交接 | M4/M7 | 一个身体写入者；不建两套互抢的撤退控制 |
| M5 ↔ M2 | 工地保护、允许挖/放、材料限制、站位可达性 | M5 声明约束 / M2 应用 | 首先检查现有能力参数能否满足；不能才设计窄内部接口 |
| M6 ↔ World | 空间观察与可用历史 | M6 消费 / World 拥有 | 无第二份长期事实真源 |
| M8 ↔ M1 | 当前库存、窗口快照、物品操作回执 | M1 拥有 Driver / M8 消费 | 生产只解释领域目标 |

接口调整原则：先复用 `CapabilityDeps`、`BodyCallScope`、`FeedbackStream`、`World.read`、`GotoDirector`；如果新需求必须跨越边界，提供具体调用场景、旧接口缺口、最小新增类型及测试，再修改对应权威文档。**不要为了并行开发提前创建统一万能 `ActionContext`/`StrategyRegistry`。**

## 9. 失败策略与完整性

| 情形 | 应采取的措施 | 不要这样做 |
|---|---|---|
| 请求未发送 | 改输入或重新选择动作 | 当成已完成 |
| 已发送、结果未确认 | 优先复查现场；必要时重新尝试幂等目标 | 立即重发可能重复消耗的动作 |
| 规划无路 | 检查目标/材料/硬约束/覆盖，或更换路线 | 仅提高时间上限 |
| 服务器连续拒绝同一动作 | 记录失败条件，避让或停止等待条件变化 | 无限重复相同动作 |
| 物理卡住 | 局部纠偏、短距离重试，必要时重规划；耗尽预算如实失败 | 多层随意偏角重试叠加到无法解释 |
| 缺材料 | 明确缺口；由 Program 决定补料或显式渐进施工 | 私自从玩家箱子取料 |
| 退出/抢占/断线 | 保证无旧控制继续写；根据现场和 Effect 复核恢复 | 自行恢复旧授权，自动重复未知动作 |

重试原则：**仅在新观察或新动作条件可能改变结局时重试**。阈值应可从游戏 Tick/网络/服务器测量得到；没有明确证据的超时兜底应优先删除或限定在异常边界。

## 10. 演进纪律

- 首先证明 Cortico 的实现解决的是 Uina 真正存在的缺口；已实现且质量不低的部分保持，不要“迁移覆盖”。
- 尽量在内部替换算法，公开能力名字、值和版本不变；确实不兼容才按 `@major` 合同迁移。修改 `fight.ended` 等结果前先查实际 Program 消费者。
- 新方案移植成功后删除被替代的旧搜索、战斗和固定重试逻辑；不保留 `legacy/new/v2` 长期双轨。暂时的 A/B 对照只留在测试工作分支。
- 若架构简化与现有停止/恢复不变量冲突，以真实控制安全为准；若复杂设计没有实际消费者，优先不实现。
- 采用 MIT 来源代码时履行许可证要求，保留原版权声明和必要归属；不要把旧版本专用补丁误认为新版本正确。

## 11. 待研究的决策（让开发 Agent 用实证决定）

| 决策 | 默认倾向 | 开发 Agent 应给出的依据 |
|---|---|---|
| Pathfinder 补丁形式 | 小补丁优先；大量稳定修改考虑维护 Fork | 依赖版本、修改点、升级成本、回归覆盖 |
| 是否采用局部物理预测 | 先不强制引入 | 固定地形 A/B 成功率、耗时和每 Tick 开销 |
| Context Steering 的权重 | 以 Cortico 16 槽作起点 | 同装备同敌群的击杀/承伤/失败率 |
| 施工完整 DAG 或 Ready 集 | Ready 集 + 必要依赖先做 | 多层/多部件建筑的正确性和调度效率 |
| 是否持久化探索覆盖 | 首轮会话内轻量存储 | 需要跨 Run 复用的具体体验与数据量 |
| 渐进施工如何公开 | 原 `build` 严格语义先保留 | 用户/Program 消费需求、版本兼容成本 |
| 需要什么新跨模块 API | 默认沿用现有端口 | 实际消费者、无法实现的场景、最小接口示例 |

**成功标准**：用户任务完成表现提升，代码结构仍然清晰，长期自主运行不虚报、不死循环，且每项复杂度都有真实消费者和测试依据。详细开发顺序与验收见配套文档。
