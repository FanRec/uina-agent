# Minecraft 开发规范

日期：2026-10-25。适用于 Minecraft 重做及其必要的 Host/Session 接缝工作；后者同时遵守仓库根 AGENTS.md。施工顺序唯一见 [总规划 §10](development-plan.md#10-剩余施工总纲2026-10-25-重排)，行为合同见 [概要](design.md) 和所属模块。

这份规范统一必须相接的地方，保留算法与内部实现的判断空间。目标是把设计能力完整、可靠地做出来，并让后续能力能沿已有接缝继续生长。

## 1. 开始一个任务

先检查工作树，读概要及本任务涉及的合同，再沿实际调用链核实。研究到足以决定当前实现即可，不为“理解全项目”扫描无关模块，不把历史实现或实验报告当现行代码。

任务描述只需四项：**要交付的行为、已有依赖、修改归属、怎样确认完成**。不要求每个函数建任务、每个改动开长设计评审或先搭占位层。

有现成真环境时直接使用。尚缺环境时明确缺什么，先推进不依赖它的部分；不为了展示进度写一套以后必删的替代实现。

## 2. 简单与复用

| 选择 | 本项目做法 |
|---|---|
| 相同操作的不同方向/目标 | 优先同一接口配参数，如 transfer 的 from/to、chat 的普通消息/指令 |
| 实际不同的事实与生命周期 | 分清接口，如在线公告名单和跟踪实体、读历史和发消息；不为压低名字数量强塞成一个万能入口 |
| 顺序、循环、临时条件、几何生成 | 普通函数和 JS 组合，不再造步骤语言或条件 DSL |
| 稳定的公共工作 | 提炼到其所有者，所有调用者复用；不允许每个能力各做取消、重试、任务句柄和记录层 |
| 只有一次的简单工作 | 直接写；不要为“以后也许用”配接口、工厂、基类和 Registry |
| 已出现的相同变化压力或明确近期消费者 | 可以提前抽取共同机制，不必机械等复制三遍；说明它替谁省掉什么 |

可以先建设的小骨架已经有明确消费者：

- 一份能力/查询声明驱动参数校验、目录、示例和发现，避免分别维护多套目录。输入类型/schema 与实现相邻维护，不为强求零重复先造全局代码生成系统。
- Runtime 的调用上下文统一委托、取消、进度和效果归属；能力只写领域算法。
- Driver 的受控操作/版本 Adapter 统一真实写入与停止；算法可以是普通函数，客户端对象不逃逸。
- Library 的同一头解析/文件扫描供读取与发现复用；编译与源码追溯消费现有函数接缝。

这些骨架随首批真实调用做完整，不先开发一个可装任意世界的框架。无状态逻辑直接导出函数；有资源的模块才用 `createX(deps)` 或等效显式装配及 `close()`。不强制统一基类。

采用成熟代码前，只核实本次要用的算法、版本、依赖与退出行为。契约兼容就复用；缺少受控停止/写入归属时补窄 Adapter。只有证据表明适配比直接实现更复杂才替换，不因接口不顺手重写整套寻路或客户端。

## 3. 必须统一的实现约定

1. **一份权威。** 公共类型落一份源码，行为归所属模块；不得在消费者复制类型、库存、队列或第二份完成事实。具体路径见总规划。
2. **显式装配。** 依赖由模块入口传入。共同纯值不依赖 Bot/Host/UI；玩法不能 import 原始 Bot；进程监管只归 Executor。使用仓库现有边界检查补必要规则，不另造依赖框架。
3. **结果真实。** 沿用 succeeded/failed/cancelled/unknown/not_started。接受、派发和达成目标分开；目标不足保留进度和剩余，未知不能算成功或安全重试。
4. **取消有归属。** 工具等待取消不等于停止 Run；调用、身体、窗口、guest 和进程各关闭自己的资源。晚回调不得恢复资格，清理/未知副作用也进原记录。
5. **策略有来源。** 参数、默认值和版本在规定边界固定并记录；算法可按世界重规划。内部时限/阈值只在需要测量的地方集中定义，不堆用户配置、隐藏 policy 或自动重试。
6. **类型与校验各就其位。** 严格 TypeScript；JSON/IPC/文件/协议入口核验一次，内部使用已明确的类型。真实异步边界仍核验存活/资格；不在每层重新校验同一业务对象，也不用 any 或吞错绕过未设计的合同。
7. **构建真实接线。** 新文件随所属功能进入类型检查和构建，Worker/WASM/native 路径用真实入口验证；禁止测试替身、缺资产回退或过期文件兜底掩盖交付问题。

## 4. 开发与并行协作

先确定共享输入/返回、错误、所有权和关闭方式，再分模块写实现；模块内部可边写边改。只有直接调用者需要知道的东西才进入公共合同。

同一个公共文件或协议由一个整合者负责。其他开发者提交明确的改动需求，不在各自分支复制一套接口。提供方改接口时同步直接消费者、声明和示例；未接上的接口不能宣布可用。

并行分支/worktree 从同一已整合基线开始。未提交的设计和删除不会自动复制过去；不能一方照旧实现、一方照新文档开发。建立共同基线时只提交已授权范围，不把用户其他脏文件一起带入。

按完整行为提交可审阅的一批改动：实际实现、接线、必要回归与文档一起完成。不规定每个小步骤都提交；提交权限和范围仍按当前任务约定，保留无关工作树修改。

允许沿任务推进局部重构：把共同行为收敛、删无效层、修清所有权和文件归属。内部改进在授权范围内直接做；跨模块行为变化先更新有关合同并通知消费者；涉及目标/持久格式/外部行为的重大改变说明依据与迁移影响。只有超出授权范围或涉及不可逆真实数据操作时再询问，不把每个设计调整升级成审批流程。

遇到设计与实测冲突，应写清“哪个场景不成立、应改哪个合同、影响谁”，修正后继续。不要为了证明文档正确堆适配或保留两套现行实现。已解决的问题就删除临时支路；真正需要长期存在的机制按正式代码维护。

## 5. 验证选择

先问这次要证明什么，再选能证明它的最短路径。下表是选法，不是每个功能都要跑完的层级清单。

| 要证明什么 | 优先验证方式 |
|---|---|
| 几何、差异、数量、选择、编码/头解析 | 小范围确定性测试，输入真实数据形状；不启动游戏证明纯计算 |
| QuickJS 语义、编译、隔离、取消、JSON 桥 | 真实 QuickJS/Worker 和正式桥；无需假装整个 Minecraft 存在 |
| 文件并发、数据库提交/恢复 | 真实临时文件/SQLite；需要重启就真的关闭重开或中断进程 |
| 进程树、Job、线程退役 | 真实 Node/Windows 进程；kill/IPC 断开不能被 mock 返回值证明 |
| 游戏动作、掉落、窗口、朝向、地图、战斗 | 支持版本的真实服务端，观察实际世界和协议证据 |
| 工具/回执/会话竞态 | 真实 Host/Subject/SessionStore 路径；用受控输入安排有关竞争，不要求真实模型替磁盘作证 |
| 模型能否学会、发现、纠错和复用 | 真实模型和真实任务；字段齐全、固定模型输出都不能证明体验 |

**不要求先 fake 再真实。** 不为每条能力新建 FakeBot/FakeWorld 或“两套同场景验收”。测试替身只用于真实环境难以稳定制造的窄边界，或隔离明确外部成本；优先复用现有夹具，只替换该边界，放在测试侧。它不成为生产目录中的 testMode、宽松授权、空 sink、内存数据库回退或第二套玩法。

模块文档中的验收场景是风险清单；凡只规定场景而没有特殊证据要求的，按本节选择环境。不再统一要求每个成功/失败都用假依赖与真环境各跑一遍。真实环境不适合稳定构造的取消/乱序/极端故障，可以在已有接缝注入，并明确结论只覆盖该边界。

回归测试优先保留：真实修过的缺陷、关键计数/语义、停止/幂等/权限竞争、持久恢复，以及未来改动容易无声破坏的公共合同。不为低影响文案、简单转发或复述实现写测试；不规定所有任务都先写失败测试，也不以覆盖率或测试数量作交付目标。

### 避免重复验证

- 工作中运行受本次变更影响的最小检查；接线批次统一跑类型/边界，涉及发包/协议则跑对应真服场景。
- 同一结果已经通过且源码、依赖和环境未变，后续里程碑引用它，不因为换了阶段名称再跑。
- 新变化、新失败或未解决疑点才扩大范围；不要对无关模块反复跑全量，也不要跳过确实受影响的消费者。
- 关闭完整集成批次时运行仓库 `pnpm typecheck`、相关回归；跨 Core/Host/Session 的改动再完成受影响全量测试，发布前验证 `pnpm build` 和真正的产物入口。已有无关失败单列，不靠删用例或屏蔽错误制造全绿。

验证记录只需：提交/工作树归属、实际命令、环境/版本、观察到的结果及边界。可复位真服用场景脚本准备和实际结果断言；手工观察要如实标明。不要在每条开发日志复制完整验收报告。

## 6. 数据与完成条件

使用独立开发世界、World 数据根和会话；可复位只指这些专用材料。不能清理真实 `.uina/world-data`、profile、认证或会话来让开发通过。专用验收环境可以准备场景；正常生存验收不能靠管理员补料或传送替代被测动作。

一次工作包完成应同时满足：

- 请求确实到达正式实现，所需依赖已接上；没有占位、无效声明或假成功。
- 本次承诺的正常、失败/部分量和停止边界能解释，实际所需验证已通过。
- 直接消费者、公开合同、示例与构建同步；留下的是可继续开发的代码。
- 报告清楚已实现/已验证/未验证，未完成事项指向具体依赖或任务。

未涉及的高级玩法可以到工作包开始时再详细设计。已承诺的能力不能凭“依赖不支持”改成永久占位；确需改变范围时显式提出裁决。完整交付以总规划的覆盖表与真实使用为准。

原生主脑接入、程序执行、文件复用与完整 I2 可以分阶段交付，但必须沿同一正式装配、记录和生命周期继续生长。每阶段声明真实支持范围，未交付方法明确失败；已要求的监管/持久回执不降级，损坏资产不伪装成可选模块。阶段完成不代表所属大模块或全部设计完成；模型校准须等本阶段正式入口可用。
