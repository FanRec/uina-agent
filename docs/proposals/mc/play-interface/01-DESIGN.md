# Minecraft 游玩接口设计

本提案定义改造后的目标行为。现行行为见 [公开接口](../public-api.md)。施工按 [重构路线](02-REFACTOR.md) 推进，完成以 [验收门槛](03-ACCEPTANCE.md) 为准。

## 产品目标

Uina 决定想玩什么。她可以把已经想清楚的事一次交给身体，在执行期间和人聊天，遇到会改变玩法的岔路再作决定。熟练的做法可以保存并在另一处现场复用。用户可以改变目标或停止当前任务，并得知已确认发生的事。

设计单位是一件有可解释完成条件的行动。插一支火把可以是完整行动。带着矿回到入口也可以。执行端处理能够从当前游戏事实和已选参数决定的步骤。更换目标、扩大施工范围、选择冒险还是撤退，留给玩家。

直播中，常规合成分成多个顶层任务，清格成功后角色仍留在井下，熔炼部分装料后模型从背包重新规划。相应设计分别是一次交出顺序、区分清格与通行的验收、把确认到的部分进度交给下一步。游玩接口消费已有观察、事件和 Rhythm，任务回执只交付本次行动带来的结果及接续所需的事实。入服和环境信息的交付由 [游玩信息交付计划](../play-context-refactor-plan.md) 定义。

## P1 · 一个目录和一套入口

| 入口 | 责任 |
|---|---|
| `session` | 连接、断开、查看当前与已知会话。 |
| `describe` | 发现行动、流程及精确合同。 |
| `observe` | 按需读取指定游戏事实。 |
| `run` | 提交行动、短序列或 Program。 |
| `tasks` | 查询、停止、续段和查证同一任务。 |
| `chat` | 游戏内说话，不取得移动或窗口的身体资格。 |
| `library` | 保存和管理可复用流程、经验和蓝图。 |

目录中的行动使用统一 selector。 `describe` 的浏览与 `query` 搜索默认返回常用视图，给出用途、关键默认行为、完成条件与可复制示例。加 `view: "all"` 可搜索完整目录，传入 `selector` 查看精确合同。常用视图推荐能够独立收尾、结果可解释的行动，包括适当的单步操作。发现顺序与运行权限分开。Program、专用玩法和显式 selector 都沿同一目录调用。

描述内容从注册合同及其示例生成。在线装配决定哪些能力可用。离线可以阅读已知合同与资料，并明确标示当前运行资格。查不到支持状态时保留未知。

给模型的用法只需三条。目标可由现成行动覆盖，就直接调用。顺序已知，就交一单 `steps`。要用现场结果改做法，再写 Program。接到后台受理后，下一次决定只依赖任务结果时交还当前回合。

## P2 · 三种提交共用一条任务生命周期

`run` 的 `params` 选择以下一种入口。三者使用现有调度合同，默认按正常队列受理。

| 入口形状 | 执行语义 |
|---|---|
| `{selector, input?}` | 调用一个能力或具名流程。 |
| `{steps:[{selector, input?}, ...]}` | 提交一组非空的固定顺序。每个 selector 和静态输入先解析、校验并绑定执行材料，再接单。每步执行前由其实现读取当前前提。 |
| `{code, input?}` | 提交一段受限 JS。用已有 Program API 处理分支、现场数据、条件等待、动态组合或精细操作。 |

`steps` 在前一步确认完成后才派发下一步。首个失败、取消或未知效果结束当前段。任务回执给出完成数量、当前步号、selector 和尚未执行的步数，详细输入与效果从 `tasks.trace` 读取。能力能交出具体决定时进入待决定，否则按实际结果结束。一单只有一个用户任务句柄。终态从真实步骤结果归并。

```json
{
  "action": "run",
  "params": {
    "steps": [
      {
        "selector": "prepare@1",
        "input": {
          "items": { "stone_pickaxe": 1, "torch": 8 },
          "source": "nearby"
        }
      },
      {
        "selector": "arrive@1",
        "input": { "to": { "place": "洞口" }, "arrival": "stand" }
      }
    ]
  }
}
```

这个任务用库存和站位分别验收两步。「带四块铁回到洞口」需要把入包增量和返回站位作为同一个玩法目标一起核对，适合用具名 Program 表达。现场找到的目标需要传给后续步骤时也用 Program 表达。

## P3 · 游戏结果由对应事实结算

行动合同负责验收它承诺的效果。例如库存净增、最终持有量、精确站位、目标格状态、窗口转移和命令派发各有自己的口径。普通 Program 正常返回表示执行完毕。具名玩法要承诺世界目标时，需在终点用实际读数验证，并保留可复查的依据。

子调用使用统一裁决。成功时 `mc.call` 和 `body.call` 返回原业务值。失败、取消或未知走结构化失败路径，包含裁决、原因、已确认的部分结果以及已有的效果引用。Program 可捕获后重新观察并显式决定如何继续。短序列按同一裁决停止后续派发。仅仅得到一个返回值、预测结果或聊天回显，不足以确认外部副作用。

保留既有 `succeeded / failed / cancelled / unknown / not_started`。部分成果属于进度或证据。派发前被拦截与派发后无法确认分别结算。后来读到的证据可更新查证结论，保留原动作发生时的回执。

## P4 · 接受、等待、交回与接管

- `accepted` 只确认任务受理，`confirming` 使用原句柄核对。前台让出使用现有工具续跑合同。
- 后台等待条件时保留任务，按玩法合同交还已无用途的窗口和身体资源。普通进度只更新现有任务读数。完成、待决定和需注意的既有游戏事件走现有投递。Rhythm 与游戏任务独立推进。
- 待决定有稳定的 `decision`，附已确认进展、具体阻塞和可用的查证入口。查证沿用 `nextCall` 指向可直接提交的工具参数。只有存在真实接续路径时才附 `choices: [{id, label}]`。具名选择传 `{action:"tasks", params:{op:"continue", task, decision, choice}}`。需要写新策略时，用 `entry` 代替 `choice`，形状与 `run` 的三种执行入口相同。两种形式都消费当前决定并在同一任务下新建执行段。
- 续段以原任务归属、当前决定和相应检查点为准。具名选择执行选项公开承诺的范围。显式 `entry` 可提交余下步骤。旧序列的尾部保持未派发，其历史进度留在原段。重新读取受阻现场，沿已确认进展继续。用户停止后，返回实际停止状态和已发生的效果。
- 普通序列的首发范围是活动连接内执行。已知仅根任务可用的模式在序列受理前报具体步号。执行进程丢失后，尚未派发与已派发而未知分别结算。跨进程续段只面向有具体恢复合同的根任务，并继承相应的同存档、同维度和旧写端退役条件。

## P5 · 首批要补齐的行动

| 行动 | 玩家输入 | 自动做到哪里 | 卡住交回什么 |
|---|---|---|---|
| `prepare@1` | `items` 最低持有量，`source: "inventory" \| "nearby"`。缺省用手头库存。首发支持石镐和火把的备料路线。 | 扣掉已有物品，按实际配方补半成品、工作台与照明。明确允许就地采补时才使用附近可达来源。终验背包。 | 已备齐数量、首个缺料或工作站、当前能核实的来源。 |
| `arrive@1` | `to` 为 `{place}` 或 `{x,y,z}`。 `arrival` 为 `stand` 或 `near`，缺省 `stand`。 | `stand` 要求角色脚位在目标所在方格和维度内并实际着地。当前维度内导航沿用无地形改动默认。 `near` 沿用现有两格邻近口径，回显实际位置。 | 当前站位、未满足的高度或通行条件、可用的试算或查证。 |
| `excavate@2` 与 `tunnel@1` | 清格沿用 `region`，通道沿用 `to`。往返由 Program 组合通道和到达。 | 清格确认方块实际清除。通道核对支撑、净空、脚位与实际通行。往返流程实际返回入口后结束。 | 清格会连续移除自身支撑时，报告站位和受阻格。通道失败报告可确认的最远脚位、阻塞和剩余目标。 |
| `smelt@1` 与收货 | 沿用 `item`、`count` 和 `wait` 的现有含义。 | 装料模式确认本批装入量。等待模式确认请求量实际入包。续段按已确认炉况取货或补缺。 | 炉址、确认装入的原料与燃料、成品是否读到、最短的现场复查入口。 |

其余现有动作按 P1 分类发现。 `goto@1` 保留邻近移动语义，`excavate@1` 保留显式清格合同，新推荐用具备脚位判据的版本。优先改善实际选择与交接，动作含义变化时使用能清楚区分的新合同。

## P6 · 从一次成功做到再次可用

用 `{action:"library", params:{op:"save", kind:"program", task, name, summary}}` 从任务根保存执行材料，保持原有源码及调用来源保存入口。短序列和 JS 共用一个具名流程目录。短序列保存固定步骤，参数化与动态逻辑由 Program 处理。保存回执给出可直接交给 `run` 的 selector，已执行任务引用自己的冻结材料。

可运行与已验证分别展示。编译和参数校验支持可运行判断。玩法验证依据实际任务的完成证据，并注明适用的现场条件。目录优先呈现与当前目标匹配的已验证流程。失败经验只在相关能力、失败原因和条件相符时作为线索返回。世界坐标、地标和本次库存归当前世界或任务记录。

## 归属

World 工具负责表达和发现。Minecraft Runtime 负责任务、调用与效果裁决。玩法能力负责游戏语义，Driver 负责实际操作和协议事实。Library 负责流程和来源材料。Host 负责主体回合、输入和持久投递。所有玩家专用行为在 Minecraft 一侧组合。
