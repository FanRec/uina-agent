# Minecraft 游玩接口重构路线

[设计合同](01-DESIGN.md) 定义结果，[验收门槛](03-ACCEPTANCE.md) 定义何时可发布。本文决定施工顺序、模块归属与技术选择。以开工时的当前源码为基线，保留开工提交和隔离验收数据。

## 改造边界

WorldDef 仍承接一个 Minecraft 工具。Minecraft Runtime 持有任务、执行段、调用和效果记录。玩法选择落在能力目录、动作和 Program。Driver 负责操作与协议事实，Executor 负责受理、受管执行端和可靠投递。Host 沿通用机制接收输入与工具结果。Library 由现有宿主写入口维护，Companion 读取执行材料。

需求编号 P1–P6 引用设计合同。S1–S4 是可以分别评审和验收的切片。每个切片的末尾通过正式入口提交一次真实形状的任务或读取。只验证内部方法的分支，不能作为该切片的集成结论。

与 [游玩信息交付计划](../play-context-refactor-plan.md) 共用一个 Task 投影与一套完成投递。批43 已在 `contracts/task.ts` 的 `taskView` 里补上 `completionScope`、执行范围的 `goalVerification: "unknown"` 与有界报告缺口；S1 的结果合同以该投影为准，不另写一份。信息交付的生产路径已切换为按需查询加新 visit 入场回执，接口改造不需要再处理快照注入。最终在两项改造合入后的生产路径复跑。各自负责的 Guide 例子在合入时统一。

## B0 · 先固定对照

记录源码提交、模型配置和验收环境。用隔离 Profile、独立存档和临时 session 准备 [验收场景](03-ACCEPTANCE.md#连续游玩场景)。已有直播仅用于选择真实问题，基线的请求数、结果和行为从本次隔离对照得到。先保留三段关键轨迹：多步备料的前台往返、指定站位与实际脚位、熔炼部分装料后的下一次动作。

## S1 · 统一逐步裁决与结果表达

覆盖 P3，建立 P4 的结果基础。

- 先沿 [Runtime 子调用](../../../../.uina/worlds/minecraft/runtime/engine.ts#L1868) 和 [Program Host 桥](../../../../.uina/worlds/minecraft/runtime/program-host.ts#L92) 列出本次受影响的调用者。当前子调用可能写入 `unknown`，同时把业务值正常返回。把调用结算与值一起交给调用边界。普通成功仍返回原值。其余裁决由桥编码为结构化失败，携带已有的效果引用和可证实的部分结果。
- Native 组合、普通 `mc.call` 和有身体资格的 `body.call` 共享这个裁决。保留 Runtime 对决定和持久挂起的专用传播。受影响的内置 Program 若依赖未确认返回值，改成明确捕获并走已有的观察或核验；检查 Program Guide 的示例是否要更新。
- 由 [任务投影](../../../../.uina/worlds/minecraft/contracts/task.ts#L90) 输出完成结论、已确认成果和有依据的下一次查证。完成投递和 `tasks.get` 共享它。效果和历史回执继续由原账本提供，查证保留时间与来源。

完成证据是 E1 和 E2。未知步骤的下游派发检查以 Driver/Effect 记录为准。

## S2 · 接入短序列和默认发现

覆盖 P1、P2 及 P4 的受理与让出。

- 在 [工具参数](../../../../.uina/worlds/minecraft/worlddef/schema.ts#L31) 和 [Runtime 入口](../../../../.uina/worlds/minecraft/contracts/runtime.ts#L30) 引入明确的序列变体，逐步复用现有输入合同。选择类型化线性执行。根任务按顺序发起同一套子调用，S1 的裁决负责决定是否推进。入口、进度、取消、退役和完成投递沿原 Run/Call 体系。
- 受理阶段绑定静态 selector、参数、版本和必要的 Program 材料。命名的固定序列静态展开时检查循环引用。对目录已声明的仅根模式一并做准入核对，如 `smelt@1` 的 `wait:"durable"`。动态 JS 的内部发现和世界读数沿现有 Program 运行时。行动即将派发时，用当前事实判断背包、地形或连接条件。验证失败给具体步号和字段，前面的步骤也保持未派发。
- 给 [目录投影](../../../../.uina/worlds/minecraft/companion/directory.ts#L181) 增加常用入口和短示例。执行合同仍来自唯一 Catalog。首批覆盖备料或合成、导航到地标、采集、施工和跟随等实际玩法。完整目录展开现有能力。进度从任务读数投影。
- 受理、确认期、停止和投递按原任务句柄工作。验证一批都是后台委派时主体确实交还。混合批次仍遵守既有 Host 行为，Guide 的常用示例把后台提交放在该轮最后。

完成证据是 E3、E4、E5。到这个阶段，可以用现有能力提交一条完整序列。新增玩法路线随后沿同一入口发布。

## S3 · 落实常用动作的游戏合同

覆盖 P4 的续段和 P5。

| 行动或行为 | 落点与技术选择 |
|---|---|
| 备料 | 以具名 Program 和可核验的库存目标实现 `prepare@1`。复用物品、配方、采集、合成和熔炼能力。先用石镐、火把两种实际材料链。可替代材料从已知配方选择，来源由本次参数限定。工作台、燃料或矿物不可得时报告可解释缺口。 |
| 到达与返程 | `arrive@1` 使用现有地点解析与寻路，增加玩家目标要求的站位读回。站稳失败报告实际脚位。往返 Program 在任务里保留该次入口，执行出程和回程，最后从同一个世界现读脚位和所得物。 |
| 清格和通行 | `excavate@1` 与 `excavate@2` 共用清格执行。新版本在派发相关写入前识别连续移除脚下支撑的情况。通道侧复用既有脚位、净空、支撑和实际通行判据。当前 `tunnel@1` 可正常返回 `stopped:"unbreakable"`，按已声明的通行目标把这种部分结果结算为受阻，并核对依赖该返回值的调用者。用垂直矿道验证一条可往返的 Program，再公开相应示例。几何规划属于玩法层，实时走位继续走 Driver。 |
| 熔炼和收货 | 复用炉子/容器窗口、已确认部分量和既有等待模式。部分写入时携带炉址、槽位和效果引用，仍打开的匹配炉窗可用 `ui@1` 复查。窗口关闭后给出明确的 `container@1` 复查步骤，其打开操作沿用既有身体规则。续段可用已确认炉况选择取货或补缺。持久等待限合资格的根动作，普通序列只调用能在其执行范围内结束的形式。 |
| 续段选择 | 在现有 decision 和 checkpoint 中承载实际可选分支及其接续输入。选择型 `tasks.continue` 消费当前决策，由原玩法从约定入口重新读取现场。显式 entry 复用 S2 的三种入口及准入，允许交余下步骤。原段和续段各自保存派发记录。源、检查点和世界身份使用现有所有者。 |

完成证据是 E6、E7、E8。发布的动作分别说清入包、持有量、放置、站位与过程已受理的区别。

## S4 · 保存并再次使用

覆盖 P6。

- 在 [Library 来源核验](../../../../.uina/worlds/minecraft/library/origin.ts#L12) 上增加任务根快捷路径。复制对应的冻结材料和可引用证据。来源不可读时沿原来源错误结算。可独立提交的手写源码沿现有保存入口。
- 采用同一命名空间下的两种流程源。JS 文件保留现有格式。固定步骤保存为具备显式格式版本的 JSON 文件，沿现有 Library 文件管理和摘要机制。相同名称在两种格式间只有一个绑定。按名称执行进入同一受理与调用路径。固定步骤可按原样再用，需要参数替换或条件时使用 JS。
- 编译及输入校验只用于判断材料可运行。可用场景与验证证据作为发现元数据，指向真实任务结果。失败经验由具体错误和已知条件匹配并附于相关回执，原经验仍可修订。

完成证据是 E9。成功保存、第二次被找到、完成真实玩法和改正失效条件，都属于这一步的验收。

## 切换、历史与权威文档

- 切换前让活动旧任务按受理时的合同完成或明确停止，再切换写端。新提交使用新合同。跨进程恢复继续按现有根任务资格核对，保留已派发效果和真实结果。旧历史读取不触发动作。
- 优先在现有根提交及记录结构中保存新的类型化数据。若旧版读取器无法识别新的持久含义，明确升级对应格式和隔离迁移步骤。在旧格式夹具上验证读取、重启和查询。升级完成前保留原始库；回退只使用原版本兼容的数据副本。
- 所有切片的行为变化先改所属模块合同与 [公开接口](../public-api.md)，再更新 [当前运行事实](../../../current-runtime.md) 和 [变更历史](../changelog.md)。本文负责重构范围与迁移路线。已确认的目标合同切回所属权威文档后，将本提案与验收记录一起归档。

整体验收 E10 通过后，才把游玩接口改造记为发布完成。
