# Uina 底座纠偏与下一阶段规划

状态：S1—S4 已完成并验证；后续候选仍待选择。编写及验收日期：2026-09-05。

依据：[方向与边界审查](../history/reviews/2026-09-05-direction-review.md)，审查基线为 `6b24c80`。本文件保留阶段安排，完成状态以末尾交付记录及验证证据为准。当前运行事实仍以 [current-runtime.md](../current-runtime.md) 及其对应验证证据为准。

## 目标与取舍

保留现有小内核，先让会话、工具结果、活动生命周期和模型事实在各层保持一致，再通过一个普通扩展触发的完整行为验证开放性。继续参考 Pi 的接缝与代码组织、DeepSeek Harness 的部分后台机制，以及 dsh-TUI/Pi 的交互；实现取舍服从 Uina 的实际需求。

本轮规划区分三类工作：修复已实现路径的问题；纠正违背项目原则的默认行为；通过真实场景补充尚未完成的接缝。长期记忆、TTS、感知、常驻和主动意图不作为当前漏洞，也不要求一次完成。

Core 保留稳定事实、生命周期和最小能力接口；内置与项目扩展继续共享注册与清理路径；UI 保留展示、输入、焦点和组合职责。允许修正被真实场景证明不合适的接口，不追求提前冻结一套永久架构。

## S1：统一会话与执行事实

先对齐四件事：哪些消息属于会话领域；工具未执行和执行失败如何区分；输入何时进入历史并离开队列；同一工具结论如何交给 hook、会话和 UI。复用已有类型与记录，只有实际无法表达时才调整合同。

| 工作项 | 调整方向 | 完成条件 |
| --- | --- | --- |
| S1.1 工具被扩展阻止后的恢复 | 使用已有 `not_started` 表达未执行，保留原因，统一 loop 与恢复规则 | 工具执行次数为 0；轮次可结束；真实临时 JSONL 重开成功；已启动但无结论的工具仍恢复为 unknown |
| S1.2 custom 消息与 compaction | retained tail 按会话领域消息校验，Provider 转换留在上下文边界 | custom 消息进入保留尾后能重开，内容及相关顺序保留；custom entry 仍不进入模型上下文 |
| S1.3 输入从队列移交到历史 | 以带输入 ID 的一次持久化提交完成两侧投影，消除消费后尚未写入历史的空档 | 在移交记录前后构造恢复点，输入有且只有一个有效归属；正常续跑不丢失也不重复提交该输入 |
| S1.4 工具结果贯通 | 工具提供明确执行结论与内容，Broker 统一传递；UI 和历史回放使用相同语义 | 本地 shell `exit 7` 的结果、事件、会话均为失败；succeeded/failed/cancelled/unknown/not_started 在实时与恢复视图中不互相伪装 |

涉及区域：[agent](../../src/agent/loop.ts)、[session](../../src/session/recovery.ts)、[ToolBroker](../../src/tools/broker.ts)、[内置 shell](../../src/extensions/runtime-tools/exec-command/index.ts)、[TUI](../../src/ui/tui.ts) 与 [Transcript](../../src/ui/components/transcript/transcript.ts)。

建议先完成 S1.1/S1.2，它们不依赖新的输入模型；再推进 S1.3/S1.4。S1.4 优先复用已有 ToolResultStatus，并收敛为携带内容与结论的最小结果合同；错误异常可以继续作为输入，最终要归入同一执行语义。不要让 UI 解析 shell JSON 补回状态，也不同时长期维护两套结果协议。

S1.3 只承诺会话输入移交的恢复语义，不承诺任意外部副作用“恰好一次”。单纯交换两条写入顺序不是完成条件。

如果涉及记录格式变化，先核对当前版本和已有数据。保留合法旧记录的可读性；新记录应可明确识别。对已产生的异常记录，只有能从原始事实确定含义时才提供定向恢复，保留原件并说明处理结果；无法确定时维持可定位错误。无需为此建设通用迁移平台。

**阶段验收：** 将 [core 探针](../history/reviews/2026-09-05-direction-evidence/core.mts) 和 [工具/UI 探针](../history/reviews/2026-09-05-direction-evidence/ui-cli.mts) 中相关反例转成少量行为回归测试。使用真实临时 JSONL 验证重开；至少覆盖正常工具执行、阻止执行、custom 压缩、输入移交边界和结果回放的组合。原审查脚本是基线证据，其退出 0 不等于修复成功。

| 工作项 | 调整方向 | 完成条件 |

| S2.3 子 Agent 状态 | 运行/空闲从 AgentHandle 实际生命周期派生；Registry 保留关系、输出和释放原因 | child 忙时追加消息不会产生 waiting/busy=true；排队、续跑、取消及关闭过程的快照一致 |
| S2.4 默认并发额度 | 移除没有 Uina 需求依据的默认 10 个 Job 限制 | 默认可接受超过 10 个轻量活动 producer；如保留显式配置，其行为与配置一致，不再隐式启用额度 |

涉及区域：[Subject](../../src/agent/loop.ts)、[AgentHandle](../../src/agent/runtime.ts)、[JobRegistry](../../src/extensions/jobs/registry.ts)、[SubagentRegistry](../../src/extensions/subagents/registry.ts) 与 [CLI 退出](../../src/cli/app.ts)。

单主体内确实需要顺序执行的历史修改可以串行；这属于状态归属，不是对工具或扩展新增任意并发上限。优先利用现有活动句柄与 AbortSignal，避免再加一套相互同步的 busy/compacting/closing 状态。Job 与可继续的子 Agent 可以保持不同生命周期，不为形式统一而合并。

取消不合作时保留实际运行状态与可定位诊断，不伪造结束，不自动增加任意超时。现有明确的用户退出/强制退出语义与正常释放应保持区别。

**阶段验收：** 使用可控制完成时机的 fake Provider/producer，验证 pending、取消请求失败、后来成功/失败、等待与释放的组合；补一次与真实临时 SessionStore 的组合，确认关闭后不会继续写历史。复现入口参考 [core](../history/reviews/2026-09-05-direction-evidence/core.mts) 和 [extensions](../history/reviews/2026-09-05-direction-evidence/extensions.mts)。

## S4：用一个完整行为检验开放性

建议第一个场景：普通项目扩展观察一份本地文件的真实变化，向主体提交带来源的事件；主体依据上下文决定读取、执行一个已具备的能力、稍后继续，或保持安静。若启动后台工作，结果通过同一输入入口回来。事件处理期间，用户仍能输入和取消。

文件变化只提供便于复现的非用户输入来源。这个场景用于检验接缝与活动接续，不作为“已具备自主意志”的证明。后续可以由 Uina 自己记录的关注或承诺触发类似流程。

| 需要验证的行为 | 最小证据 |
| --- | --- |
| 普通扩展可提交输入 | 从项目扩展激活入口注册来源，不改 CLI 专用闭包；主体看到来源与内容，事件不伪装成人类消息 |
| 输入、展示和对外表达可以区分 | 收到事件不强制打印一条人类发言；明确可选择不对外表达；行为经过真实模型场景检查 |
| 后台结果可接续 | 已有 Job 完成/失败后经同一入口返回，主体按需读取结果 |
| 交互仍可进行 | 后台工作运行时发送用户输入，能够处理；取消后不再启动原活动的后续动作，向运行中的 producer 传递取消，停止结果与未确认状态如实可见 |
| 扩展生命周期完整 | 卸载后 watcher/订阅关闭，不再向主体递交新事件；错误带来源并可定位 |

以现有 AgentInput 和 ActivationScope 为出发点，只开放这条路径真正缺少的 API。保留事件顺序与处理来源的可解释性。传感器平台、通用事件总线、永久宿主和远程 RPC 均不作为该实验前置。

先测当前普通输入与后台运行期间的输入响应，记录事件到达、开始处理、模型请求、首段输出和取消结算时间。试验开始时据所选 Provider 与用户体验要求写明接受的延迟范围，再比较候选；当前没有测量依据，不填写虚构毫秒目标。只让必需工作进入交互等待路径，长工具和整理工作异步继续。真实吞吐出现问题时，再按观测定义排队、合并过时事件或取消规则，不预设额度。

**完成条件：** 一个普通扩展从真实事件到主体处理、实际结果、取消/失败可见全部走通，新增入口不再要求改核心业务分支。若需要多个尚无消费者的新模块才能完成，先缩小场景或纠正一个已暴露边界；未被场景使用的抽象不保留。

## 验证、回退与后续协作

每批以具体行为作为可独立审查的改动单位。记录改动前后行为、涉及的事实归属、验证命令与未验证边界。不要按文件数量、抽象数量或测试数量判断进度。

- 用最便宜且能证明问题的层级验证：纯规则/转换、模块组合、真实临时 JSONL/子进程、本地协议、实际 Provider/设备。明确每一步是否使用 fake；日志前缀模拟不等于实际断电测试。
- 针对已复现的错误和关键组合增加回归测试；不为 getter、转发函数或纯粹镜像实现补测试。每阶段集成后运行 `pnpm typecheck`、`pnpm test`、`pnpm build`，通过后不因形式需要重复全套。
- CLI 验收使用全新工作目录与独立配置/会话，检查成功、可见失败和退出码；保护用户真实 session。真实 TTY/IME、真实服务或设备未测时如实标记，不以资源文件存在代替交互证明。
- 保留每批改动前的代码与必要数据样本以便回退。涉及日志格式时，先确认回退版本能否读取新记录；不能直接回读时，用隔离数据验收并提供明确回退办法，不无条件承诺兼容。
- 只有当实现和验证完成后，才更新阶段状态及 [当前运行事实](../current-runtime.md)。当前事实文档只写已证明内容，审查报告保留历史证据；旧提案与新实现冲突时更新状态说明，不默默混用。

实施交接时，直接引用相应工作项编号，例如“完成 S1.1/S1.2，保留真实 JSONL 重开与 unknown 恢复语义”。每批先检查相关反例，再修改其根因，最后用正常路径和反例共同验收。发现必须改变本规划的假设时，说明新证据并缩小或调整该批范围；不机械执行已失效的方案。
