# Uina 认知扩展设计

状态：设计提案，未实现。本文不把扩展可实现性、概念推演或已有测试当作长期认知效果的证明。

源码基线：`2c0ea3aa50accc3eb8bcf3e4e68048cd6b372f71`（原基线 `fc3263a` 因仓库对象重建失效，2026-09-22 重锚）。配套：[开发路线](cognition-extension-plan.md)。输入表达沿用[外部事件帧设计](../../proposals/runtime/external-event-frame-design.md)，该设计已于 2026-09-22 完成 Host 默认装配。

## 1. 结论

采用一个官方认知扩展：**少量稳定行为说明、按需读取的长期记忆、明确的写入工具、可关闭的后台整理**。它通过现有 Hooks、工具、会话查询和输入入口工作，不再建一个独立认知运行时。

长期记忆第一版使用带最少元数据的 Markdown 文件。搜索索引是可重建的加速层；以后可以接全文数据库、向量检索或外部记忆服务，但同一条记忆始终只有一个权威写入者和一个当前版本。

不同“人”的隔离值得做。主体身份与存储根属于 Host 装配，记忆解释属于认知扩展。不同人物使用独立主体目录、会话、可变应用状态和设置；同一人物的多次会话共享其长期记忆。

长期战略：让经验能修正行为，让模型升级直接获益，同时让任何认知政策都能删除或替换，不破坏历史事实。

## 2. 六条规则

1. **事实和理解分开。** 原始输入、工具结果归 journal；笔记、印象、方法是可修订的理解。
2. **按需要读取。** 常驻少量身份与记忆线索，完整内容通过工具展开。
3. **写入有依据。** 保留来源、适用范围和当前版本；不把重复转述算多份证据。
4. **每份状态有一个主人。** 每个主体一个记忆写入者，每条记录一个权威当前版本。
5. **慢工作离开前台。** 默认回答前不追加一次模型检索、反思或记忆抽取调用。
6. **用结果决定复杂度。** 只有检索、纠错、延迟或可靠性实测不够，才增加新机制。

不建立五层脑区、情绪评分器、动机总线、多个互相审判的 Agent、知识图谱默认依赖、通用学习框架或自动修改代码的能力。

## 4. 最小架构与所有权

```text
CLI 选择 Profile → Host 固定主体身份、数据根、会话与能力装配
                         │
外部环境 → 统一输入 → Subject → 模型 → 普通工具 → 实际结果
                         │         ↑
                         └── 认知扩展
                              ├─ 拼接必要上下文
                              ├─ 搜索/读/写长期记忆
                              └─ 可选后台整理 → 同一记忆写入者
```

| 层 | 拥有 | 不拥有 |
| --- | --- | --- |
| Core | 输入、调用、执行、历史、journal、hooks/events | subject 人格、记忆目录结构、反思策略 |
| Host | 主体身份绑定、路径、会话归属、生命周期、能力配置 | 笔记是什么意思、哪些经历值得记住 |
| 认知扩展 | 身份说明的使用、检索与写入规则、整理、行为经验 | Provider wire、UI、真实执行事实改写 |
| 环境扩展/App | 环境观察、动作、实际状态与回执 | 直接修改其他主体的记忆 |
| UI | 展示有效配置、来源、记忆状态和操作结果 | 主体/记忆的权威状态 |

先实现一个能力内部的少量模块，不将每项功能拆成独立插件。event-frames 负责输入编码；cognition 负责记忆及行为说明。Host 只装配一个 ProjectionPolicy，cognition 使用原有 context hook，不抢第二个投影 owner。

## 5. “不同的人”：需要隔离什么

三个概念保持分开：

- **personaTemplate**：一份可复用的初始性格/表达模板。
- **subjectId**：一个持续个体，绑定一套独立经历与持久状态。
- **actorId**：这个个体遇到的其他人；不能拿昵称当稳定身份。

改模板、模型或配置不自动创建新人；换 subjectId 才是另一个个体。仅复制模板默认创建空白经历，不复制原人的会话、承诺、令牌或缓存。

建议新增的显式 profile 目录：

```text
<subjectsRoot>/<subjectId>/
  profile.json                 主体标识、模型引用、能力开关、工作目录
  persona.md                   人类可编辑的初始行为/身份说明
  sessions/                    此主体的 canonical journals
  memory/
    records/<id>.md            当前权威记忆
    revisions/<id>/            历史版本，仅按需查阅
  state/
    cognition.json             整理水位/禁用状态等运行状态
    worlds.json                  该主体的应用启停状态
    settings.json              该主体的模型/会话偏好
  app-data/<appName>/           该主体的应用可变数据
  cache/                       可重建检索缓存
```

这个目录只是落盘布局，不等于 Profile 的全部语义。Profile 应分成六个层次：

| 层次 | 必需内容 | 作用 |
| --- | --- | --- |
| Identity | `subjectId`、显示名、模板版本 | 确定“这是哪个人” |
| Persona | 稳定行为原则、表达偏好、禁止事项 | 提供低频、可人工审阅的身份底色 |
| Cognition | 记忆开关、召回预算、整理开关、默认作用域 | 选择认知策略，不保存运行事实 |
| Sessions | 当前会话目录、默认会话名、回放策略 | 决定对话历史归属 |
| Resources | workspace、memory、state、app-data、cache | 固定所有权和可变数据边界 |
| Runtime policy | 模型引用、工具集、环境扩展、权限与并发配置 | 决定这个人能接触什么世界 |

Profile 不是一串“人格参数”。它是 Host 在启动时解析出的不可变装配结果；模型和扩展不能通过普通文本修改 `subjectId`、资源根或其他主体的权限。

Cortico 的 `persona/` 目录值得学的是职责拆分：稳定身份说明、环境说明、记忆说明、交接说明分别有主人。Uina 不必复制它的文件数量；只有在内容拥有不同生命周期、不同写入者或不同验证方式时才拆文件。建议第一版只保留：

```text
persona.md          稳定身份与行为原则
memory-policy.md    记忆使用纪律（可选，短文本）
profile.json        机器配置与能力绑定
```

World/环境说明由环境扩展提供，交接和记忆规则由认知扩展提供，不把所有文本都塞进 `persona.md`。后续某一部分需要独立编辑、版本、权限或测试时，再拆出专门文件。

### Session 与 Profile 的关系

Session 不是人物。一个 Profile 可以拥有多个相互隔离的 Session；这些 Session 共享该人物的长期记忆，但拥有独立的对话历史、临时上下文、未完成输入和回溯主线。

```text
Profile: alice
  ├─ Session: qq:group-1
  ├─ Session: qq:dm-42
  └─ Session: project-x

Profile: bob
  └─ Session: qq:group-1
```

`subjectId` 隔离人物；`sessionId` 隔离场景。`actorId` 只标识人物遇到的其他人，不能代替 session。默认不把同一人物的所有外部消息塞进一条历史；接入层必须按稳定的 channel/space/thread 规则选择 session。

建议的 session 归属键为 `profileId + sessionId`。Session journal、队列、回溯和当前上下文都属于这个键；记忆默认属于 `profileId`，再由 `scope` 限定适用空间。一个 session 关闭不会删除人物长期记忆；删除人物也不能悄悄删除其原始 journal，必须是单独的明确操作。

第一版可继续让 CLI 一个 Host 只打开一个 session，但数据模型与 Host 装配要预留 `sessionId`。同一 Profile 的多 session 可以先通过多个 Host 进程实现；不要在当前 Subject 内提前发明多消费者、多上下文调度器。

Cortico 的 `cormini` 默认更接近“一个 deployment 一个持续 session”；这适合单一终端主体，不足以直接覆盖 Uina 的多聊天场景。Uina 应借鉴 Persona 可声明 session 的思路，但把 Profile 和 Session 明确拆开。
subjectsRoot 由 Host 显式解析，不从模型文本读取。工作区 cwd、共享扩展代码路径、主体 stateRoot 是三个不同概念。多个主体可读同一项目代码，但不因此共享记忆或 App 状态。

第一版一个进程只激活一个 profile；切换人物关闭旧 Host、等待 teardown 后创建新 Host，不在活动 Subject 上热换身份。允许不同进程同时运行不同主体；同一主体数据根只允许一个活动写入进程。首版在启动任何能力前用排他创建（wx）取得锁文件，记录随机 ownerToken 和 PID；正常关闭在全部写入结算后核对 ownerToken 再删除，不能删除后来进程的锁。

锁实现需 Windows/Linux 的双进程测试。崩溃残留锁明确阻止启动；提供检查与恢复命令，只有能确认旧进程已退出或操作者明确处置时才清理。PID 可能被复用，不能仅凭时间过期偷锁。允许第一版保守地要求人工恢复，不为此引入租约、心跳或分布式锁。

子 Agent 默认属于父主体的临时执行者，不是新人物。可以通过绑定的记忆服务读父主体信息；写入仍经父主体同一个 writer。独立人物间的协作通过明确消息，不能继承对方 MemoryStore 引用。

共享资源只允许显式配置的只读知识资料；不得把所有个人记忆放进一个池，再只靠每次调用传正确的 subjectId。模型工具参数不接收任意 subjectId 或其他主体路径。

**隔离边界：**以上保证官方接口、检索、会话及状态不会意外混用。受信任扩展和全权限 shell/文件工具仍可能访问其他目录；需要强安全隔离时使用 OS 用户/容器。这一版不声称提供敌对代码隔离。

CLI 建议增加 `--profile <id>`。不传时保持现有启动与数据位置；认知 profile 显式启用，不把旧 data/session.jsonl 自动搬走或混入新人。凭据通过已有 Provider 配置只读引用，不复制到 persona 或 memory。新增参数和路径必须同步 DECISIONS/FACTS，并覆盖 TUI、stdio、oneshot 与无 UI。

## 6. 记忆方案选择

这里按设计路线比较。Hermes/Mem0 仅用于对应用户提到的思路，不对其当前版本、接口、性能或支持功能作已核实断言；本次不继续外部调研。

| 路线 | 适合承担的职责 | 主要代价 | 本方案裁定 |
| --- | --- | --- | --- |
| Cortico 式文件工作区 | 可读写的长期笔记、经验、身份连续性 | 来源、冲突、检索质量仍需自己定义 | 吸收可读性与普通工具思路，补少量元数据 |
| Hermes 类核心记忆＋可复用方法路线 | 小量常驻个人信息、任务方法的逐步积累 | 常驻内容易膨胀；程序性经验易过度泛化 | 吸收小量锚点与按需方法，避免全量注入 |
| Mem0 类自动抽取/记忆服务路线 | 降低抽取、召回的工程成本 | 抽取误差、服务依赖、来源/删除/隔离需要核查 | 首轮不依赖；以后作为候选生成或检索适配器 |
| 专用数据库 | 大规模查询、事务、并发索引 | schema、迁移、部署与维护成本 | 出现实测瓶颈再引入，不先造“记忆数据库产品” |
| 分职责组合 | 本地权威记录＋可重建索引＋可替换整理器 | 需要明确谁能写权威内容 | 推荐的长期结构 |

**混合的是职责，不是两个同时写事实的系统。**

第一版记录用文件，启动时构建内存索引，按标题/关键词和作用域检索。中文先用确定性的字符片段匹配，不依赖模型生成英文关键词。给模型普通 search/read 工具，允许它根据当前任务继续查找。

以后可加 SQLite FTS、向量库或远端搜索：只返回 memoryId、revision、匹配片段；最终从当前权威记录读取正文。失效版本、已忘记记录或错误作用域的命中必须丢弃。缓存键包含主体、作用域、内容版本，禁止跨人物复用。

如果将来确定第三方服务更适合做权威存储，应整体验证导出、修订、删除、命名空间和故障语义，再迁移写入所有权，退休原文件写路径。不得长期保持文件和服务双向同步的双主状态。

## 7. 最少的数据模型

一条记录就是一个稳定 ID、一段 Markdown 和一行机器可解析的 JSON 元数据。不引入 YAML 解析器、复杂分类体系或图节点。

```text
<!-- uina-memory {"schema":1,"id":"m42","revision":3,"type":"note","basis":"reported","scope":{"spaceId":"private:alice"},"sources":[{"sessionId":"s1","entryId":"e8"}],"status":"active","pinned":false} -->
# Alice 的回复偏好
Alice 在该私聊中明确要求先给结论，再按需要展开。不能据此推断她在所有场合都偏好短文。
```

- type 仅为 note、commitment、procedure。偏好、人物印象、世界知识先用普通 note，不先创造更多对象类型。
- basis 为 observed、reported、inferred；来源是“用户说过”不等于外部世界已验证。不要生成虚假置信度小数。
- sources 指向本主体 journal 的 sessionId/entryId；对工具效果必须能追到对应真实结果。来源不可用时明确标记，不编造原话。
- scope 是适用范围；可含 spaceId/projectId/actorId，已填字段必须全部匹配当前接入上下文。无字段代表该主体全局，需明确选择，默认写入当前作用域。
- status 仅 active/retired；修改同一认识沿用 ID、增加 revision，旧版本不参加常规召回。
- pinned 是少量主动锚点；仍受作用域与上下文预算约束，不能越过隔离。
- body 允许普通自然语言；精确引用和模型理解需要写清。无需把所有知识拆成主谓宾。

scope 来自接入层和当前输入，不能只信任模型传回的 subjectId/actorId。当前来源不够明确时只使用主体全局的非敏感锚点，不猜会话身份。

memoryId 与路径由 writer 分配，工具只接受 ID，不接受任意 filesystem path。手动编辑支持离线进行，重新启动校验；在线变更需通过统一写入路径。revision 用于展示，更新条件使用读出时的整文件内容 hash，防止外部编辑未递增 revision。

## 8. 普通工具即认知动作

第一版只需三个工具：

| 工具 | 作用 |
| --- | --- |
| memory_search(query) | 在当前绑定主体/作用域检索，返回 ID、摘要、版本与来源提示 |
| memory_read(id) | 读取当前可用记录全文与来源；不返回其他作用域的内容 |
| memory_write(operation) | create/revise/retire，经同一 writer 验证与提交 |

修改需要 expectedHash；创建/修改必须提供来源引用，或明确 basis=inferred 并保留其依据。writer 验证引用存在、属于当前主体与可用历史范围，验证对象版本和 schema；它不能证明自然语言推论正确，不假装具备这项能力。

每次写入顺序：验证 → 串行 writer → 备份旧版本 → 写临时文件并 flush → 替换当前文件 → 更新内存索引 → 返回成功。进程异常时当前文件应为旧版或新版；不承诺所有操作系统与实际断电下未验证的原子性。

写成功但索引更新失败时以文件为准，重建索引并报告检索降级；不能假装记忆未写成功诱发重试创建。备份失败则不覆盖旧版。多记录批次允许部分成功，逐条返回结果，不发明跨文件事务框架。

空白返回、校验失败、版本冲突不能报告“记住了”。冲突返回当前版本，调用者重新读取后再决定；不自动重试覆盖。

retire 表示不再常规使用，仍保留版本与历史。用户要求“忘记”使用明确命令，由 writer 先写持久抑制记录，立即停止召回，再清理当前文件、版本、缓存与外部索引；相应来源进入整理排除集合，避免从旧日志重新长回来。

遗忘长期记忆不等于删除原始会话。历史擦除属于单独的明确操作，不静默重写 canonical journal。文档/界面必须如实说明删除范围；未来接远端服务时确认远端删除，否则显示未完成。新的明确重新介绍可以形成新来源，不永久封禁一个话题。

## 9. 每次模型请求看什么

```text
稳定前缀：运行契约＋persona.md
真实历史：外部事件帧、内部通知、模型行为、工具结果
当前记忆线索：小量锚点/匹配摘要，带 ID、来源和适用范围
```

人格基础说明由 profile 加载，后台整理不直接改写运行契约或 persona.md。学到的风格与经验先成为普通记忆，可通过 pinned 提高可见性，但仍是可质疑、可修订的信息。用户显式要求修改 persona 时走配置操作，不把模型随口总结当作宪法更新。

自动检索只做本地确定性查找：来自最新已接纳输入的文本与已知 actor/project 线索，绝不把整个历史先送另一个模型生成查询。没有相关内容就不注入。模型需要更多背景时主动 memory_search/read。

第一版上下文只有一个认知 hook owner。顺序固定为：事件投影 → 既有 compaction → cognition 的瞬态记忆块 → 最终协议校验。记忆块不落 journal，不修改旧消息，每次从当前记忆重新生成。

这样过去的瞬态检索不会被再次当成独立经历归纳。压缩需要预留配置的记忆增量预算；请求最终估算必须同时包括工具 schema。当前 token 估算与图像成本的未知性仍存在，不能承诺字符估算等于精确窗口。

memory/search 注入失败时降级为无检索，不阻塞回答；先丢可选记忆，不丢最新用户输入、工具终态或来源标签。身份配置非法应在启动时报错，不能用别人的 profile 填补。

普通内部报告通过 user 表达，来源写成 memory/summary，不是系统命令。环境原话继续使用 external_event_frame；真实工具读到的内容继续使用原有 tool result。

## 10. 后台整理：可选、可取消、不过度自动化

第一阶段不开自动整理，先证明前台明确记忆的写、读、用、纠错。之后提供手动整理，再根据纠正、任务结束等新证据启用空闲整理。没有新材料不调用模型，不默认定时“空想”。

一个主体只有一个整理 worker。触发只记录待处理历史范围，重复触发合并水位，不排一串重复任务。事件 handler 只排期并立即返回；worker 用独立取消信号调用 pi.models.stream，不把模型工作放进被 await 的 agent_end handler。

整理器读取不可变历史范围与记录版本，输出针对已有记录的 patch：合并重复、纠错、补来源、收束未完事项。第一版不让后台批量创建新事实或任意改写身份；新记忆主要由前台明确工具形成。

提交前检查：主体绑定未变、scope 未关闭、来源仍适用、目标 hash 未变、抑制记录没有新增。旧 patch 不满足时跳过并报告冲突，不能覆盖前台新写入。

每条 patch 独立提交；批次崩溃后保留已提交结果，不自动重放旧 patch。重新从当前文件/历史读取再整理；相同内容写入为 no-op。整理水位是扩展运行状态，不能用“水位前进”替代实际记忆文件写成功。水位、遗忘抑制等 cognition.json 的读改写也进入同一个串行写入通道，避免两个后台动作覆盖彼此状态。

关闭时 abort worker，阻止新的提交，并等待已进入 writer 的短提交结算。Provider 不响应取消时，scope 关闭和 generation token 仍须拒绝迟到 patch；不得显示整理成功。当前 pi.models.stream 被 ResourceScope 跟踪，deactivate 还会等待 pending，因此防迟到写入不等于能立即关闭。自动整理启用前必须验证所用 Provider 的取消会结算；否则显示仍在关闭，不能释放锁并启动同一主体的新 Host。后台调用只读取证据，不持有真实外部动作工具，因此迟到模型输出不会直接产生外部副作用。

常规整理完成不唤醒主体，也不向人类播报“我刚做了一场梦”。只有影响当前未完事项的明确结果才经 submitInput 回流；结果标 internal/report，不升级为命令。

整理的稳定提示只需：区分事实/陈述/推断；同一事件的转述不算独立证据；保留纠错与来源；少改且精确；整理多于追加；无法判断就保留不确定性。

## 11. 行为经验与主动性

procedure 是有适用条件的方法笔记：何时用、建议做法、支持经历、反例。模型按需读取；不会因为文件存在就自动执行，也不安装代码或扩大工具权限。

升级为常驻经验前，应在固定场景中证明它改善实际结果。删除一个失败的方法不会破坏 journal；切换模型后重新评估，不假设旧模型形成的技巧永远有效。

commitment 是承诺/未完成事项的记忆。记录截止日期不代表已经设置闹钟；需要提醒时调用现有/以后独立的调度能力，并确认其受理回执。认知扩展不悄悄长出第二个调度器。

未来注意力机制也先在环境扩展合并可替代快照；用户请求、工具终态、承诺变化不能按“只保留最新”丢弃。没有证明调度不足前不改 Mailbox。

## 12. 最小接口与模块

建议 `src/extensions/cognition/` 初始只有：

- `index.ts`：activate、生命周期、三个工具、配置装配。
- `context.ts`：本地召回和瞬态块构造。
- `memory.ts`：文件格式、作用域、搜索、单 writer、版本与遗忘。
- `consolidation.ts`：可选 worker、范围水位、patch 验证。
- `PROMPT.md`：短行为协议。

Host 增加 profile/path 装配模块。不为每个认知名词建包。

```ts
// 扩展内私有接口，不是 Core MemoryPort，也不是对第三方的永久 SDK。
interface MemoryRepository {
  search(query: string, scope: RecallScope): Promise<MemoryHit[]>;
  read(id: string, scope: RecallScope): Promise<MemoryRecord | undefined>;
  write(change: MemoryChange): Promise<MemoryWriteResult>;
  close(): Promise<void>;
}
```

RecallScope 是 Host/接入上下文导出的作用域；MemoryHit 包含 id/title/excerpt/hash，MemoryRecord 对应 §7；MemoryChange 对应 §8；结果区分 committed/conflict/rejected 并带实际记录版本。绑定 subjectRoot 在构造时完成，不出现在模型参数中。

实现第一版时以上接口也可以只是一个类的私有边界。接入第二种真实后端后再决定是否抽象，不为假想数据库预造 adapter 插件系统。

## 13. 当前阻碍与改动优先级

| 问题 | 最小处理 | 归属/时机 |
| --- | --- | --- |
| 事件帧已实施，外部输入不再压成普通 user 文本 | 认知扩展沿用 Host 默认的 `external_event_frame` 投影，不另做 | 已合入 `287bb27`，不再是前置 |
| 无统一主体目录/应用状态根 | Host 固定 profile；给扩展注入绑定的 stateDir；App 可变目录单独传入 | Host/Extension API，隔离前必须 |
| 全局设置跨人物 | load/saveSettings 接受显式路径，默认保持旧行为 | ai 配置/Host，隔离前必须 |
| 跨会话来源查询不足 | 暴露只读当前 session ID；Host 给认知扩展绑定的历史读取器，仅访问自身 sessions | 公共会话事实＋Host 装配，记忆闭环必须 |
| 结果 hook 可覆写原始执行状态 | 持久结论与模型可见正文分开；先保原始结果，再处理展示 | Tool execution，在自动归纳工具经验前必须 |
| 多个 hook 最后覆盖 system | 官方认知一个 owner，明确装配顺序；不增加中央 ContextManager | Host/扩展组合，必须 |
| 摘要同步及全请求预算不足 | 先做记忆预算预留/末端估算；耗时摘要优化独立测量后再做 | compaction/请求组装，必须/后续 |
| 后台任务随 scope 关闭 | 独立 worker＋abort/generation guard＋teardown；不要求先重写 Job 框架 | 认知扩展，启用整理前必须 |
| 通用文件工具可绕过记忆 writer | 官方记忆写路径只用 memory_write；声明受信任工具边界，强隔离另选 OS 机制 | 工具装配，不假造沙箱保证 |
| 回溯后旧经验适用性 | 保留真实已发生的外部结果；放弃的任务意图不能继续当当前承诺，来源标记并复核 | 认知能力，必须 |

不为了认知功能新增情绪、动机、Memory、Dream 等 Core 概念。跨会话库是独立权威状态，不能把所有长期内容塞进当前 session auxiliary；auxiliary 适合该会话的引用与运行信息。

## 14. 性能与故障合同

前台新增路径只读本地缓存/文件，不等待整理，也不进行额外模型调用。建议验收目标为在固定本机数据集上新增上下文准备 p95 ≤ 50ms；这是实验目标，不是当前已证明的性能或内核硬限制。

记忆上下文预算是 profile 可配置值，首次可用 1,200 估算 token 做实验；它约束该能力的注入量，不限制主体工具轮数或并发。锚点也在预算内。窗口未知时使用显式注入预算，不伪造模型容量。

索引不可用：当前主体文件关键词查询或本轮跳过；远端不可用：使用本地权威记录；写失败：明确未记住；记录损坏：报告文件并排除该项，不能拿其他主体库回填。

整理积压只保存“尚未处理的范围”，不无限创建模型任务；来源缺失、关闭、回溯变化都能停止该轮处理。大型语料无法达到前台目标时，才引入后台索引，不把耗时扫描搬进每次请求。

## 15. 验收、停止与演进

必须证明完整行为链：写入 → 跨新会话召回 → 正确使用 → 后来纠错。仅向上下文注入一段字符串不算验收。

基础场景：

1. A 人物记住一个专属暗号；B 人物相同问题、搜索、重启、缓存命中均不能得到它。
2. 同一人物新会话记住偏好；无关任务不套用该偏好。
3. 对方改昵称仍用稳定 actorId；同昵称不同 ID 不串档。
4. 用户修正旧认识后，旧索引命中也不能恢复旧正文。
5. 后台读旧版本、前台写新版本，后台 patch 必须冲突而不覆盖。
6. 被回溯放弃的任务不继续成为当前承诺；真实外部副作用仍保留证据。
7. forget 后常规召回、缓存、整理均不重新出现；如保留原始会话要明确说明。
8. 模型报告工具成功，但实际 unknown/failed，记忆不能升级成功。
9. 整理未启用时零后台模型调用；启用后无新材料也不空转。
10. 关闭、换人、进程崩溃后不提交迟到 patch，不把未完成记忆写入报告成成功。

对照基线是相同模型/工具/样例下的无长期记忆版本。先定样例和评分：相关召回、无关误用、纠错成功、跨人泄露、额外调用数、延迟。隔离泄露和未确认成功必须为零；明确任务不能新增关键失败。记忆使用质量由模型实跑和人工评估共同判断。

门槛：在固定样例上有可复现收益才启用默认整理；文件检索召回不足时加入全文索引；表达不同但语义相近的查询持续漏召回时测试向量检索；并发/写入或查询事务成为实测问题时考虑专用数据库。

若增强没有改善指标，删除增强，保留可读记录。替换后端时导出内容与来源，重建索引，冻结旧 writer，验收后移除旧写路径。不要留下永远并行维护的两套架构。

## 16. 长期不变与允许变化

长期不变：输入与执行事实可追溯、主体归属明确、记忆能纠错、状态只有一个写入主人、扩展失败不伪造成功。

允许变化：人格文本、记忆介质、检索算法、整理模型、触发策略、经验格式。模型越来越强时，可以删掉不再有收益的补偿规则。

推荐首先实施“两个隔离主体＋每人三个记忆工具＋一次跨会话纠错”，之后再增加自动整理。这条切片同时检验效果、纯内核边界与长期潜力。
